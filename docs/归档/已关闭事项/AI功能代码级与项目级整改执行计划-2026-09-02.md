## 3. 整改目标与完成定义

### 3.1 目标

1. 建立跨需求识别、Plan、UI、Build 和准入层唯一且闭合的任务类型契约。
2. 对任务类型冲突、用户点名算法、承诺输出和任务极性实施显式、可测试的 fail-closed 校验。
3. 用业务语义绑定替代 `Any`/首个兼容端口驱动的关键连线，确保业务结果真实到达 `ResultOutput`。
4. 让图像来源、节点身份和公开诊断与用户选择、图结构和真实失败原因一致。
5. 把报告中的一次性复现转成永久回归门禁，并完成旧 Plan/旧别名兼容验证。

### 3.2 全局完成定义（DoD）

- `AI-01` 至 `AI-10` 每项均有产品修复、永久测试、测试结果和代码审查结论，状态全部为 `[x]`。
- 原始“划痕缺陷 + 计算面积 + Canny”场景不再发生任务类型冲突，不再把规则推断伪装成用户明确输入；生成路线保留 Canny 能力并输出约定的面积语义。
- 所有可解除 `task_type` 的值都有唯一规范值、兼容别名、默认路线和 v2 路由合同；PLC 输出不再抢占主检测任务。
- 路由准入同时验证处理能力、从输入到处理器再到终点的路径、判定语义和承诺业务字段可达性；处理器本身不得充当合格终点。
- `Image -> ResultJudgment.Value`、计数值复用为置信度、Blob-only 模板定位等已知错误图被永久测试拒绝。
- presence、defect、template、sequence、classification、measurement、code recognition、object detection 均至少有 `OK / NG / 边界或缺失条件` 用例，判定极性正确。
- `file_sample` 生成 `SourceType=File`，相机类选择生成 `SourceType=Camera`；不支持的输入来源显式阻断，不再静默退化。
- 同一流程内所有 `TempId` 唯一，且对重复算子和前置节点数量不敏感。
- 对外主诊断优先展示最具体、可操作原因，同时保留通用摘要作为次级诊断。
- 后端定向回归、Product 全量回归、服务门禁、Desktop 端点门禁和相关前端测试全部为绿色；测试数量不得因删除或改名而无说明下降。

## 4. 开工前冻结的设计决策

以下决策用于避免五个工作块分别发明不兼容口径。若实施时必须改变，先在本节追加“变更原因 + 兼容影响 + 新测试”，再修改代码。

### 4.1 任务类型与来源可信度

- 规范主任务集合收敛为：`presence_absence`、`attribute_classification`、`object_detection`、`template_location`、`surface_defect`、`geometry_measurement`、`wire_sequence`、`code_recognition`。
- `classification`、`barcode_qr`、`surface_or_pose_defect` 及现有 route-only 名称只作为兼容别名；进入 Plan 有效值、Build 和准入前必须归一到上述规范值。
- `plc_output` 是 `output_target`/输出通道要求，不是主任务；`button_inspection` 是路线场景模板，不是新的任务类型。
- `general_inspection`、`custom_task` 不得产生 `resolve_field` 效果；若无法归一到规范任务，保持待澄清并阻断 Build。
- 启发式分类、关键词命中或正则推断使用低可信度来源，不得标记为 `explicit_user_text`。优先新增 `rule_inferred`，同时兼容读取 `legacy_inferred`；只有能绑定到原始用户文本明确值及证据片段的直接选择才可标记为 `explicit_user_text`，前端和后端使用同一优先级表。
- 没有用户明确选择时，只要语义、成熟度、规则答案的规范任务不同，就产生结构化 `task_type_conflict`，不得 Overlay 覆盖后继续构建。用户明确选择可解除冲突，但冲突轨迹仍需留在审计字段中。
- “检测划痕并计算面积”解释为主任务 `surface_defect` 加业务输出/测量目标 `defect_area`；“面积”不得单独把主任务改写为 `geometry_measurement`。

### 4.2 路线与方案忠实度

- 路由合同升级为 v2，并至少描述：规范任务、允许处理能力、必需处理能力、判定输入语义、必达业务结果、合法终点和兼容别名。
- 合格图必须存在 `图像源 -> 任务处理器 ->（需要时）ResultJudgment -> ResultOutput` 的有效路径；处理器自身不再视为终点。
- 用户点名的算法、算子或输出字段属于强约束。只有用户明确接受替代方案时才允许替换；“目录中不存在”的判断必须由实际算子目录验证。
- v1 旧草稿可以加载和编辑，但在 Apply/Deploy 前必须按 v2 重评；不得因历史来源而放行语义错误图。

### 4.3 连线、结果和判定

- 数据类型兼容只是连线必要条件，不是充分条件。`ResultJudgment.Value`、`ResultJudgment.Confidence`、`ResultOutput.Text/Data` 和 mask/region 类关键输入必须由任务感知的业务语义映射决定。
- `Any` 回退不得用于关键业务端口；普通图像预处理链可保留受限的 `Image -> Image` 回退。
- 一个输出只能承担其声明语义。计数不能兼作置信度，图像不能接入判定值，预览图不能替代缺陷掩膜。
- 用户承诺的字段必须到达 `ResultOutput`：码值走 `Text`，结构化详情/位姿/特征走 `Data`，判定走 `Result`，预览图走 `Image`。
- 若面积仅存在于集合或嵌套特征中，必须生成明确的提取/聚合语义；在没有确定“总面积/最大面积/单个面积”规则时标记输出目标未解决，禁止用 `BlobCount` 冒充面积。
- 判定参数由“任务 + 实际上游端口语义 + 用户验收条件”共同生成。缺少验收阈值时保留 pending，不得用通用 `>= 1` 猜测。

### 4.4 兼容与诊断

- 旧字符串值在完整性/Plan Hash 校验之后做内存归一化，不静默重写历史快照；审计事件同时保留原值和规范值。
- 诊断选择采用明确优先级：具体可操作原因 > 结构/端口/参数原因 > 通用摘要。通用 `route_semantics_not_satisfied` 可保留，但不得遮蔽 `route_missing_task_processor` 等具体原因。
- 所有公开诊断继续经过现有脱敏边界，不为提高可操作性而泄露路径、Prompt、资源标识或内部异常文本。

- 旧 Plan 先按原始快照计算和核对 Hash，再做内存任务别名归一；Hash 不一致路径拒绝继续，兼容事件保留 raw/canonical 审计证据。

- 未提供的测量、存在性、目标数量或缺陷验收值继续保持 pending；仅任务固有 Boolean 语义及“成功读到码”使用明确判定。
- File、Camera、待确认和不支持来源由单一解析器分流；unknown/video 不退化为 Camera，资源绑定仍与来源能力分离。
