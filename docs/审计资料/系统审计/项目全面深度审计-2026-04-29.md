ClearVision 当前已经不是“算子堆叠型 Demo”，而是一个具备工程分层、桌面端运行时、WebView2 本地工作台、155 个正式算子、独立 NuGet 算子库、质量矩阵和质量飞轮证据体系的工业视觉平台雏形。

本次审计的总体判断是：

```text

本地桌面端 API 验证：较强
CI 真实测试覆盖：存在关键缺口
密钥与本机 API 安全边界：存在高风险
实时检测启停链路：存在可复现失败
现场数据 / 真实 field replay：仍需谨慎对外表述
```

| 优先级 | 结论 | 影响 | 证据 |

## 2. 架构审计

### 2.1 正向发现

当前架构分层基本清晰：

| 层 | 作用 | 观察 |
|---|---|---|
| `Contracts` | 跨层消息、DTO、接口契约 | 已独立项目化，利于桌面端/外部包复用 |
| `Core` | 实体、值对象、枚举、领域接口 | Operator / Flow / AppConfig 等领域对象较完整 |
| `Application` | 项目、用户、检测、AI 编排等应用服务 | 业务服务与基础设施有明确边界 |
| `Infrastructure` | OpenCV、相机、PLC、AI、算子实现、存储 | 算子和运行时能力集中，复杂度最高 |
| `Desktop` | WinForms + WebView2 + 本地 Kestrel API | 产品入口明确，可做桌面工作台 |
| `Acme.OperatorLibrary` | 独立 NuGet 打包 | 使用 linked compile items 复用主项目算子源码 |

架构上的成熟点：

- 使用 `OperatorMetaAttribute` 统一算子元数据，155 个正式算子口径可扫描。
- 桌面端采用本地 Kestrel API + WebView2 UI，便于前后端分离和接口测试。
- `InspectionRuntimeCoordinator` / `InspectionWorker` 将运行状态和后台执行拆开，方向正确。
- 独立算子库已经能打包为 NuGet，并有 smoke/acceptance 测试。
- 质量飞轮已经从“文档清单”推进到矩阵、baseline、suite manifest 和 release gate。

### 2.2 架构风险

#### A1. 主 solution 未包含测试项目

证据：

- `dotnet sln Acme.Product/Acme.Product.sln list` 仅列出 6 个 `src` 项目。
- 本地执行 `dotnet test Acme.Product/Acme.Product.sln --configuration Debug --no-build --no-restore --verbosity minimal` 退出码为 0，但没有测试输出。
- CI 的 `Run Unit Tests with Coverage` 使用的是 solution 路径：

```text
.github/workflows/ci.yml:76-84
dotnet test ${{ env.SOLUTION_PATH }}
```

影响：

- CI 的“Unit Tests with Coverage”可能没有运行 `Acme.Product.Tests` 和 `Acme.Product.Desktop.Tests`。
- 后续检测类/性能类脚本会补一部分测试，但服务、端点、认证、项目保存等普通回归不一定进入门禁。

建议：

1. 将两个测试项目加入 `Acme.Product.sln`。
2. 或 CI 改成显式执行：

```powershell
& "./scripts/run-tests-services-regression.ps1" -NoBuild -NoRestore
& "./scripts/run-tests-desktop-endpoints.ps1" -NoBuild -NoRestore
& "./scripts/run-dotnet-test-serial.ps1" -Project "Acme.Product/tests/Acme.Product.Tests/Acme.Product.Tests.csproj" ...
```

#### A2. 本地 API 安全边界偏宽

证据：

```text
Acme.Product/src/Acme.Product.Desktop/Program.cs:125-130
policy.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader();

Acme.Product/src/Acme.Product.Desktop/Program.cs:133-135
options.ListenLocalhost(_webPort);

Acme.Product/src/Acme.Product.Desktop/Middleware/AuthMiddleware.cs:129-138
支持 query string token 与 X-Auth-Token
```

风险判断：

- 监听 `localhost` 降低了局域网暴露风险，这是正向设计。
- 但 `AllowAnyOrigin` 使任意网页都能向本机端口发起跨源请求。
- 鉴权中间件能挡住大部分 API，但首装白名单、健康检查、静态资源和 query token 仍是需要收紧的边界。

建议：

- 将 CORS 限制为 WebView2 注入的固定 origin 或关闭跨任意来源。
- 删除 query string token，SSE 如需 token 可改为短期一次性握手 token。
- 首次初始化 `setup-admin` 增加本机 nonce、窗口内一次性 token 或仅允许 WebView2 宿主触发。

#### A3. 会话 token 生成不宜继续使用 `Guid.NewGuid()`

证据：

```text
Acme.Product/src/Acme.Product.Application/Services/AuthService.cs:307-310
private static string GenerateToken()
{
    return Guid.NewGuid().ToString("N");
}
```

风险判断：

- `Guid.NewGuid()` 对普通 ID 足够，但 auth token 更推荐使用 `RandomNumberGenerator.GetBytes` 产生 256-bit 以上随机 token，并采用 base64url 编码。
- 当前会话保存在内存中，应用重启会失效；这对桌面应用可接受，但需要明确口径。

## 3. 安全审计

### 3.1 P0：明文 API Key 被提交到被 Git 跟踪的配置文件

证据：

```text
Acme.Product/src/Acme.Product.Desktop/appsettings.json:7
"ApiKey": "<REDACTED>"

git ls-files 确认该文件被 Git 跟踪。
```

审计中已确认存在 `sk-` 前缀密钥形式。为避免二次泄漏，本报告不复述密钥内容。

影响：

- 如果仓库曾推送到远端或共享给第三方，该密钥应视为已经泄漏。
- 即使只在本地，也会被打包、复制、日志或截图误带出。

建议立即执行：

1. 在对应服务商后台轮换/吊销该 API Key。
2. 将 `appsettings.json` 中密钥改为空字符串或占位符。
3. 使用环境变量、本机用户配置或受保护的本地 secret store 注入。
4. 对 Git 历史做 secret 扫描；若密钥进入远端历史，按泄漏流程处理。
5. 加入 pre-commit 或 CI secret scanning，至少覆盖 `sk-*`、`ghp_*`、云厂商 key、JWT/private key。

### 3.2 AI 模型配置会以明文 JSON 落盘

证据：

```text
Acme.Product/src/Acme.Product.Infrastructure/AI/AiConfigStore.cs:288-294
File.WriteAllText(_modelsFilePath, json);

Acme.Product/src/Acme.Product.Infrastructure/AI/AiConfigStore.cs:301-310
默认模型会从 fallback.ApiKey 初始化 ApiKey
```

影响：

- 即使移除了 `appsettings.json` 中的 key，运行后 `ai_models.json` 仍可能明文保存 key。

建议：

- Windows 桌面端可用 DPAPI / Windows Credential Manager 保护本机密钥。
- UI 列表继续只返回 `hasApiKey`，但落盘时应加密或拆分存储。
- 增加“清除密钥”和“导出诊断时自动脱敏”测试。

### 3.3 权限边界存在但覆盖不均

正向点：

- `AuthMiddleware` 对大部分 API 做 token 校验。
- `UserEndpoints` 已通过 `CurrentUser` 判断 Admin。
- 密码使用 BCrypt work factor 12。

需收紧：

- 工程、设置、PLC、相机、AI 模型测试等端点大多是“认证即允许”，缺少更细角色授权。
- `setup-admin` 白名单在首装阶段需要更明确的本机交互保护。
- query token 容易进入日志、浏览器历史、代理或错误报告。

## 6. 代码质量与运行时风险

### 6.1 同步等待与阻塞点

扫描发现值得关注的同步等待：

```text
Program.cs:163                      configService.LoadAsync().Result
InspectionRuntimeCoordinator.cs     _stateLock.Wait()
ConnectionPoolManager.cs            _gate.Wait()
OnnxPatchEmbeddingExtractor.cs      gate.Wait()
PlcCommunicationOperatorBase.cs     _heartbeatTask?.Wait(...)
SerialCommunicationOperator.cs      Thread.Sleep(100)
ForEachOperator.cs                  results.Select(r => r.Result)
```

判断：

- 桌面启动路径中的 `.Result` 容易在未来引入 UI / host 启动死锁。
- `SemaphoreSlim.Wait()` 在同步方法中可接受，但需要确认没有跨 await 持锁。
- PLC / 串口硬件路径中的 sleep 和 wait 应尽量转为带 cancellation token 的 async wait。

建议：

- 启动初始化改成 async flow，不在 `Program` 中 `.Result`。
- 运行时协调器保留同步锁可以，但应做专门并发压测。
- 硬件通信路径统一超时、取消和重试策略，避免设备无响应时拖死流程。

### 6.2 空 catch 和弱日志

风险样例：

```text
MindVisionCamera.cs:274,280,283,454,467,493,506
GpuAvailabilityChecker.cs:280,318,348
AiApiClient.cs:609,797 捕获 JsonException 后静默忽略
OperatorService.cs:468 捕获 Exception 后静默
```

判断：

- 相机 SDK 和 GPU 探测路径确实需要容错。
- 但空 catch 会让“设备枚举失败、驱动加载失败、硬件能力误判”变成无证据的降级。

建议：

- 所有硬件/AI 能力探测 catch 至少打 Debug/Trace，并返回结构化诊断字段。
- UI 的设备诊断页应能展示“为什么不可用”，而不是只显示空列表。

## 8. 工具链与依赖风险

### 8.1 SDK 漂移

证据：

```text
global.json:
version = 9.0.301
rollForward = latestMajor

本机 dotnet --info:
SDK = 10.0.101
```

影响：

- 本地审计用的是 .NET 10 SDK/MSBuild 18。
- CI 通过 `actions/setup-dotnet` + `global.json` 可能安装并使用 9.0.301。
- 同一 net8 项目在不同 SDK 下 warning、analyzer、NuGet restore 行为可能不一致。

建议：

- 如果目标是稳定复现，改为 `rollForward: latestFeature` 或安装固定 9.0.301。
- 如果决定升级到 SDK 10，显式更新 global.json 并跑全量 CI。

### 8.2 Microsoft.Extensions 版本混用

观察：

- 主项目 net8，但部分包使用 `Microsoft.Extensions.* 10.0.0`。
- OperatorLibrary 使用 `Microsoft.Extensions.* 9.0.0`。
- EF Core、AspNetCore TestHost 等仍有 8.0.x。

判断：

- 这不一定立即坏，但会增加运行时绑定和 CI/本机差异。
- 对 NuGet 算子库尤其需要谨慎，因为消费者项目可能是 net8。

建议：

- 对 net8 发布线优先统一到 8.x 或明确兼容策略。
- 升级 9/10 应以“全仓一轮依赖升级 + 全量测试 + 发布说明”为单位。
