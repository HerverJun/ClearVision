已对照实现修复 STATE-01 至 STATE-09，并补充期望行为回归。以下原始审计内容保留为基线证据，其中的行号、缺陷探针断言和“未修改产品”描述对应修复前版本。

### 修复取舍

- 不放宽 Plan Hash、资源、参数、路由、Apply 或部署门禁；没有证据支持修改线程同步模型。
- 同会话重复 HTTP Build 创建明确拒绝为 409，不新增按请求内容猜测同一操作的自动复用。已有 mutation receipt 仍在运行检查之前处理同一 mutation 的幂等重放；HTTP 创建级自动返回原 Run 属于后续增强。
- 本次补齐现有生命周期恢复集合，并用后端源码状态覆盖回归约束它；未引入跨语言代码生成体系。未知生命周期保持保守阻断，但不把真实 revision 清零。

## STATE-01: 新 Plan 继承旧 Build 只读状态

**触发**：同一会话中完成或失败一次 Build，然后提出新需求生成新 Plan；新 Plan 仍有需要回答的问题。

**已复现**：真实端点先持久化成功 Build，再创建并完成新 Plan。新快照 `LifecycleState=plan_blocked` 且有新 `PlanId`，但 `BuildRunId` 仍为上一轮的 `ar_d521ed869cc048d0929e87e3b6994aad`，`SubmittedBuildFingerprint` 也保留旧值。前端得到 `readOnly=true`，保存直接返回 `{ skipped: true, readOnly: true }`。内置浏览器中，算法问题的三个选项、“其他/补充说明”和两个构建模式按钮全部 disabled。

**根因**：

- `aiPanelAgentWorkspace.js:780` 仅判断任意 BuildRunId/SubmittedBuildFingerprint 是否存在，没有比对其所属 Plan。
- `agentWorkspaceState.js:510` 的 `PLAN_RECEIVED` 和 `:543` 的 `PLAN_CLEARED` 都保留 `run.build` 和 `persistence`。
- `AgentRunEndpoints.cs:234` 创建新 Plan 时没有清理旧 Build 关联。
- `ConversationalFlowService.cs:1879` 只在更新明确提供 Build 字段时修改它们，null 表示保留。
- `aiPanelPlanPresentation.js:156`、`:262` 及 `aiPanelClarificationPresentation.js:243` 将该标记投影为实际控件禁用。

**修复方向**：将 Build 关联绑定到 Plan 身份/修订，而不是整个会话。新 Plan 的正式转移应由后端原子清理旧 Build 权限标记，前端同步切换；历史 Build 可保留在历史记录中。

**必补回归**：成功/失败/取消 Build -> 同会话新 Plan -> 回答问题 -> 保存 -> 再次 Build，至少覆盖一次恢复历史后重复操作。

## STATE-02: 正常成功快照被误判为损坏

**触发**：恢复成功生成过流程的历史会话；或在 Plan 运行时刷新/恢复。

**已复现**：真实成功投影产生 `build_completed`。`normalizeWorkspaceSnapshotForRestore` 将其判断为 `invalid_lifecycle`，输出 `trusted=false`、`revision=0`、空 BuildRunId。`planning` 也被同样拒绝。浏览器恢复成功快照后得到 revision 0 和空 Build 记录。

**根因**：

- `VisionAgentBuildTerminalProjector.cs:154` 写入 `build_completed`。
- `AgentRunEndpoints.cs:240` 写入 `planning`。
- `aiPanelSnapshotRecovery.js:2` 的白名单只有 `plan_running`、`build`、`building` 等值，没有上述两个实际生产值。
- `aiPanelSessionHistory.js:465` 因 `trusted=false` 清空 `flow`、`buildResult`、`applyGate` 和工具证据，标记 `degraded_restore`。
- `aiPanelSessionHistory.js:566` 将工作台版本号重置为 0，后续请求可能继续撞到后端版本冲突。

`recovery_conflict` 也不在白名单，但它需要专门的恢复错误展示，不能简单当成健康状态放行。本项的确定误杀证据是正常的 `build_completed` 和 `planning`。

**修复方向**：由共享合同导出生命周期集合，保留正常运行/终态与真正损坏快照的区别；未知状态可以禁用危险操作，但不应丢弃可用于恢复的真实版本号和运行标识。

**必补回归**：后端每个正式生命周期快照直接交给前端恢复函数；成功 Build 的真实会话必须恢复同一流程、运行和版本号。

## STATE-03: 一次保存失败会反复挡住后续操作

**触发**：修改 Plan 后自动保存遇到一次瞬时网络/存储失败，随后网络或磁盘恢复。

**已复现**：一次保存失败后，把服务恢复正常，依次执行 before_build、history_switch、new_conversation。三个边界全部返回 false，网络请求总数仍为 1，dirty 始终为 true。

**根因**：`aiPanelAgentWorkspace.js:945` 的 `_flushWorkspaceSnapshotBeforeBoundary(reason)` 只等待已失败的 `workspaceSnapshotSaveQueue`，catch 后比较 generation；不会调用已有的队列保存方法再次提交。`reason` 没有用于重试。构建、历史切换、新建会话及宿主关闭检查均复用这个边界。

用户可能通过再次修改任意字段触发新保存来绕过，但界面没有解释这一要求，也没有明确的“重试保存”入口。因此不是线程死锁，却会表现为“怎么重试都无法离开/构建”。

**修复方向**：等待当前保存结束后，对失败且仍 dirty 的同一工作台身份重新提交最新快照，使用明确的 mutation 身份及版本冲突处理；同时提供可见的保存重试操作。

**必补回归**：一次 503 -> 服务恢复 -> 原样点击构建/切换/新建，无需再编辑字段即可重新保存并继续。

## STATE-04: 历史运行恢复没有重新连接事件流

**触发**：Build 尚在运行时恢复该会话；对 Plan 而言还需先修复 STATE-02 才能完整进入恢复分支。

**已复现**：回放响应的 summary.status 为 running，包含 run.started；前端仅处理这一批事件，订阅启动次数为 0。恢复后的 activeRunId 存在，但后续后端事件不会再到达。

**根因**：`aiPanelSessionHistory.js:658` 调用 `_replayAgentRunPublicEventsById`；`aiPanelAgentRun.js:1317` 只 GET 一次并遍历历史事件，未根据 summary/terminal 状态启动 `_startAgentRunEventSource` 或轮询，也没有为恢复中的 Plan 建立正常的完成处理上下文。

**修复方向**：恢复时先回放并核对终态；运行中的任务从已处理 sequence 继续订阅，重新建立 busy/cancel/终态投影处理；终态历史无需订阅。

**必补回归**：恢复时后端仍 running，恢复后再发布 terminal；界面必须自动更新为终态，而不是重新进入历史才能看到。

## STATE-05: 取消命中了已完成的历史 Plan

**触发**：恢复包含已完成 Plan 的会话，再启动 Build，随后点击取消。

**已复现**：在历史 Plan 完成、当前 Build 为 current-build-run 时，取消请求实际发往 `/ai/agent-runs/completed-plan-run/cancel`；当前 Build 未被取消，isCancellingGenerate 已置为 true。

**根因**：

- 历史回放将 PlanRunId 放入 `activePlanRunId`。
- `aiPanelAgentWorkspace.js:2526` 的 `_resolveActivePlanRun` 在没有 `activePlanRunCompletion` 时立即返回；历史恢复明确没有该 completion，因而旧 ID 没被清理。
- `aiPanelGenerateRequest.js:689` 无条件优先取消 activePlanRunId，没有检查 Plan 的终态以及当前实际执行种类。
- 取消已完成任务不会产生用来结束当前 Build 等待的有效新终态。

**修复方向**：拆分“历史记录中的 RunId”和“当前可取消的 RunId”，按运行种类、状态和会话身份选择取消目标。恢复终态不应依赖在线创建时的 Promise 才能清理活动状态。

**必补回归**：恢复 completed Plan -> 新 Build -> 取消，请求必须命中 Build，并最终释放取消和生成忙碌状态。

## STATE-06: 同一会话的两个 Build 可同时执行

**触发**：第一个 Build 尚未结束，另一个请求使用当前快照 revision 再次提交 BuildFromPlan。历史恢复未恢复完整 busy/订阅状态会提高这一场景出现的可能性。

**已复现**：两个 POST 均返回 HTTP 200；实际构建处理器进入两次，两个 Run summary 同时为 running；会话唯一 BuildRunId 已切换成第二个。运行 ID 和完整响应保存在 backend-observations.json 的 overlapping-builds 条目中。

**根因**：`AgentRunEndpoints.cs:390` 的 BuildFromPlan 分支调用 `PrepareBuildAssociation`；`VisionAgentBuildRunService.cs:71` 直接 `TryUpdateWorkspaceSnapshot` 写入新关联，只做 revision 条件更新。相反，普通 Generate 分支在 `AgentRunEndpoints.cs:446` 调用带运行检查的 `TryBeginAgentRun`。版本号防止同时覆盖同一旧 revision，但不等于“同会话没有运行中任务”。

**影响**：重复执行、运行关联覆盖、旧终态与新工作台发生投影冲突。不能仅靠按钮 disabled 保证后端互斥。

**修复方向**：将“当前无冲突运行 + revision 匹配 + Build 关联保存”放在同一次后端事务/锁内；同一操作的网络重试应幂等返回原 Run，不应新建第二个运行。

**必补回归**：第一个 Build 卡在受控执行点，第二个使用最新 revision 提交，必须被明确拒绝或幂等复用，执行器进入次数仍为 1。

## STATE-07: 创建响应晚到后污染新会话

**触发**：Plan/Build 的创建响应延迟，用户先取消规划、切换会话，或面板被销毁。

**已复现**：

- Plan：把当前会话切到 new-session、revision 99，再返回旧创建响应。方法虽然报“Plan Run 已过期”，但已经把会话改回旧值、revision 改为 8。
- Build：面板 `_disposed=true` 后返回旧创建响应，仍改回旧会话/版本，并尝试为 late-build-run 启动事件订阅。

**根因**：`aiPanelAgentWorkspace.js:2344` 在 `_isActivePlanRequest` 前采用 canonicalSessionId 和 workspaceSnapshot；`aiPanelAgentRun.js:546` 在 await 之后完全没有 request/session/navigationEpoch/disposed 校验。

**修复方向**：发送前捕获请求和会话导航身份；响应返回后先验证身份，再允许修改会话、版本、活动 Run 或订阅。迟到但后端已创建的运行需要与显式取消意图协调。

**必补回归**：延迟 create 响应 + 取消/新会话/dispose，响应到达后新会话身份、内容、版本和订阅均保持正确。

## STATE-08: 草稿模式恢复时被切回严格模式

**触发**：历史 Plan 保存为 draft，恢复后 Readiness 已过期，需要重新校验；或在 Plan 身份首次进入本地映射时激活。

**已复现**：Plan 自身 requirementMode 为 draft，工作台也先恢复 draft；调用正常校验链入口使用的 `_activatePlanIdentity` 后，effectiveMode 变成 strict。浏览器显示“确认完整后构建”，资源重新标记为“阻止构建”。

**根因**：`aiPanelAgentWorkspace.js:1017` 对不在内存 `planRequirementModes` Map 中的身份固定写入 strict，再覆盖 `this.requirementMode`。`aiPanelSessionHistory.js:649` 对过期预览触发校验，而恢复过程未先填充该 Map。

**修复方向**：新 Plan 的默认值与恢复已有 Plan 的权威模式应采用不同规则；恢复时把持久化模式绑定到该 Plan 身份，重新校验不能偷偷改变模式。

**必补回归**：保存 draft -> 重建面板进程/清空内存 Map -> 恢复 -> 预览重新请求，request.requirementMode 必须仍为 draft。

## STATE-09: 超时提示“请重试”，但不存在校验重试操作

**触发**：Readiness 请求失败或超过默认 15 秒。

**已复现**：实际新版 AiPanel 进入 timeout 后，浏览器查询包含“重试/校验”文字的全部按钮，只有两处“构建条件校验超时，请重试”，而它们都 disabled；没有可点击的重试校验入口。

**根因**：

- `aiPanelAgentWorkspace.js:3434` 对 failed/timeout 返回 canStart=false，`:1484` 据此禁用 Build 主按钮。
- 旧 `_renderPlanWorkspace` 在 `aiPanelAgentWorkspace.js:5404` 和 `:5552` 提供并绑定了重试校验按钮。
- `aiPanelPlanPresentation.js:381` 的实际新版 renderer 覆盖旧实现；其操作区 `:408` 没有重试入口，`:426` 安装时无条件替换旧 renderer。

重新改变模式或答案可以间接触发校验，但它要求用户修改本来正确的业务状态。无问题可答时，“重试规划”也不是同一操作，会无端重跑模型规划。

**修复方向**：新版 Plan 操作区根据 Readiness 状态显示并绑定显式重试，复用当前 plan/hash/answers/mode，成功前仍保留 Build 阻断。

**必补回归**：生产 renderer 下，Readiness timeout -> 点击可用重试 -> 请求成功 -> Build 恢复可操作；不能只测旧 mixin 的按钮。

本轮没有证据支持删除 Plan Hash、业务路由语义、资源/参数完整性或部署准入校验。`ApplyGateResolver.cs` 已把 CanvasApplyReady、RuntimeDraftReady 和 DeploymentReady 区分开；`aiPanelPendingParameters.js` 也明确把 AI 复核作为可选步骤。它们不应为了绕开状态错误而被统一放松。
