# AI 功能代码级与项目级复查报告（2026-09-02）

## 1. 结论摘要

本轮对此前发现的 AI 问题进行了运行记录、代码实现、项目契约和最小可执行探针四层复查。最终确认 **10 项真实问题**，其中 `P1` 8 项、`P2` 2 项、`P0` 0 项；另有 6 组旧判断被收窄、降级或排除。

截图中的构建失败不是编译失败，也不是因为仓库没有 Canny 算子。准确原因是：同一需求的模型语义和计划意图均为 `surface_defect`，规则抽取器却把包含“面积”的需求生成成 `task_type=geometry_measurement`，并错误标记为 `explicit_user_text`；该答案覆盖语义后，构建按 `measurement` 路由合同检查一个 `Thresholding + BlobAnalysis` 流程，因没有测量处理算子而触发 `route_missing_task_processor`，随后准入层对外只显示首条通用诊断 `route_semantics_not_satisfied`。

同时，隔离工件证明该草稿即使绕过本次路由阻断，也没有实现用户要求：它使用 `Thresholding` 而不是已存在的 `EdgeDetection/Canny`，把 `BlobCount` 同时连接到 `ResultJudgment.Value` 和 `ResultJudgment.Confidence`，且没有任何面积输出连线。

本轮只新增本报告，没有修改产品代码。审计开始前已存在的两处用户修改保持原样：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentRunRecoveryReconciliationService.cs`
- `ClearVision.Product/tests/ClearVision.Product.Tests/AI/BuildFromPlanEntryParityTests.cs`

## 5. 问题明细与复现方式

### AI-01：任务识别冲突与来源可信度膨胀（P1）

**结论**：纯规则成熟度按 `TaskSignalTerms` 的插入顺序命中首个类别。“面积”位于几何测量词表，而几何测量位于缺陷词表之前；确认答案抽取器又有另一套优先级，其中正则 `检测…上的…` 在缺陷词之前直接返回 `presence_absence`。所有这些规则推导值最后统一标记为 `explicit_user_text`。答案验证没有与语义抽取结果比对，Overlay 会直接覆盖语义值，Planner 修复又保留基线确认答案。

**触发与影响**：同时包含缺陷和面积的请求可被改写成测量任务；“检测产品上的裂纹”则表现为成熟度仍是缺陷任务、确认答案却是有无任务。下游可能构建错误路线或像截图一样被错误合同阻断。

**代码证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentRequirementMaturityGate.cs:57-94`：几何词表包含“面积”，并排在缺陷词表之前。
- 同文件 `:930-943`：命中首个词表后立即返回。
- 同文件 `:483-511`、`:567-613`：确认答案抽取及另一套任务优先级；`检测…上的…` 先于缺陷判断。
- 同文件 `:653-672`：所有规则生成答案写成 `explicit_user_text`。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentPlanRequirementOverlay.cs:18-22`：答案无冲突检查地覆盖语义字段。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentPlanPlannerService.cs:420-489`：修复后的 Plan 保留基线语义和确认答案。

**最小复现**：分别调用 `Evaluate` 和 `ExtractExplicitPlanAnswers`：

- 划痕面积样本：纯规则 `geometry_measurement`；结构化语义 `surface_defect`；抽取答案 `geometry_measurement / explicit_user_text`。
- `检测产品上的裂纹`：成熟度 `surface_or_pose_defect`；抽取答案 `presence_absence / explicit_user_text`。
- 将 `surface_defect` 语义与 `geometry_measurement` 确认答案交给 `VisionAgentPlanAnswerValidator` 和 Overlay：`ConflictedFields` 为空，最终 `Values.task_type=geometry_measurement`。

### AI-02：任务类型体系不闭合（P1）

**结论**：核心常量定义了 `code_recognition`、`barcode_qr`、`plc_output`，默认 Plan 也生成扫码与 PLC 路线；但准入注册表的支持集合不包含这些值。相反，注册表独有 `object_detection`。UI/Plan 兜底选项还把 `general_inspection`、`custom_task` 当作可解除字段的值，但注册表同样不支持。PLC 又被优先识别成“任务类型”而不是输出通道，其默认路线包含目录中不存在的 `InspectionOperator`，后续会被静默删除。

**触发与影响**：扫码、二维码或 PLC 输出需求，以及用户选择“通用视觉检查/自定义视觉任务”时，会形成表面上已解决、实际无法通过路由准入的 Plan。包含 PLC 的复合检测需求还会遮蔽真正的主检测任务。

**代码证据**：

- `ClearVision.Product/src/ClearVision.Product.Core/DTOs/VisionAgentPlanContracts.cs:12-26`：规范任务常量。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/VisionTaskRouteContractRegistry.cs:20-40`、`:91-104`：实际支持集合和归一化映射。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentPlanFieldPolicy.cs:21-30`、`:540-555`、`:667-692`：`task_type` 允许自由文本，两个 UI 值会被当作 `resolve_field`。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentOrchestrator.cs:1002-1004`、`:1071-1077`、`:1103-1109`：PLC 抢占场景，扫码路线和含虚构算子的 PLC 路线。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/PlanSelectionResolver.cs:272-304`：非法算子从路线中移除。

**最小复现**：`VisionTaskRouteContractRegistry.Assess` 对上述五个正式/可选值均返回 `Supported=false`，对 `object_detection` 返回 `Supported=true`；`OperatorPipelineSelector` 会把 `InspectionOperator` 放入 `InvalidOperators` 并从步骤中删除。本轮探针均已复现。

### AI-03：Plan 缺少需求—方案忠实度校验（P1）

**结论**：本次 Plan 明确写出“目录没有专用 Canny 算子”，并使用 `Thresholding` 近似；仓库实际上公开了 `EdgeDetection`，其默认方法就是 `Canny`。Planner 的路线修复只检查候选算子是否属于目录白名单，没有检查用户点名的 Canny 是否保留，也没有检查“输出划痕面积”是否在结果数据流中实现。

**触发与影响**：模型出现事实错误或用“近似路线”替换明确要求时，只要所有算子名合法，Plan 合同就可能接受。若 AI-01 被修正为表面缺陷，本次 `Thresholding + BlobAnalysis` 甚至可能通过当前表面缺陷路线合同，形成静默需求偏离。

**代码与运行证据**：

- Run `ar_plan_ee6fb01995ad287dd3a390f9d949c8aa`：风险文本声称没有专用 Canny，路线实际使用 `Thresholding`。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/CannyEdgeOperator.cs:17-62`：公开边缘检测算子、`Method=Canny` 默认值和实际 `OperatorType.EdgeDetection`。
- `ClearVision.Product/src/ClearVision.Product.Core/Enums/OperatorExposureCatalog.cs:28-38`：`EdgeDetection` 为 `PackagePublic`。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentPlanPlannerService.cs:795-833`：路线修复仅做目录成员过滤。

**最小复现**：目录探针可取得 `EdgeDetection` 合同，且 `Method.DefaultValue=Canny`；与上述 Run 的计划声明直接矛盾。

### AI-04：自动连线只做类型兼容，不做业务语义兼容（P1）

**结论**：`WorkflowDraftBuilder` 先按端口名偏好查找，找不到后选最近上游的第一个类型兼容输出；任一侧为 `Any` 即判兼容。由此会稳定生成以下错误或可疑连线：

- `SurfaceDefectDetection.Image -> BlobAnalysis.Image`，而不是更符合缺陷连通域分析的 `DefectMask`。
- `CodeRecognition.Image -> ResultJudgment.Value`，并可能把 `CodeCount` 当作 `Confidence`。
- `CircleMeasurement/LineMeasurement/ContourMeasurement/AngleMeasurement.Image -> ResultJudgment.Value`，忽略 `Radius/Length/Area/Angle`。
- 截图工件中 `BlobCount` 同时进入 `Value` 和 `Confidence`。

**影响**：流程可通过端口类型检查和 metadata DryRun，但判定读取的是图像、计数或其他错误语义，属于“结构合法、业务错误”的高风险缺陷。

**代码证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/WorkflowDraftBuilder.cs:545-706`：连线偏好和首个兼容端口回退。
- 同文件 `:595-604`：Blob 的源端口顺序为 `Image`、`DefectMask`、`Mask`。
- 同文件 `:615-618`：`ResultJudgment.Value` 偏好表遗漏扫码文本和多种测量值。
- `ClearVision.Product/src/ClearVision.Product.Core/Enums/PortDataTypeCompatibility.cs:5-9`：`Any` 与所有类型兼容。
- 算子真实端口：`ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/SurfaceDefectDetectionOperator.cs:22-31`、`ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/CodeRecognitionOperator.cs:26-30`、`ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/CircleMeasurementOperator.cs:25-39`、`ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/LineMeasurementOperator.cs:19-25`、`ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/ContourMeasurementOperator.cs:17-21`、`ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/AngleMeasurementOperator.cs:18-26`。

**最小复现**：使用 `WorkflowDraftBuilder.DraftAsync` 构造 `ImageAcquisition -> 目标算子 -> ResultJudgment -> ResultOutput`。本轮探针逐一得到扫码 `Image` 以及四种测量算子的 `Image` 接入 `Value`；表面缺陷接 Blob 时得到 `Image` 而非 `DefectMask`。

### AI-05：结果判定默认值与任务极性不一致（P1）

**结论**：除少数特殊任务外，参数映射默认写入 `Condition=GreaterOrEqual`、`ExpectValue=1`。`ResultJudgmentOperator` 的数值比较不会把 Boolean 转为数值，因此 `true >= 1` 为 false；缺陷计数为 1 时则得到 true，即“发现缺陷”为 OK。线序特殊分支又把布尔 `IsMatch` 与字符串“线序待确认”比较，仍为 false。

**触发与影响**：模板匹配、线序、缺陷计数等自动生成路线可能产生稳定的假 NG 或反向 OK。若进入实际质检链路，可能造成错误放行或误剔除。

**代码证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/ParameterMappingService.cs:317-345`：通用默认值及线序特殊值。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/ResultJudgmentOperator.cs:171-224`、`:238-266`：比较和数值解析行为。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/DetectionSequenceJudgeOperator.cs:45-57`：线序主结果是 Boolean `IsMatch`。

**最小复现**：本轮直接执行算子得到 `true >= 1 -> IsOk=false`、`1 >= 1 -> IsOk=true`、`true Equal 线序待确认 -> IsOk=false`。

### AI-06：业务结果在默认输出链中丢失（P1）

**结论**：`ResultOutput` 的普通自动连线只连接判定结果和图像。扫码 `Text`、模板 `Position/Angle/Scale`、测量标量、Blob 特征等均没有对应连线。Blob 的面积位于 `BlobFeatures` 集合内，不是独立 `Area` 端口；且截图工件中 `OutputDetailedFeatures=false`，永久算子测试证明该设置会固定返回空特征列表。

**触发与影响**：即使路线通过构建，用户要求的码值、位姿或面积也无法作为默认结果输出。截图中“输出：划痕面积”只是展示承诺，实际数据流没有面积。

**代码证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/WorkflowDraftBuilder.cs:620-624`：默认只连接 `Result` 和 `Image`。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/CodeRecognitionOperator.cs:26-30`：扫码文本端口。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/TemplateMatchOperator.cs:39-54`：模板位姿和分数端口。
- `ClearVision.Product/tests/ClearVision.Product.Tests/Operators/BlobDetectionOperatorTests.cs:116-157`、`:160-175`：面积提取路径以及禁用详细特征时返回空列表的永久测试。

**最小复现**：本轮 CodeRecognition 草稿仅得到 `ResultJudgment.JudgmentResult -> ResultOutput.Result`，未出现 `CodeRecognition.Text -> ResultOutput.*`；截图隔离工件的面积连线数为 0。

### AI-07：路由合同可误放行不满足任务目标的图（P1）

**结论**：路由合同主要检查图像源、处理器类型、必填输入和可达路径，不检查特定任务必须输出哪些业务字段。多个处理器本身被认定为终点，`template_matching` 的处理器集合还直接包含 `BlobAnalysis`。

**触发与影响**：只含 `ImageAcquisition -> BlobAnalysis` 的图即可通过 `template_matching` 路由合同，无需模板、位姿或 `ResultOutput`。这会掩盖 AI-04、AI-05、AI-06 的错误，让语义错误的工件获得 `RouteSemanticsSatisfied=true`。

**代码与测试证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/VisionTaskRouteContractRegistry.cs:31-40`：模板处理器包含 Blob。
- 同文件 `:133-225`：只验证处理器存在和路径可达。
- 同文件 `:361-373`：处理器自身可作为终点。
- `ClearVision.Product/tests/ClearVision.Product.Tests/AI/VisionAgentBuildOrchestrator/VisionAgentBuildOrchestratorTests.cs:288-309`：永久测试明确把 Blob-based robot guidance 视为应通过。

**最小复现**：本轮对 `ImageAcquisition -> BlobAnalysis` 图调用 `Assess("template_matching", graph)`，返回 `Supported=true`、`Satisfied=true`。

### AI-08：图像来源答案没有进入采集参数（P1）

**结论**：规范字段 `image_source` 可保存 `file_sample`、`station_camera` 等值，但 `ParameterMappingService` 生成 `ImageAcquisition.SourceType` 时没有读取该字段，而是无条件返回 `Camera`。算子自身的合同默认值其实是 `File`。

**触发与影响**：用户确认离线样张后，草稿仍要求 `CameraId`，造成错误资源阻断并与界面选择不一致。

**代码证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/ParameterMappingService.cs:255-270`：`SourceType` 固定为 `Camera`。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Operators/ImageAcquisitionOperator.cs:35-54`：算子合同按 SourceType 控制资源，默认值为 `File`。

**最小复现**：在 `BuildPlanLoad.RequirementAnswers` 和 `EffectiveRequirement.Values` 同时写入 `image_source=file_sample`，映射结果仍为 `ImageAcquisition.SourceType=Camera`。本轮探针已复现。

### AI-09：重复圆测量节点可生成相同 TempId（P2）

**结论**：圆测量 TempId 由整个算子序列中的绝对序号决定：序号不大于 2 为 `op_circle_a`，否则为 `op_circle_b`。当两次圆测量前已有两个或更多步骤时，两者都会得到 `op_circle_b`。

**触发与影响**：Planner 在双圆测量前加入 Filtering/ROI 等预处理即可触发。后续路由合同会发现重复节点身份并阻断构建，属于确定性的可用性问题；默认无预处理的双圆路线暂不触发。

**代码证据**：`ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/Build/OperatorPipelineSelector.cs:63-74`、`:173-192`。

**最小复现**：选择 `ImageAcquisition, Filtering, CircleMeasurement, CircleMeasurement`，本轮探针得到两个 `op_circle_b`。

### AI-10：公开诊断遮蔽真正原因（P2）

**结论**：准入层先加入 `route_semantics_not_satisfied`，再追加具体路由原因；应用层只取 `Diagnostics.FirstOrDefault()` 构造失败码。因此界面主错误稳定显示通用码，而更可操作的 `route_missing_task_processor` 只留在深层工件/事件字段中。

**影响**：用户看到“算子、端口、参数、连线或路由可能有问题”的宽泛提示，无法判断本次实际是任务类型与路线处理器不一致，显著增加排障成本。

**代码与运行证据**：

- `ClearVision.Product/src/ClearVision.Product.Infrastructure/Services/WorkflowArtifactAdmissionGate.cs:989-1031`：通用诊断先于具体路由诊断。
- `ClearVision.Product/src/ClearVision.Product.Infrastructure/AI/Agent/VisionAgentBuildApplicationService.cs:879-891`：只公开第一条诊断。
- 隔离工件和 Run `ar_7ca7e2342ed14888ab1a5c261499fd53`：两条诊断及截图展示顺序与代码一致。

**最小复现**：提交任一 `RouteSemanticsSatisfied=false` 且注册表同时返回具体原因的 AI 工件，比较 Admission Report 与最终 `FailureSummary.Code`。
