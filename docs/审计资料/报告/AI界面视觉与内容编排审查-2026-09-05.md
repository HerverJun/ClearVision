# AI 界面视觉与内容编排审查

## 结论

当前 AI 已具备工程工作台的主要功能骨架，但页面仍以展示系统状态和工程字段为主，用户真正需要做的判断、补充和确认没有得到相应的视觉优先级。最值得投入的是内容可信度、任务推进顺序、资源与配置表单、变更可读性，然后才是视觉细节统一。

现有中性深浅主题和克制的红色品牌点缀可以延续。建议把 AI 页完善成面向视觉工程师的任务工作台：首屏回答“正在处理什么、目前缺什么、现在做什么”，细节围绕这三个问题展开。

本轮仅完成审查、证据和改进计划，未修改生产功能。

## 审查范围与证据

检查默认生产 `wwwroot` / `AiPanel`，覆盖初始输入、规划展示、方案澄清、资源补齐、构建结果、验证失败、应用预览、紧凑会话和 AI 模型设置。未将 FrontendV2 的并行实现作为当前默认体验。

证据包括当前代码、内置浏览器 1366×768 / 1024×768 深浅主题场景，以及仓库已有 1920×1080 WebView2 资源阻断截图。本轮浏览器场景复用仓库测试数据并隔离外部 I/O，不代表真实 LLM、设备或生产部署验收。

截图、DOM 测量和可复现夹具见 [审查证据](../../../quality/evidence/ai-visual-content-review-20260905/README.md)。已修复的会话状态和恢复问题依据仓库 2026-09-05 修复记录处理，不重新列为未修复项；本次也未重复运行它们的全部回归。

## 问题与建议

### V01 · P1 · 性能概览展示固定数值，损害数据可信度

AI 设置页显示 450ms、Token 14.2K/50K、RPM 45/100，源码直接写死这些值和图形比例。夹具模型尚未测试，配置详情显示 `untested`，性能概览仍显示这些数字。页面底部“健康状态以测试连接为准”的说明不能消除指标本身的误导。

位置：`wwwroot/src/features/settings/tabs/aiTab.js:1295`，固定数值在 1304、1314、1322 行。

建议：优先移除无来源的指标；已有 `lastTestStatus`、`lastTestAt`、`lastTestLatencyMs` 应组成紧凑的连接测试结果。无采集数据就显示“未测试”或“暂无数据”。只有存在明确模型范围、时间窗口和采集来源时才展示用量和速率。

验收：切换两个测试状态不同的模型，状态、耗时和时间分别对应所选模型；未测试、失败或无数据时不得出现成功数字及绿色占比图。

### V02 · P2 · 阻断计数的含义与来源不一致

2 个澄清问题和 1 个模型资源的场景，任务栏显示“2 项阻断”，主按钮显示“还需补充 3 项信息”。前者只数 `clarificationQueue` 中的问题，后者包含资源与权威缺项分区。资源已经去重，但不同位置对“还剩多少”的表达仍有歧义。

位置：`wwwroot/src/features/ai/aiPanelShellPresentation.js:104`；`aiPanelAgentWorkspace.js:3386`、`:3558`。

建议：消费同一份权威缺项分区。任务栏表达为“待处理 3 项”，明细为“决策 2 · 资源 1”；严格/草稿模式分别明确“构建前必需”和“运行前必需”。若局部计数只包含问题，应明确标注“待确认问题 2 项”。

验收：全页总数、列表和按钮解释一致；切换草稿、完成绑定、恢复会话后的分类和数字一致；展示改造不改变实际 Build/Apply/部署判定。

### V03 · P2 · 首屏优先展示说明，真正要做的事被推到下方

1366×768 中，方案区可视高度约 535px，澄清区从页面 y≈837px 开始。用户先看到大块“AI 理解成了什么”和“推荐方案”，第一个问题仍在首屏外。顶部只有禁用的构建按钮提示缺项。1024px 模式另有工作台/会话一层标签，问题更难及时出现。

失败构建也先展示四格统计和流程摘要；首屏“先修复最重要的验证问题”没有直接指出本场景的“输出端口类型不兼容”。现有“前往处理区域”可导航，但动作名称不够具体。

位置：`wwwroot/src/features/ai/aiPanelPlanPresentation.js:399` 的渲染顺序；`aiPanelBuildPresentation.js:1017` 的区域顺序。

建议：阻断状态优先显示当前待处理事项，任务理解缩为紧凑摘要，推荐流程在其后。就绪状态突出方案/变更复核。失败状态显示“问题对象 + 失败原因 + 修复动作”，主入口改为“检查结果输出连接”等具体操作。为被阻断的构建保留禁用判定，同时提供可点击的“补齐 3 项”导航。

验收：1366×768、1024×768 的首屏都可看到第一个待处理问题和至少一个有效操作；定位问题后标题和控件不被固定栏遮挡。

### V04 · P2 · 一项资源展开成审计表，操作距离过长

当前一张模型资源卡约 399px 高，先列资源、影响算子、影响参数、阻断范围、来源、解决位置、原因和 AI 建议，再出现“选择模型文件”。`op_detect.ModelPath` 与 `build_readiness / plan` 默认外露，即使已有“技术详情”折叠区。真实 WebView2 相机资源截图也呈现同类结构。

位置：`wwwroot/src/features/ai/aiPanelResourceBinding.js:182`。

建议：资源行默认只保留名称、所作用的可读算子名、影响范围、当前值和绑定操作。例如“表面缺陷检测模型 · 阻止构建 · 选择模型文件”。原因紧邻操作。来源、canonicalId、内部参数键和多源合并信息进入技术详情。多个资源采用可扫描的任务列表；当前任务展开表单，其余保持紧凑。

验收：单资源默认块建议不超过约 160px；绑定操作无需越过八个元数据字段；仍能查看资源来源、绑定证据和完整技术身份。

### V05 · P2 · 浅色对比度与多层框线削弱可读性

资源字段沿用深色半透明背景，浅色主题实际形成灰底配灰字。标签 10px、值 11px，对比度估算分别为 1.69:1、3.12:1。输入框外层与 textarea 同时显示红色聚焦光晕；方案、澄清、资源与字段叠加边框，构建摘要又采用 12px 圆角容器。应用预览仍使用偏紫的旧弹窗表面，和主工作台的中性背景不同。

位置：`wwwroot/src/shared/styles/ai-panel.css:2662`、`:2690`；`ai-conversation.css:100`；`ai-build.css:29`。

建议：资源字段使用当前主题 surface/text token；常用正文 13–14px，元信息原则上不小于 12px；正文对比度至少 4.5:1。页面主区采用平面布局与分隔线，只给独立交互项和模态框加边框。输入区保留一处清楚的焦点反馈，普通卡片圆角统一到 6–8px。

验收：资源、禁用原因、输入焦点和应用弹窗分别检查深浅主题；对比度与键盘焦点单独验证。不要用“取消全部 outline”解决重复聚焦。

### V06 · P2 · 模型配置七列并排，难以辨认；本地模型入口无内容切换

1366×768 下模型详情被右侧性能概览挤压，首行七个 `flex:1` 字段每个约 75.44px。协议、接口和模型名只能看到片段，中英文标签又没有形成明确概念层级。“本地模型”被画成可点击标签，但本轮点击不切换，代码为无切换标识和逻辑的普通 `div`。

位置：`wwwroot/src/features/settings/tabs/aiTab.js:822`、`:1247`。

建议：配置所选模型采用“基本连接 / 能力与用途 / 高级参数”分组。服务商、协议、API 接口三个概念用明确名称，并根据服务商预置常规值；高级覆盖仍可访问。宽屏默认两列、单字段至少约 220px，窄区单列。用途用“流程生成 / 方案规划 / 评估”替代直接展示 generation/planner/shadow。本地推理服务可通过现有协议管理；本地检测模型应进入其真实资源管理入口，缺少入口时移除伪标签。

验收：常用值无需横向滚动即可辨认；标签具有正确 button/tab 语义；每个看似入口的控件确实有目标；测试连接与保存操作的对象明确。

### V07 · P2 · 开发说明进入用户正文，增加理解负担

已确认的可见文案包括“AI 会沿用现有规划、构建与恢复链路”“不创建第二套队列”“验证状态仅来自既有 BuildResult、Validation Preview 与 Apply Gate”“按钮继续服从现有 Apply Gate”。规划等待渲染器还展示 Router、Plan Run 事件数量和进度真实性的实现说明。

位置：`wwwroot/src/features/ai/aiPanel.js:519`；`aiPanelPlanPresentation.js:321`；`aiPanelBuildPresentation.js:931`、`:959`、`:1053`、`:1104`。

建议：把系统内部约束保留在代码注释、诊断详情和开发文档。用户正文使用可判断的任务事实，如“正在生成方案”“模型文件尚未绑定”“结构检查通过，尚未完成样本验证”“新增 4 个节点，修改 2 个参数”。统一采用“方案、构建、验证、应用到画布”等中文术语。每个阶段默认只保留一条状态和一条下一步。

初始页快捷“缺陷检测”预填了高斯滤波、Canny、Blob 固定路线（`aiPanel.js:575`）。建议换成检测对象、缺陷和输出条件，避免示例在没有图像依据时预先决定算法。

验收：普通视图不出现 Router、BuildResult、ApplyGate 等内部标识；进度不虚构百分比或预计耗时；失败信息给出具体可执行动作。

### V08 · P2 · 应用预览使用内部连线 ID，不利于复核变更

预览中的算子已有可读名称，但连线显示 `op_acq.op_acq_out -> op_roi.op_roi_in`。用户必须把 ID 对回流程后才能判断新增连线是否正确。弹窗仍以逐条技术差异为主，缺少对关键参数影响的优先编排。

位置：`wwwroot/src/features/ai/aiPanelApplyPreview.js:392`、`:477`。

建议：用流程中的算子/端口元数据解析为“图像采集 · 图像 → ROI 管理 · 图像输入”。同名算子追加序号区分。删除、重连、阈值/单位/输出目标变更优先展示；ID 进入可复制的详情。后续可复用真实画布渲染只读变更预览。

验收：名称冲突可区分；未知端口有明确回退；长链路可换行；确认前能够辨认新增、删除和参数前后值。继续验证版本过期、门禁变化与撤销行为。

## 已有能力与后续功能方向

| 已有基础 | 建议加强的用户价值 | 实施边界 |
| --- | --- | --- |
| 方案/构建分区与单主操作 | 根据阶段把当前问题或结果放到最前面 | 保留现有状态与权限来源 |
| 资源身份去重、严格/草稿分区 | 让每个资源可以直接定位、绑定、理解影响 | 不在前端新增放行逻辑 |
| 参数填写、确认、资源选择入口 | 表单紧邻失败原因；成功后明确显示还剩什么 | 使用现有确认与持久化链路 |
| 验证、DryRun、部署预检 | 区分结构检查、元数据预演、真实样本效果 | 未执行真实图像时不展示检测成功结论 |
| 附件处理报告 | 样本缩略图、OK/NG 标注、输入来源及本轮是否实际使用 | 优先复用现有资源/预览能力，需先核对数据合同 |
| Apply Preview 与撤销 | 业务名称、参数前后值和真实画布差异 | 保留 revision、门禁与回滚保护 |
| 历史会话与恢复 | 历史列表显示工程、阶段、更新时间；恢复后突出当前任务 | 不重新实现会话状态机 |
| 模型管理与连接测试 | 当前使用模型、视觉输入能力、真实最近测试结果 | 配置来源、编辑对象和实际激活模型分开表达 |

样本证据是后续最有价值的领域增强：视觉工程师需要看到输入图、检测区域、结果叠加和判定依据。当前 AI 主工作区主要以文本、算子摘要和元数据为核心；这不等于全产品没有预览功能。应接入已有流程预览能力，并分别注明“未运行 / 元数据检查 / 样本实测”，避免为增强视觉效果而制造结果图。

## 目标内容结构

顶部任务条：任务名、工程/草稿归属、当前阶段、准确的待处理数、一个主操作、历史/更多入口。

桌面主区继续采用工作台 + 会话的双区结构。工作台承担决策、配置和证据；会话承担补充条件与解释。会话宽度可调整或收起，避免固定占据大面积而只有少量消息。1024px 下保留区域切换，但任务摘要和问题入口应跨视图可见，减少两层标签占用高度。

| 状态 | 工作台第一内容 | 主操作 | 后续内容 |
| --- | --- | --- | --- |
| 无任务 | 输入 + 样本入口 + 最近任务 | 发送 | 少量业务示例 |
| 规划中 | 当前阶段、已用时/最近更新、必要的取消入口 | 取消 | 已明确的需求摘要；技术事件折叠 |
| 待澄清/缺资源 | 第一个阻断及其表单 | 确认答案 / 绑定资源 | 其余待办、方案摘要 |
| 可构建 | 方案与关键假设复核 | 开始构建 | 验收条件、工程详情 |
| 验证失败 | 具体失败对象、原因与修复入口 | 定位并修复 | 对应验证证据、流程摘要 |
| 可应用 | 变更摘要与有效验证证据 | 预览并应用 | 完整差异、工程详情 |
| 已应用 | 目标工程、应用版本、下一步验证 | 查看流程 | 变更历史、可用的撤销 |

这只是展示和操作编排，实际构建、应用、运行仍分别遵循现有权威状态。

## 实施计划

工时为熟悉代码的一名前端工程师的粗估，不是交付承诺；真实样本能力需要先确认现有接口与主机集成，单独评估。

| 阶段 | 优先级 / 粗估 | 交付与主要模块 | 验收门槛 |
| --- | --- | --- | --- |
| 1. 可信度与可读性 | P1/P2，2–3 人日 | 移除伪指标；统一计数来源与名称；设置表单两列；修复资源对比度和双焦点；清理实现文案。涉及 aiTab、ShellPresentation、ResourceBinding 与现有样式模块 | 无固定性能数；同场景计数一致；常用字段可读；普通正文与焦点达标 |
| 2. 任务编排 | P2，4–6 人日 | 阻断优先布局；紧凑资源任务；失败原因前置；清楚的修复入口；小屏导航优化；应用差异可读名称。涉及 Plan/Clarification/BuildPresentation、ApplyPreview | 关键状态首屏可操作；一个明确主任务；原有回答/绑定/保存/恢复/Apply 合同通过 |
| 3. 领域证据 | 先做约 1 人日接口核对，再估开发量 | 样本入口、使用状态、验证证据和只读画布差异；工程/模型上下文与历史任务增强。复用 Attachments、ValidationPreview、流程预览和画布能力 | 每张图与结果能追溯到输入、运行和版本；真实效果和元数据检查明确区分 |

优先完成阶段 1 和阶段 2，可形成一次独立的体验改善版本。第一阶段按“可信数据与计数”“设置表单”“主题与文案”拆成易审查的变更；第二阶段按方案、构建、预览分批验证，避免一次同时改变所有状态展示。

## 验证与验收

1. 固定场景：空白、规划中、单问题、多问题+资源、草稿、可构建、缺参数、缺资源、结构失败、DryRun 失败、可应用、已应用、恢复中、保存失败、Readiness 超时、未配置模型。
2. 布局：1920×1080、1366×768、1024×768；深浅主题；WebView2 100%/125%/150% DPI；键盘与 reduced motion。390px 作为额外回归，桌面窗口优先。
3. 信息：总数对齐；状态有数据来源；未测试不成功；失败首屏有具体原因；技术标识默认收起；长中文、长路径、同名算子、6 个以上资源仍可操作。
4. 流程：选答案、改答案、绑定资源、草稿切换、保存失败重试、会话恢复、应用预览取消与失效、应用撤销。沿用已有测试，不因视觉通过放宽业务判定。
5. 用户走查：找 3–5 位目标使用者完成“补齐条件并构建、解释失败原因、复核应用变更”。记录首个正确操作耗时、错误点击和查找次数。以多数人在约 5 秒内定位当前问题、10 秒内找到下一步为初始目标，不把这些目标当作已有测量结果。

实施后的前端验证优先使用现有 `ai-shell-visual.spec.ts`、`ai-plan-clarification.spec.ts`、`ai-build-workspace.spec.ts`、`ai-agent-responsive.spec.ts` 和状态/恢复合同测试。涉及后端时，遵循仓库串行 .NET 测试脚本约束；真实 WebView2 走查作为发布前补充。

本次已验证工作台/会话切换、Build 验证定位、应用预览打开与取消，以及本地模型标签不切换内容。没有修改产品代码，没有重新调用真实 LLM/设备，也没有重复完整测试套件。Build 夹具任务栏的阶段文字不作为生产生命周期缺陷，详见证据边界。
