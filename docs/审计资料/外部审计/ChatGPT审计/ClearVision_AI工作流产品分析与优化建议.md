# ClearVision：AI 生成视觉检测工作流的产品分析与优化建议

> 角色视角：专业产品分析师  
> 生成日期：2026-04-30  
> 分析依据：基于 ClearVision 当前仓库资料、AI 生成链路代码、质量矩阵与审计整改文档进行产品化分析。  
> 核心问题：ClearVision 的核心竞争力不应只表述为“调用 LLM 生成工作流”，而应升级为“面向工业视觉的、受约束、可验证、可预演、可人工接管的 AI 工作流 Copilot”。

---

## 1. 执行摘要

ClearVision 已具备一个非常有潜力的产品底座：工业视觉算子体系、流程编排桌面端、AI 流程生成服务、模板优先策略、结构化校验、Dry-Run 预演、待确认参数与缺失资源提示、算子质量矩阵等。这说明项目已经不是“LLM 调用演示”，而是正在接近“工业视觉低代码 + AI Copilot”的雏形。

但从产品竞争力角度看，**LLM 调用本身不是护城河**。模型能力会被平台化、平权化，未来任何视觉软件都可以接入大模型。ClearVision 真正有机会建立护城河的地方，是把 LLM 限定在一个工业视觉专用的可控空间里：

1. 用算子元数据、端口、参数、模板和质量证据约束 LLM。
2. 用 Validator、Dry-Run、人工确认和现场回放证明结果不是“看起来合理”，而是“可运行、可解释、可验收”。
3. 用场景包和真实客户数据把通用生成能力沉淀为行业 know-how。

因此，我建议你把产品主线从“AI 帮我生成工作流”升级为：

> **用户描述检测目标并上传样图后，ClearVision 自动识别场景、推荐模板、生成可校验的视觉流程，标出缺失资源和待确认参数，经仿真预演与人工确认后进入运行与回放闭环。**

这句话比“调用 LLM 生成流程”更能体现产品价值，也更容易打动工业客户、集成商和评审者。

## 2. 当前项目画像

### 2.1 已形成的产品资产

| 资产 | 当前价值 | 产品化含义 |
|---|---|---|
| 桌面端流程编排 | WinForms + WebView2 + 本地后端端点 | 适合工业现场本地部署与工程师可视化操作 |
| 统一 Operator 体系 | 算子被封装为元数据、端口、参数、运行时 | LLM 可以基于稳定能力目录生成流程，而不是自由幻想 |
| 155 个正式算子 | 覆盖预处理、检测、测量、标定、匹配、AI 推理、通信、流程控制等 | 已具备构造完整视觉检测方案的素材库 |
| AI 工作流生成服务 | 自然语言、多轮上下文、附件、模板优先、校验、Dry-Run | 已有 AI Copilot 的核心骨架 |
| 质量矩阵与证据体系 | Contract、Golden、Dataset、Field replay 等层级 | 可向客户证明“可用性”和“可信度”，而不是只展示 demo |
| OperatorLibrary 包 | 算子库可打包为 NuGet | 未来可走 SDK、集成商、生态插件路线 |

### 2.2 AI 生成链路的成熟度判断

从当前代码和文档看，AI 生成链路已经具备以下关键环节：

```text
用户自然语言 + 附件
    ↓
PromptBuilder 组织系统提示词
    ↓
模板优先 / 场景骨架收窄生成空间
    ↓
LLM 生成结构化流程 JSON
    ↓
解析 JSON
    ↓
AiFlowValidator 校验算子、端口、参数、连线、环路
    ↓
DryRunService 做预演与覆盖率统计
    ↓
返回推荐模板、待确认参数、缺失资源
    ↓
人工确认后应用到流程编辑器
```

这个链路的方向是正确的，因为它没有把 AI 当作最终裁决者，而是把 AI 放在“受约束的草案生成器”位置。工业视觉产品最怕“AI 看似聪明但不可控”，ClearVision 当前的 Validator、Dry-Run、人工确认边界正好能降低这个风险。

### 2.3 目前最大的产品短板

当前短板不是“缺少更多算子”，而是“生成出来的流程如何被客户相信、使用、复用、验收”。

| 短板 | 影响 | 建议方向 |
|---|---|---|
| LLM 生成质量缺少系统化指标 | 无法判断 AI 功能是否真的越来越好 | 建立 NL2Flow 评测集与生成成功率指标 |
| 真实现场验证不足 | 客户可能认为只是实验室 demo | 优先做 workflow 级 field replay 与客户试点 |
| 场景模板资产尚未产品化 | AI 每次都像“从零生成” | 建立高频场景包和模板市场雏形 |
| 参数确认体验可能不够产品化 | 工程师仍需大量理解细节 | 做待确认参数面板、风险解释和修复建议 |
| “AI 生成”卖点容易被竞品复制 | 调用模型门槛低 | 把护城河放到工业算子知识库、验证闭环、真实数据证据上 |
| Prompt 与知识组织需要更工程化 | Prompt 一旦变长、变乱会影响稳定性 | Prompt 版本化、UTF-8 清理、RAG 化、结构化输出约束 |

## 3. 重新定义 ClearVision 的核心竞争力

### 3.1 不建议这样定位

> ClearVision 的核心竞争力是调用 LLM，让 AI 生成视觉检测工作流。

这个表述的问题是：

1. 容易让人觉得只是“套壳调用大模型”。
2. 难以解释为什么别人不能接同样的模型。
3. 无法体现工业视觉对可靠性、现场集成、验收、复现的要求。

### 3.2 建议这样定位

> ClearVision 是一个面向工业视觉检测的 AI 工作流 Copilot。它把自然语言、样图和现场约束转化为受算子知识库约束的视觉检测流程，并通过模板优先、结构校验、Dry-Run、待确认参数、缺失资源提示和现场回放证据，帮助工程师更快构建、验证和复用检测方案。

### 3.3 你的护城河应由五层组成

| 护城河层级 | 说明 | 可复制难度 |
|---|---|---:|
| 算子知识库 | 155 个算子的用途、端口、参数、限制、典型连接方式 | 中 |
| 场景模板库 | 线序、表面缺陷、尺寸测量、OCR、PLC 通信等场景骨架 | 中高 |
| 验证闭环 | Validator、Dry-Run、Contract/Golden/Dataset/Replay 证据 | 高 |
| 现场数据闭环 | 客户真实样本、失败案例、验收记录、回放脚本 | 很高 |
| 工程师交互体验 | 参数确认、差异修复、可视化解释、部署报告 | 中高 |

结论：**LLM 是入口，工业知识与验证闭环才是壁垒。**

## 4. 产品优化方向一：从“生成流程”升级为“生成可验收方案”

### 4.1 目标状态

AI 不只是返回一张流程图，而是返回一份可执行的方案包：

```text
检测任务理解
+ 推荐模板
+ 工作流草案
+ 参数待确认清单
+ 缺失资源清单
+ 风险点说明
+ Dry-Run 结果
+ 建议测试样本
+ 验收指标
+ 可导出的部署/验收报告
```

### 4.2 建议新增“工作流就绪度”概念

不要只给用户显示“生成成功 / 失败”。工业场景更需要分级：

| 就绪度 | 定义 | 用户动作 |
|---|---|---|
| Draft | 结构完整，但参数或资源缺失 | 补参数、补模型、补图片 |
| Runnable | Dry-Run 通过，可在测试环境运行 | 导入样本测试 |
| Verifiable | 有 Contract/Golden/Dataset 证据 | 执行验收脚本 |
| Pilot-ready | 有替代回放或实验室回放 | 小范围产线试点 |
| Production-ready | 有真实现场签核与长期稳定性证据 | 正式上线 |

这能显著提升产品可信度，也能避免 AI 功能被误解为“生成后直接上线”。

### 4.3 建议新增“AI 生成结果评分”

每次生成返回一个结构化评分：

| 评分维度 | 示例指标 |
|---|---|
| 意图匹配度 | 是否识别出检测对象、缺陷类型、输出方式 |
| 算子合法性 | 算子是否存在、端口是否兼容、是否无环 |
| 参数完整性 | 必填参数是否已填、多少参数待确认 |
| 资源完整性 | 模型文件、标定文件、PLC 地址、相机配置是否缺失 |
| 运行可信度 | Dry-Run 是否通过、覆盖率如何 |
| 工业风险 | 是否涉及安全动作、误判成本、节拍压力 |

建议公式可以先简单化：

```text
workflow_readiness_score =
  30% 结构合法性
+ 20% 参数完整性
+ 15% 资源完整性
+ 15% Dry-Run 结果
+ 10% 模板匹配置信度
+ 10% 风险可解释性
```

## 5. 产品优化方向二：做强“模板优先”，不要让 LLM 自由发挥

### 5.1 为什么模板优先是正确路线

工业视觉工作流不是开放创作，它更接近“标准工艺 + 少量现场参数变化”。高频场景通常有稳定骨架：

- 图像采集 → 预处理 → 阈值/Blob → 判定 → 输出
- 图像采集 → 模板匹配/定位 → ROI → 测量 → 公差判断 → 输出
- 图像采集 → AI 推理 → 条件分支 → PLC OK/NG
- 图像采集 → OCR/码识别 → 数据校验 → PLC/数据库写入
- 标定 → 坐标转换 → 测量/定位 → 机械臂/PLC 交互

因此，ClearVision 应把 LLM 的任务从“从零设计流程”转成“选择模板、填充参数、处理例外”。这样稳定性会大幅提升。

### 5.2 建议优先产品化 6 个场景包

| 场景包 | 价值 | 推荐优先级 |
|---|---|---:|
| 端子/线序检测 | 高重复、高行业特征，适合模板优先 | P0 |
| 表面缺陷检测 | 工业视觉常见需求，AI/传统视觉都可覆盖 | P0 |
| 尺寸/圆孔/边缘测量 | 容易体现精度与标定价值 | P0 |
| 二维码/OCR 识别 + PLC/数据库 | 集成价值明显，容易演示端到端 | P1 |
| 模板匹配定位 + ROI 检测 | 适合展示流程编排能力 | P1 |
| AI 缺陷检测 + OK/NG 分支 | 适合展示 LLM + ONNX + 通信闭环 | P1 |

### 5.3 每个场景包应包含什么

```text
scenario_pack.json
├── 场景名称、行业、关键词、适用/不适用边界
├── 推荐流程模板 skeleton
├── 必需资源：相机、光源、标定、模型、PLC 地址等
├── 参数先验：阈值范围、默认置信度、常用 ROI 形态
├── 样例自然语言请求
├── 样例图片与脱敏说明
├── 验收用例：OK/NG 样本、边界样本、异常样本
├── Dry-Run stub 配置
├── 典型失败原因与修复建议
└── 导出报告模板
```

场景包的意义是把一次性的 AI 生成能力沉淀为可复用资产。未来你甚至可以把场景包做成商业化模块。

## 6. 产品优化方向三：把算子库变成“AI 可理解的工业知识图谱”

### 6.1 当前算子元数据还可以继续增强

LLM 生成工作流时，单纯知道算子名称、端口和参数还不够。它还需要知道：

| 知识类型 | 示例 |
|---|---|
| 什么时候使用 | 表面缺陷可以用 BlobAnalysis、AnomalyDetection、SurfaceDefectDetection |
| 什么时候不要使用 | 光照极不稳定时，不建议只依赖固定阈值 |
| 上游常见算子 | DeepLearning 前通常需要 ImageResize / Normalize |
| 下游常见算子 | BlobAnalysis 后通常接 ResultJudgment / ResultOutput |
| 参数经验值 | Confidence 默认 0.5，但高误报场景建议 0.6-0.8 |
| 业务风险 | 模型路径、PLC 地址、相机曝光、标定文件不能由 AI 编造 |
| 失败模式 | 端口不兼容、缺少 ROI、缺少输出、重复连接 |
| 现场证据状态 | 是否有 Dataset、Field replay、真实产线签核 |

### 6.2 建议建立 Operator AI Card

每个算子除现有名片外，再生成一个专供 AI 检索的短卡片：

```yaml
operator: DeepLearning
category: AI检测
use_when:
  - 用户提到缺陷检测、目标检测、YOLO、AI模型
avoid_when:
  - 没有模型文件且用户要求立即上线
required_resources:
  - onnx_model_path
  - class_names
  - input_size
common_upstream:
  - ImageAcquisition
  - ImageResize
common_downstream:
  - BoxNms
  - ConditionalBranch
  - ResultOutput
pending_parameters:
  - ModelPath
  - Confidence
  - UseGpu
risk_notes:
  - 模型路径和类别名必须由用户确认
  - Dataset 证据不等于现场签核
example_patterns:
  - ImageAcquisition -> ImageResize -> DeepLearning -> ConditionalBranch -> ResultOutput
```

这类卡片比把完整算子文档塞进 Prompt 更稳定，也更适合 RAG 检索。

### 6.3 建议把算子关系沉淀为图谱

可以先不做复杂数据库，用 JSON/YAML 即可：

```text
OperatorGraph
├── 节点：OperatorType
├── 边：常见连接、可选连接、禁止连接
├── 标签：场景、行业、风险、证据等级
└── 权重：专家推荐度、历史采用率、失败率
```

AI 生成时先检索高权重路径，再让 LLM 生成结构化结果。长期看，这会比单纯 Prompt 工程更稳定。

## 7. 产品优化方向四：把“用户输入”从一句话升级为需求澄清闭环

### 7.1 一句话生成适合 demo，不适合所有工业现场

用户常说：

> “帮我检测产品缺陷。”

但工业视觉方案至少需要知道：

- 检测对象是什么？
- 缺陷类型是什么？划伤、脏污、缺料、错装、尺寸超差？
- 图像来自相机、文件还是视频流？
- 是否有样图？有 OK/NG 样本吗？
- 输出给谁？PLC、数据库、CSV、界面报警？
- 节拍是多少？允许多长推理时间？
- 是否已有模型、标定文件、模板图？
- 误判和漏判哪个成本更高？

如果用户没有给这些信息，AI 不应该装作已经知道，而应该把缺口显式暴露出来。

### 7.2 建议新增“需求澄清模式”

生成前先让 AI 输出结构化需求卡片：

```json
{
  "detectedScene": "surface_defect_detection",
  "confidence": 0.78,
  "knownFacts": ["检测表面缺陷", "需要输出OK/NG"],
  "missingFacts": ["缺陷类型", "图像来源", "节拍", "输出方式", "是否已有模型"],
  "recommendedQuestions": [
    "你要检测的是划伤、脏污、凹坑还是缺料？",
    "结果需要发送给 PLC 还是只在界面显示？",
    "是否已有 OK/NG 样本图片？"
  ],
  "canGenerateDraftNow": true,
  "draftRiskLevel": "medium"
}
```

这样能避免用户误以为 AI 生成的流程已经完备，也能减少后续返工。

### 7.3 建议做两种模式

| 模式 | 适用场景 | 产品表现 |
|---|---|---|
| 快速草案模式 | demo、探索、用户只想先看结构 | 允许信息不完整，生成 Draft，并标出风险 |
| 严谨实施模式 | 真实项目、准备上线 | 先澄清关键参数，满足最低信息集后再生成 |

这两个模式可以兼顾演示效果和工业严肃性。

## 8. 产品优化方向五：把 UX 从“聊天框”升级为“AI 工程师工作台”

### 8.1 推荐交互结构

```text
左侧：AI 需求对话 / 澄清问题
中间：流程画布 / 差异预览 / 节点高亮
右侧：参数确认 / 缺失资源 / 风险说明 / Dry-Run 结果
底部：生成日志 / 测试样本 / 验收报告入口
```

### 8.2 关键 UX 组件建议

| 组件 | 用途 | 优先级 |
|---|---|---:|
| 场景识别卡 | 展示 AI 判断的场景、置信度、命中模板 | P0 |
| 待确认参数面板 | 集中显示模型路径、阈值、PLC 地址等 | P0 |
| 缺失资源清单 | 告诉用户还缺相机、模型、标定、样图 | P0 |
| 流程差异预览 | 修改已有流程时显示新增/删除/修改节点 | P1 |
| 一键修复建议 | 针对验证失败给出“修复此问题”按钮 | P1 |
| 节点解释 tooltip | 解释为什么选这个算子、参数依据是什么 | P1 |
| 样图测试面板 | 允许用户拖入 OK/NG 样图快速验证 | P1 |
| 验收报告导出 | 输出流程、参数、测试结果、风险声明 | P2 |

### 8.3 生成失败时不要只显示错误

当前 AI 生成失败可能来自 JSON 解析、端口错误、参数错误、模型服务失败等。产品上应把失败转化为可操作建议：

```text
问题：DeepLearning 的 ModelPath 缺失
影响：无法执行 ONNX 推理
建议：选择一个 .onnx 模型文件，或改用传统视觉模板
操作：[选择模型文件] [改用传统视觉方案] [重新生成]
```

这比“AI 返回内容校验失败”更符合工程师使用习惯。

## 9. 产品优化方向六：建立 AI 生成质量评测体系

### 9.1 为什么必须做评测

如果没有评测集，AI 工作流生成会陷入三个问题：

1. Prompt 改动后不知道变好还是变坏。
2. 更换模型后不知道是否影响工业场景稳定性。
3. 很难向客户证明 AI 功能可靠。

### 9.2 建议建立 NL2Flow Eval v1

每条评测样本包含：

```yaml
id: surface_defect_yolo_to_plc_001
user_request: 用AI模型检测产品表面缺陷，有缺陷发NG给PLC，没有缺陷发OK
attachments: []
expected_scene: ai_defect_detection
must_include:
  - ImageAcquisition
  - ImageResize
  - DeepLearning
  - ConditionalBranch
  - ModbusCommunication
must_not_include:
  - OCR
  - CodeRecognition
required_pending_parameters:
  - ModelPath
  - PlcIpAddress
acceptance_rules:
  - graph_is_dag
  - all_ports_exist
  - no_duplicate_input_connections
  - has_result_output_or_plc_output
expert_template_id: ai_defect_to_plc_v1
```

### 9.3 建议使用的核心指标

| 指标 | 含义 | 目标建议 |
|---|---|---:|
| First-pass valid rate | 首次生成通过 Validator 的比例 | 80%+ |
| Dry-Run pass rate | 通过 Dry-Run 的比例 | 70%+ 起步，逐步提升 |
| Template match accuracy | 场景模板命中是否正确 | 85%+ |
| Required operator recall | 必需算子召回率 | 90%+ |
| Invalid operator rate | 幻觉算子比例 | 接近 0 |
| Pending parameter precision | 待确认参数是否真的需要确认 | 80%+ |
| Human edit distance | 人工采用前需要修改多少节点/连线 | 越低越好 |
| Time to first runnable workflow | 从输入需求到可运行流程的时间 | 核心商业指标 |
| Acceptance conversion | AI 草案被用户采纳的比例 | 核心产品指标 |

### 9.4 建议建立评测分层

```text
L0：格式评测 —— 是否输出合法 JSON
L1：结构评测 —— 算子、端口、连线、DAG 是否合法
L2：语义评测 —— 是否选对场景与关键算子
L3：运行评测 —— Dry-Run / stub / 样本测试是否通过
L4：专家评测 —— 工程师是否愿意采用
L5：现场评测 —— 是否通过真实产线验收
```

只有做到 L3 以上，AI 生成能力才适合对外宣传为“可落地”。

## 10. 产品优化方向七：强化真实现场证据，不要只停留在算子级质量

### 10.1 当前证据体系的机会与风险

你已有质量矩阵，这是很好的工程资产。但产品上要注意：

- 算子质量高，不代表 AI 生成的整条 workflow 就一定可靠。
- 合成 Golden case 不等于真实产线样本。
- Dataset 证据不等于现场签核。
- Field replay substitute 不等于真实客户验收。

因此，下一阶段应从“算子级证据”升级到“工作流级证据”。

### 10.2 建议建立 Workflow Evidence Matrix

| Workflow 模板 | Validator | Dry-Run | Golden 样本 | Dataset | Field replay | 客户签核 | 状态 |
|---|---:|---:|---:|---:|---:|---:|---|
| wire_sequence_v1 | ✅ | ✅ | ✅ | 部分 | 待补 | 待补 | Pilot-ready |
| surface_defect_blob_v1 | ✅ | ✅ | ✅ | 待补 | 待补 | 待补 | Verifiable |
| ai_defect_to_plc_v1 | ✅ | ✅ | 部分 | ✅ | 替代回放 | 待补 | Pilot-ready |
| ocr_to_database_v1 | ✅ | ✅ | 待补 | 待补 | 待补 | 待补 | Runnable |

这会比单独展示“155 个算子 A 级”更贴近客户采购逻辑。

### 10.3 真实现场数据闭环建议

优先选择 3 条试点闭环：

1. 线序/端子检测：场景边界清晰，适合模板优先。
2. 表面缺陷检测：客户价值明显，但需要样本积累。
3. AI 缺陷检测 + PLC 输出：最适合展示端到端闭环。

每条闭环至少收集：

```text
- OK 样本 50 张
- NG 样本 50 张
- 边界样本 20 张
- 误检/漏检案例
- 相机/光源/曝光/节拍配置
- 生成前用户需求
- AI 生成草案
- 人工修改记录
- 最终上线流程
- 验收结果与复现命令
```

这部分数据会成为 ClearVision 未来最难被复制的资产。

## 11. 产品优化方向八：工程架构与 LLM 策略优化

### 11.1 Prompt 工程需要产品化治理

建议把 Prompt 当作产品配置，而不是散落在代码里的长文本。

| 建议 | 目的 |
|---|---|
| Prompt 模板文件化 | 便于版本管理、A/B 测试、热更新 |
| 强制 UTF-8 与可读性检查 | 避免编码乱码影响模型理解 |
| Prompt 单元测试 | 检查关键规则、输出格式、few-shot 是否存在 |
| Prompt 版本号写入结果 | 方便追踪某次生成由哪个版本产生 |
| Prompt diff 审核 | 防止一次修改破坏核心规则 |

如果系统提示词里出现乱码、重复或过长内容，LLM 的输出稳定性会明显下降。建议优先把 PromptBuilder 的文本内容清理为独立、可审计、可测试的资源文件。

### 11.2 结构化输出优先级高于“自然语言约束”

建议优先采用：

1. JSON Schema / structured output。
2. 函数调用式输出约束。
3. 输出后 schema validation。
4. 不合法时进入 repair loop。

不要只依赖“请只返回 JSON”这类自然语言要求。

### 11.3 引入受控 repair loop

当生成失败时，建议区分自动修复与人工修复：

| 问题类型 | 建议处理 |
|---|---|
| JSON 格式错误 | 自动 repair 1 次 |
| 算子名不存在 | 自动基于候选算子替换 1 次 |
| 端口名错误 | 自动基于元数据修复 |
| 缺少必填参数但有默认值 | 自动填默认值，并提示用户 |
| 缺少模型路径、PLC 地址、标定文件 | 不自动编造，进入人工确认 |
| 涉及安全动作或设备控制 | 必须人工确认 |

这能同时提升成功率和安全性。

### 11.4 模型路由策略

建议不要绑定单一模型，而是建立模型路由：

| 任务 | 推荐模型策略 |
|---|---|
| 场景分类 | 小模型 / 本地模型即可 |
| 模板检索 | 规则 + embedding 检索 |
| 流程 JSON 生成 | 强结构化能力模型 |
| 图片理解 | 支持视觉输入的多模态模型 |
| 参数解释 | 小模型即可 |
| 高隐私客户 | 本地模型或私有化模型 |

这样可以降低成本、延迟和供应商锁定风险。

### 11.5 日志与隐私

需要特别注意：

- 不要在日志中保存完整 API Key。
- 不要默认保存用户上传的生产图片。
- 不要向前端或日志暴露模型 chain-of-thought；可以输出简短 rationale。
- PromptTrace 只在开发态或显式调试时开启。
- 生成结果、人工修改、采用情况可以匿名化采集，作为优化数据。

## 14. 建议的产品指标体系

### 14.1 北极星指标

> **从用户提出检测需求到生成可运行工作流的时间。**

英文可定义为：Time to Runnable Vision Workflow。

这个指标非常适合 ClearVision，因为它直接体现 AI 工作流生成的价值。

### 14.2 核心产品指标

| 指标 | 说明 |
|---|---|
| AI 生成使用率 | 有多少新流程由 AI 生成入口创建 |
| AI 草案采纳率 | 用户最终采用 AI 草案的比例 |
| 人工编辑距离 | 用户采用前修改了多少节点、连线、参数 |
| 首次校验通过率 | 生成后第一次通过 Validator 的比例 |
| Dry-Run 通过率 | 生成后通过 Dry-Run 的比例 |
| 待确认参数完成率 | 用户是否顺利补齐参数 |
| 模板命中率 | 高频场景是否命中正确模板 |
| 失败原因分布 | JSON、端口、参数、资源、模型服务等 |
| 场景包复用率 | 哪些模板真正被反复使用 |
| 试点转正式率 | 客户试用后进入正式部署的比例 |

### 14.3 建议建立 AI 生成看板

```text
今日生成次数
├── 成功 / 失败
├── 失败原因 Top 10
├── 模板命中 Top 10
├── 平均待确认参数数
├── 平均人工修改节点数
├── 平均生成耗时
├── 模型成本
└── 用户采纳率
```

这会让你持续知道 AI 功能是否真的产生价值。

## 15. 风险清单与应对策略

| 风险 | 表现 | 应对 |
|---|---|---|
| LLM 幻觉 | 编造算子、端口、参数 | 元数据约束、Schema、Validator、repair loop |

| 隐私安全 | 上传图片、API Key、日志泄露 | 本地部署、脱敏、密钥保护、日志策略 |

## 16. 近期最值得做的 12 件事

1. **把产品定位改成“AI 工作流 Copilot”，不要只说“调用 LLM”。**
2. **清理并版本化 PromptBuilder，确保给模型的系统提示词干净、可测、可审计。**
3. **建立 NL2Flow Eval v1，至少覆盖 100 条高频工业视觉需求。**
4. **选择 5 个核心场景包，优先做模板优先生成。**
5. **新增工作流就绪度：Draft / Runnable / Verifiable / Pilot-ready / Production-ready。**
6. **把待确认参数、缺失资源、风险说明做成右侧产品面板。**
7. **建立 Workflow Evidence Matrix，从算子证据升级到流程证据。**
8. **给每次 AI 生成记录指标：生成成功率、失败原因、人工采纳率、修改距离。**
9. **做流程 diff，让“修改已有流程”成为强功能。**
10. **建立受控 repair loop，能自动修 JSON、端口、算子小错误，但不编造关键资源。**
11. **把真实 field replay 作为 90 天内的产品里程碑，而不是长期技术债。**
12. **设计一个 10 分钟端到端演示，用 AI 生成 + 参数补齐 + Dry-Run + 报告导出讲清产品价值。**

## 17. 建议的对外话术

### 一句话版本

> ClearVision 让工程师用自然语言和样图快速生成工业视觉检测流程，并通过模板、校验、预演和人工确认，把 AI 生成结果变成可落地的工程方案。

### 三句话版本

> ClearVision 不是让大模型自由画流程，而是让大模型在工业视觉算子、模板、端口规则和质量证据约束下生成流程草案。  
> 系统会自动识别场景、推荐模板、生成流程、标出待确认参数和缺失资源，并通过 Validator 与 Dry-Run 做预演。  
> 工程师确认后可以直接进入测试、复用和验收，大幅缩短从需求到可运行视觉方案的时间。

### 面向客户的价值表达

> 以前搭一个视觉检测流程需要工程师熟悉算子、参数、连接和通信配置；现在用户只需描述检测目标，ClearVision 就能生成可审查的流程草案，并告诉你还缺哪些模型、阈值、相机或 PLC 配置。

## 18. 结论

ClearVision 当前最有价值的方向，不是继续堆更多算子，也不是单纯追求“大模型一次生成正确”。真正的优化方向应是：

```text
算子库规模
    ↓
算子知识化
    ↓
场景模板化
    ↓
AI 生成受控化
    ↓
验证预演闭环化
    ↓
现场证据产品化
    ↓
客户交付规模化
```

你的项目已经有不错的工程基础。下一步要把“技术功能”转译成“产品能力”：让客户看到生成流程不仅快，而且可解释、可补齐、可验证、可复用、可验收。

最关键的战略判断是：

> **LLM 不是 ClearVision 的最终护城河；ClearVision 的护城河是工业视觉知识、场景模板、验证闭环和真实现场证据共同构成的 AI 工作流生成系统。**
