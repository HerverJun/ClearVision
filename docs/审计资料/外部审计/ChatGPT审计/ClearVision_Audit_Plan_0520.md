# ClearVision 现场视觉软件用户视角审计计划

> 文档定位：本计划以“现场视觉软件使用者”为核心视角，用于审计 ClearVision 在真实产线、工位调试、班组巡检、异常处理和工程交付中的可用性、稳定性与产品化成熟度。  
> 适用对象：产品负责人、研发负责人、现场实施工程师、售后维护人员、质量负责人、项目汇报材料编写者。  
> 版本日期：2026-05-20

---

## 1. 背景与目标

ClearVision 当前已经具备较完整的工业视觉平台雏形：包括桌面端 Studio、现场端 Station、可视化流程编排、检测结果追溯、实时通信、工业设备接入、算子库、测试体系和部署文档等能力。  
但从现场用户视角看，软件是否“能跑”不是最终标准，真正的标准是：

- 操作员是否敢用；
- 班组长是否看得懂；
- 工程师是否能快速交付；
- 维护人员是否能独立定位问题；
- 现场出故障时是否能快速恢复；
- 软件是否能在低配工控机和复杂网络环境下稳定运行。

本次审计目标不是继续堆叠功能，而是把现有工程能力转化为现场可感知的产品能力，重点关注以下问题：

1. 用户进入软件后，能否迅速找到自己需要的功能；
2. 结果、状态、异常是否足够直观；
3. 现场故障是否有统一诊断入口；
4. 算子成熟度是否能帮助工程师做正确选择；
5. Station 与 Studio 的多点部署是否便于维护；
6. 软件是否适合低配工控机长期运行；
7. 是否具备可量化的产品改进指标。

## 2. 用户画像与典型场景

### 2.1 操作员

典型任务：

- 打开软件；
- 选择当前产线项目；
- 启动检测；
- 查看 OK/NG；
- 查看最近异常；
- 在必要时导出或截图反馈给工程师。

核心诉求：

- 不要看到太多工程配置；
- 不要误操作；
- 异常提示要说人话；
- 能一眼看出设备是否正常、结果是否实时。

主要风险：

- 当前界面如果默认暴露过多工程入口，会让操作员产生畏惧；
- 如果结果页没有明确“实时/历史/补齐/离线”标识，现场人员可能误判产线状态；
- 如果异常信息暴露堆栈或英文错误，现场沟通成本会很高。

### 2.2 视觉工程师 / 工艺工程师

典型任务：

- 新建项目；
- 配置相机、光源、触发和 PLC 通信；
- 搭建检测流程；
- 调整参数；
- 做离线样本验证；
- 发布运行包到 Station；
- 回看数据并优化方案。

核心诉求：

- 高频场景有向导；
- 参数调整有即时反馈；
- 算子成熟度可见；
- 发布前有检查项；
- 不要靠记忆和经验排查环境问题。

主要风险：

- 算子数量越多，越需要成熟度标识；
- 如果没有模板和向导，工程师会把大量时间花在重复配置上；
- 如果部署前没有自动体检，现场交付会被环境差异拖慢。

### 2.3 班组长 / 质量负责人

典型任务：

- 查看多个工位运行状态；
- 查看当天 OK/NG 统计；
- 定位最近异常；
- 回看某批次结果；
- 导出质量记录；
- 确认产线是否稳定。

核心诉求：

- 只读巡检；
- 多工位总览；
- 异常趋势；
- 快速追溯；
- 不需要安装或理解完整工程编辑器。

主要风险：

- 如果必须打开完整 Studio 才能查看状态，使用门槛偏高；
- 如果没有轻量看板或只读模式，管理人员很难养成日常巡检习惯；
- 如果统计口径不清楚，会影响质量复盘可信度。

### 2.4 现场维护 / 售后实施

典型任务：

- 判断 Station 是否在线；
- 判断相机是否掉线；
- 判断 PLC 通信是否中断；
- 检查端口、权限、磁盘、驱动、WebView2 等环境；
- 导出日志与诊断包；
- 协助远程研发定位问题。

核心诉求：

- 一键诊断；
- 一键导出支持包；
- 错误按“原因—影响—处理建议”呈现；
- 不需要翻源码或找研发问字段含义。

主要风险：

- 如果错误分散在日志、弹窗、控制台、前端页面中，定位效率会很低；
- 如果没有诊断包，现场复现困难；
- 如果只有开发者视角日志，售后无法独立初判。

## 3. 核心使用流程审计清单

### 3.1 操作员日常检测流程

审计问题：

- 登录后是否默认进入操作员应看到的页面；
- 是否能在 3 步内启动上次项目；
- OK/NG 是否足够醒目；
- 当前检测是否正在实时运行是否明确；
- 最近 NG 是否能快速打开；
- 是否有误入工程编辑页面的风险；
- 停机、断网、相机异常时是否有清楚提示。

建议验收标准：

- 新操作员无需工程师指导，可在 90 秒内启动上次项目；
- 用户能准确说出当前结果是实时数据还是历史数据；
- 用户能在 60 秒内找到最近一次 NG 记录；
- 操作员权限下隐藏高风险编辑入口。

### 3.2 工程师建项与调试流程

审计问题：

- 新建项目是否有场景模板；
- 相机配置是否能自动识别或引导连接；
- ROI、阈值、匹配、OCR、尺寸测量等参数是否有即时预览；
- 流程节点之间的输入输出类型是否清晰；
- 节点错误是否能定位到具体原因；
- 发布前是否检查缺失输入、通信配置、路径、权限、Station 状态；
- 是否支持离线样本回放。

建议验收标准：

- 工程师可在 12 分钟内通过模板得到第一个有效 OK/NG；
- 发布前检查能覆盖 80% 以上常见配置错误；
- 算子选择界面能显示成熟度、适用场景和风险提示；
- 调试过程中无需查看源码即可判断节点异常原因。

### 3.3 Station 部署与同步流程

审计问题：

- Studio 与 Station 的身份、版本、在线状态是否清晰；
- 运行包发布是否有版本号、哈希、时间戳和回滚策略；
- Station 收到包后是否校验完整性；
- 失败时是否有明确恢复路径；
- 多 Station 情况下是否能区分不同产线、工位和设备；
- 是否有断线重连、历史补齐、结果去重机制；
- 是否能提示当前数据是否完整。

建议验收标准：

- 每个 Station 有唯一身份；
- 每次发布都有可追溯记录；
- 发布失败能自动报告阶段：上传失败、校验失败、解包失败、加载失败或运行失败；
- 结果页标识“实时 / 历史补齐 / 离线快照 / 数据可能缺失”。

### 3.4 异常诊断流程

审计问题：

- 相机断连、PLC 断连、Station 离线、网络超时、磁盘不足、权限不足、模型缺失是否分类展示；
- 错误提示是否包含“发生了什么、影响什么、先检查什么、如何导出诊断”；
- 是否有统一故障中心；
- 是否支持一键导出诊断包；
- 诊断包是否包含运行日志、配置摘要、设备状态、版本信息、最近错误、性能指标；
- 现场人员是否能根据提示完成初步判断。

建议验收标准：

- 维护人员可在 5 分钟内导出完整诊断包；
- 80% 常见故障能在故障中心给出初步原因；
- 用户界面不直接暴露原始堆栈作为主要错误提示；
- 研发拿到诊断包后无需再次让现场手动收集基础环境信息。

## 4. 功能与交互改进建议

### 4.1 建议一：角色化首页与工作模式

当前产品更像工程师平台，而现场软件需要根据角色自动收敛入口。

建议设计三类工作模式：

| 工作模式 | 默认对象 | 首页核心内容 | 隐藏内容 |
|---|---|---|---|
| 操作模式 | 操作员 | 当前项目、启动/停止、OK/NG、最近异常、追溯入口 | 流程编辑、算子配置、高级通信 |
| 工程模式 | 工程师 | 项目、流程、相机、算子、样本、发布 | 系统级维护项可弱化 |
| 维护模式 | 实施/售后 | Station 状态、设备连接、日志、诊断包、环境体检 | 复杂算法配置 |

落地建议：

- 登录后按角色进入对应首页；
- 支持管理员临时切换模式；
- 操作模式下禁止危险编辑；
- 首页只放当天最常用功能，不追求功能大全。

### 4.2 建议二：统一故障中心

现场最需要的不是“更多日志”，而是“可理解的诊断”。

建议故障中心至少包含：

- 当前系统健康状态；
- 相机连接状态；
- PLC / TCP / 串口 / MQTT 连接状态；
- Station 在线状态；
- 结果流状态；
- 最近错误列表；
- 一键复制错误摘要；
- 一键导出诊断包；
- 常见处理建议。

错误提示建议采用统一结构：

```text
问题：Station A 已离线
影响：该工位检测结果不会继续实时上传
可能原因：网络断开、Station 程序退出、端口被占用、防火墙阻断
建议检查：
1. 检查工位电脑是否开机
2. 检查 Station 程序是否正在运行
3. 检查局域网连接
4. 点击“导出诊断包”发送给维护人员
```

### 4.3 建议三：结果数据鲜度与完整性标识

视觉软件现场使用中，用户最怕“看到了结果，但不知道结果是不是当前真实状态”。

建议在检测页、监控页、追溯页统一增加数据状态标识：

- 实时；
- 补齐中；
- 历史快照；
- Station 离线；
- 数据可能缺失；
- 仅显示摘要，未显示原图；
- 通信延迟过高。

建议展示字段：

- 最近一次结果时间；
- 最近一次 Station 心跳时间；
- 当前结果序号；
- 丢包或补齐次数；
- 当前显示数据来源：实时通道 / 历史接口 / 本地缓存。

### 4.4 建议四：高频场景向导化

建议优先做四个向导：

1. 线序检测向导；
2. OCR / 读码向导；
3. 尺寸测量向导；
4. 标定 / 视觉引导向导。

每个向导建议固定为以下步骤：

1. 选择场景；
2. 连接相机；
3. 采集样图；
4. 选择 ROI；
5. 选择算法模板；
6. 设置判定条件；
7. 映射输出字段；
8. 进行离线验证；
9. 发布到 Station；
10. 生成交付记录。

向导的价值不是降低专业性，而是把重复工程动作产品化。

### 4.5 建议五：算子成熟度前置

ClearVision 的算子库如果只展示“有哪些算子”，现场用户仍然不知道怎么选。建议在 UI 中展示成熟度标记。

建议字段：

| 字段 | 含义 |
|---|---|
| 成熟度等级 | 实验级 / 可用级 / 现场验证级 / 推荐级 |
| 适用场景 | 尺寸测量、定位、OCR、缺陷检测等 |
| 样本覆盖 | 是否有 golden test |
| 现场回放 | 是否经过 field replay |
| 性能风险 | 是否对 CPU/GPU/内存敏感 |
| 使用建议 | 推荐参数范围和典型失败条件 |

算子选择界面建议增加筛选：

- 仅显示现场验证算子；
- 仅显示低配工控机友好算子；
- 仅显示当前场景推荐算子；
- 显示不推荐原因。

## 5. 稳定性与现场容错建议

### 5.1 相机异常容错

重点审计：

- 断线后是否自动重连；
- 重连期间是否阻塞主 UI；
- 是否能区分“采图失败、图像异常、驱动异常、超时、权限/占用”；
- 是否记录异常帧信息；
- 是否有相机状态页；
- 是否能在不重启软件的情况下恢复采集。

建议：

- 相机采集线程与 UI 解耦；
- 采图失败必须进入可恢复状态；
- 对连续失败次数做阈值；
- 保留最近 N 次异常帧摘要；
- 相机 SDK 错误码翻译成中文现场语义；
- 提供“重连相机”按钮；
- 明确区分“相机在线但无图”和“相机离线”。

### 5.2 Station 与网络容错

重点审计：

- Studio 断线后是否自动恢复；
- Station 离线是否影响本地检测；
- 结果上传失败是否缓存；
- 网络恢复后是否补传；
- 是否能避免重复上传；
- 是否有心跳和最后在线时间；
- 是否支持多 Station 管理。

建议：

- Station 本地检测不依赖 Studio 在线；
- 结果上传采用队列；
- 失败结果进入本地缓存；
- 恢复后按序补传；
- 每条结果有唯一 ID；
- UI 显示“待上传数量”和“最近同步时间”。

### 5.3 低配工控机容错

重点审计：

- CPU 占用峰值；
- 内存长期增长；
- 图像缓存是否及时释放；
- 日志是否无限增长；
- UI 是否因检测阻塞卡死；
- 多线程异常是否会导致静默失败；
- 长时间运行是否有资源泄漏。

建议：

- 图像缓存上限明确；
- 日志滚动和自动清理；
- 大图像处理避免在 UI 线程执行；
- 模型加载和推理资源可监控；
- 增加 24h / 72h 长稳测试；
- 低配模式禁用高成本实时预览；
- 对 CPU、内存、磁盘空间设置告警阈值。

### 5.4 异常恢复策略

建议建立统一恢复等级：

| 等级 | 场景 | 系统行为 |
|---|---|---|
| L1 轻微异常 | 单次采图超时、单次通信失败 | 自动重试，记录事件 |
| L2 可恢复异常 | 相机短暂断连、Station 短暂离线 | 显示黄色状态，自动重连 |
| L3 需人工介入 | 连续采图失败、PLC 长时间断连 | 显示红色状态，给出检查步骤 |
| L4 严重异常 | 项目包损坏、模型缺失、磁盘满 | 停止相关任务，禁止继续误判 |
| L5 系统异常 | 主进程崩溃、配置损坏 | 启动恢复模式并导出诊断 |

## 6. 性能与资源管理建议

### 6.1 关键性能指标

建议持续采集以下指标：

| 指标 | 说明 |
|---|---|
| 单帧采集耗时 | 相机采图延迟 |
| 单帧处理耗时 | 图像预处理 + 算法耗时 |
| 推理耗时 | AI 模型单次执行耗时 |
| 结果输出延迟 | 从采图到结果显示/上传的时间 |
| UI 卡顿次数 | 主界面无响应或延迟 |
| CPU 峰值/均值 | 工控机负载 |
| 内存峰值/增长率 | 检查泄漏 |
| 磁盘写入速率 | 追溯和日志压力 |
| Station 同步延迟 | 多站点数据实时性 |
| 队列积压数量 | 判断系统是否跟不上产线节拍 |

### 6.2 性能测试场景

建议建立三档测试：

| 档位 | 硬件假设 | 测试目标 |
|---|---|---|
| 低配工控机 | 低端 CPU、8GB 内存、无独显 | 验证最低可用体验 |
| 标准工控机 | 中端 CPU、16GB 内存 | 验证常规部署稳定性 |
| 高配工程机 | 较高 CPU/GPU | 验证算法上限和调试体验 |

每档都应跑：

- 1 小时冒烟测试；
- 8 小时班次测试；
- 24 小时稳定性测试；
- 72 小时长稳测试；
- 断网/断相机/断 PLC 注入测试；
- 日志和追溯压力测试。

### 6.3 资源管理建议

- 明确图像生命周期：采集、显示、处理、保存、释放；
- 大图预览与算法处理分离；
- 对实时预览设置帧率上限；
- 对历史图像加载使用分页或懒加载；
- 对模型资源做加载状态和释放策略；
- 对日志与图片追溯设置保留策略；
- 对异常重试设置退避，避免疯狂重连拖垮系统；
- 对 Station 结果队列设置上限和溢出策略。

## 7. 协作与版本管理建议

### 7.1 运行包版本管理

每个发布包建议包含：

- 项目名称；
- 项目版本；
- 发布时间；
- 发布人；
- 目标 Station；
- 算子版本；
- 模型版本；
- 配置哈希；
- 依赖清单；
- 发布说明；
- 回滚包引用。

建议 UI 中展示：


### 7.2 工程变更审计

建议记录以下操作：

每条记录包含：

### 7.3 现场协作机制

建议形成三类文档自动化输出：

1. 工程交付单：记录项目配置、设备、通信、版本、验收结果；
2. 异常诊断单：由故障中心一键导出；
3. 质量追溯单：用于某批次或某次 NG 的复盘。

这样可以减少口头沟通和截图传来传去的问题。

## 11. 结论

ClearVision 当前最值得肯定的是：它已经不是单纯的算法 Demo，而是具备平台化基础的工业视觉软件。  
但下一阶段真正决定产品成熟度的，不是继续增加多少算子，而是把“现场用户每天会遇到的问题”处理好。

最优先的方向应当是：

1. 角色化首页，让不同用户只看到自己该做的事；
2. 统一故障中心，让异常可理解、可导出、可恢复；
3. 结果鲜度标识，让用户知道自己看到的数据是否可信；
4. 高频场景向导，让工程交付从经验驱动转向流程驱动；
5. 算子成熟度前置，让用户知道哪些能力适合现场；
6. 低配与长稳测试，让软件能在真实工控环境长期运行；
7. 多 Station 与只读巡检，让 ClearVision 从单机工具进化为产线平台。

一句话总结：  
**ClearVision 已经具备工程底座，下一步要从“工程师能用”升级为“现场人员敢用、维护人员能修、管理人员看得懂”。**
