## 一、多线程、死锁与异步陷阱（8个）

### 风险点 1：Dispose 内部同步阻断异步 DisconnectAsync 引发死锁
* **所处文件**：[PlcBaseClient.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.PlcComm/Core/PlcBaseClient.cs#L588-L604)
* **代码片段**：
  ```csharp
  public void Dispose()
  {
      if (_disposed)
          return;
      try
      {
          DisconnectAsync().GetAwaiter().GetResult();
      }
      finally
      {
          _disposed = true;
          _communicationLock.Dispose();
          _connectLock.Dispose();
          GC.SuppressFinalize(this);
      }
  }
  ```
* **潜在危害**：主界面或通信线程永久死锁挂起，进程无响应。
* **机理分析**：
  在同步 `Dispose` 方法中，使用了 `.GetAwaiter().GetResult()` 来阻断式调用异步方法 `DisconnectAsync()`。如果在具有同步上下文（SynchronizationContext）的 UI 线程中被触发，由于异步回调需要返回原线程排队，而此时原线程正被 `.GetResult()` 强行阻塞等待，从而形成经典的 **“双向死锁”**。此外，`DisconnectAsync()` 内部还会尝试等待 `_connectLock.WaitAsync()`，如果此时该锁正被其他挂起的网络异步任务持有，死锁将无法解开。而在 `finally` 块中立即释放锁（Dispose）更会导致排队中的其他线程抛出致命的 `ObjectDisposedException`。
* **修复建议**：
  实现 `IAsyncDisposable` 接口支持异步释放。在同步 `Dispose` 中，不应调用带有复杂锁同步的异步 `DisconnectAsync()`，而是以非阻塞的同步方式直接强行 `Close/Dispose` 底层的 `TcpClient` 和 `NetworkStream` 释放 Socket 句柄，促使所有挂起的网络等待瞬间以 `SocketException` 崩溃退出并回卷，最后再释放锁：
  ```csharp
  public void Dispose()
  {
      if (_disposed) return;
      _disposed = true;
      try
      {
          _networkStream?.Close();
          _tcpClient?.Close();
      }
      catch { /* 忽略释放物理连接的异常 */ }
      finally
      {
          _communicationLock.Dispose();
          _connectLock.Dispose();
      }
  }
  ```

### 风险点 3：Coordinator 准备关机时同步阻断 Task.WhenAll 造成死锁
* **所处文件**：[InspectionRuntimeCoordinator.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Infrastructure/Services/InspectionRuntimeCoordinator.cs#L429-L436)
* **代码片段**：
  ```csharp
  try
  {
      Task.WhenAll(pendingCleanupTasks).GetAwaiter().GetResult();
  }
  catch (Exception ex)
  {
      _logger.LogDebug(ex, "[Coordinator] 等待清理任务结束时异常");
  }
  ```
* **潜在危害**：系统在退出、切换运行包或关机时发生无限卡死。
* **机理分析**：
  在协调器 `Dispose` 时，获取了所有后台清理 Task（`CleanupSessionAsync`）并强行阻断式等待 `Task.WhenAll`。然而这些清理 Task 内部在延迟 `Task.Delay(100)` 后，会执行 `await _stateLock.WaitAsync()`。如果 `Dispose` 正在执行且调用线程被 `GetResult()` 卡住，而在单线程同步上下文中被调度，正在排队等待进入 `_stateLock` 锁的 `CleanupSessionAsync` 将因为上下文被阻断而永远无法获得执行机会，造成不可解的**循环死锁**。
* **修复建议**：
  重构为异步释放 `DisposeAsync`，在其中 `await Task.WhenAll(pendingCleanupTasks)`。如果必须保留同步 `Dispose`，则不应对这些后台清理 Task 进行阻塞式等待，仅发出取消信号后让其在线程池自行销毁。

### 风险点 5：WebView2 共享图像缓冲区过早 using 释放导致的内存越界与崩溃
* **所处文件**：[WebView2Host.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Desktop/WebView2Host.cs#L421-L433)
* **代码片段**：
  ```csharp
  using var sharedBuffer = _environment.CreateSharedBuffer((ulong)data.Length);
  using (var stream = sharedBuffer.OpenStream())
  {
      stream.Write(data, 0, data.Length);
  }
  var additionalData = JsonSerializer.Serialize(new { width, height });
  _webView.CoreWebView2.PostSharedBufferToScript(
      sharedBuffer,
      CoreWebView2SharedBufferAccess.ReadOnly,
      additionalData);
  ```
* **潜在危害**：高频发送图像时，前端界面花屏、黑屏，或 WebView2 渲染进程发生致命非法内存访问而瞬间崩溃退出（ProcessFailed）。
* **机理分析**：
  `PostSharedBufferToScript` 是一次**异步的跨进程内存共享（IPC）**，该方法在 C# 线程执行完毕时，Chromium 渲染进程很有可能**尚未接收或正在读取**共享缓冲区的数据。然而在 C# 端，使用了 `using var sharedBuffer = ...`，这会导致 `SendSharedBuffer` 方法大括号一结束，`sharedBuffer.Dispose()` 将**立即执行并销毁底层共享内存页面**。此时前端再去读取，将直接发生**时序竞态条件冲突**。轻则读取不到数据呈现黑屏，重则导致底层非托管内存非法访问越界，引起渲染进程直接挂掉崩溃。
* **修复建议**：
  不能在每次发送时就销毁共享内存。应采用 **环形双缓冲区（RingBuffer）重用模式**。前端在消费完图像后，必须通过 API 向后端发送 Ack 回执，后端收到 Ack 后再将该 Buffer 标记为可复用或在此时 Dispose，从而保证生命周期同步。

### 风险点 6：跨线程 UI 委托排队滞后运行引起的 NullReferenceException 崩溃
* **所处文件**：[WebView2Host.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Desktop/WebView2Host.cs#L301-L308)
* **代码片段**：
  ```csharp
  // 在 UI 线程上执行
  if (_webView.InvokeRequired)
  {
      _webView.Invoke(() => _webView.CoreWebView2.PostWebMessageAsJson(json));
  }
  else
  {
      _webView.CoreWebView2.PostWebMessageAsJson(json);
  }
  ```
* **潜在危害**：在关闭应用或频繁交互中，桌面程序抛出未捕获的空指针异常（NullReferenceException）并瞬间闪退。
* **机理分析**：
  虽然在 `SendMessageAsync` 开头有 `if (!_isInitialized || _webView.CoreWebView2 is null)` 的检查。然而由于多线程执行，当 `_webView.Invoke` 把委托排队到 WinForms UI 消息队列等待调度时，存在显著的时序延迟。在此期间如果用户关闭了窗口或销毁了 Web 视图，UI 线程执行该委托时，`_webView.CoreWebView2` 极有可能已经被设为 `null` 且底层物理句柄已销毁。这就导致排在队列里的 Lambda 表达式在运行到 `_webView.CoreWebView2.PostWebMessageAsJson` 时直接抛出空指针异常，并因处于 UI 主消息循环的顶层而拖垮整个进程。
* **修复建议**：
  在 `Invoke` 的 Lambda 委托体内部增加二次 null 检查和 `IsDisposed` 判断：
  ```csharp
  _webView.Invoke(() =>
  {
      if (!_webView.IsDisposed && _webView.CoreWebView2 != null)
      {
          _webView.CoreWebView2.PostWebMessageAsJson(json);
      }
  });
  ```

### 风险点 7：WinForms UI 助手 BeginInvoke 缺乏二次状态检查引发顶级崩溃
* **所处文件**：[MainForm.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Station/MainForm.cs#L1522-L1536)
* **代码片段**：
  ```csharp
  private void Ui(Action action)
  {
      if (IsDisposed)
      {
          return;
      }
      if (InvokeRequired)
      {
          BeginInvoke(action);
          return;
      }
      action();
  }
  ```
* **潜在危害**：程序关闭时频繁抛出 `ObjectDisposedException` 或 `InvalidOperationException` 崩溃异常。
* **机理分析**：
  `Ui` 助手用于在主线程更新 UI。当后台线程（如 `SnapshotChanged` 回调）投递 UI 动作时，`BeginInvoke` 将其异步排入队列。但由于排队滞后，在排队等待期间如果 MainForm 被关闭释放，当 UI 线程执行该 action 时，action 内部访问并更新控件（如 `_previewBox.Image = ...`）的操作将会因为控件已释放而瞬间崩溃。`IsDisposed` 的首部检查在排队之前做，无法阻挡排队之后的状态退化。
* **修复建议**：
  在排队的 Lambda 内部增加 IsDisposed 保护过滤：
  ```csharp
  private void Ui(Action action)
  {
      if (IsDisposed) return;
      if (InvokeRequired)
      {
          BeginInvoke(() => { if (!IsDisposed) action(); });
          return;
      }
      action();
  }
  ```

### 风险点 8：PLC 驱动核心层中字长（DataType Word）映射不一致的致命 Bug
* **所处文件**：[HaoPlcClientBase.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.PlcComm/Core/HaoPlcClientBase.cs#L399-L413) 与 [PlcBaseClient.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.PlcComm/Core/PlcBaseClient.cs#L525-L539) 对比
* **代码片段对比**：
  * `PlcBaseClient.cs` 的映射：
    ```csharp
    "Int16" or "UInt16" or "Short" or "UShort" => (2, PlcDataType.Word),
    "Int32" or "UInt32" or "Int" or "UInt" => (4, PlcDataType.DWord),
    ```
  * `HaoPlcClientBase.cs` 的映射：
    ```csharp
    "Int16" or "UInt16" or "Short" or "UShort" => (1, PlcDataType.Word),
    "Int32" or "UInt32" or "Int" or "UInt" => (2, PlcDataType.DWord),
    ```
* **潜在危害**：读取 PLC 数据时抛出致命的 `IndexOutOfRangeException` 通信异常并导致整个系统判定出错或通信中断。
* **机理分析**：
  两个核心基类中对相同基础类型的“读取长度”做出了完全冲突的映射：`PlcBaseClient` 将 `Int32` 的读取长度映射为 `4`（代表 **4 个字节 Byte**），而 `HaoPlcClientBase` 却将其映射为 `2`（代表 **2 个字 Word**）。
  如果西门子/三菱客户端继承了 `HaoPlcClientBase` 并在底层调用时发生了对于长度单位的混淆（例如部分协议库以字节为参数，部分以字为参数），那么 `ReadAsync<int>` 在执行时可能仅在物理上读取了 2 字节（因为 `length` 被传入了 `2`），导致返回的 `buffer` 只有 2 字节。随后进入 `ConvertBytesToType<T>` (L415) 进行 `ByteTransform.ToInt32(buffer, 0)` 强制解析 4 字节，就会发生**数组越界（IndexOutOfRangeException）**崩溃！这在工业高频控制中是严重的稳定性灾难。
* **修复建议**：
  在基类级别统一读取长度的语义定义（建议统一以 Byte 字节数或者明确以 Word 字数表述，并严格做单位转换），彻底纠正 `HaoPlcClientBase` 中写死的混淆参数。

## 二、本地存储、IO 性能与并发冲突（5个）

### 风险点 9：本地配置高频日志与健康序号生成时强行同步写磁盘
* **所处文件**：[StationLocalSettingsStore.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Station/StationLocalSettingsStore.cs#L107-L125)
* **代码片段**：
  ```csharp
  public long NextLogSequenceId()
  {
      lock (_syncRoot)
      {
          _settings.LastLogSequenceId++;
          SaveLocked(); // 写入磁盘！
          return _settings.LastLogSequenceId;
      }
  }
  ```
* **潜在危害**：工控机硬盘 IO 队列打满，写入寿命剧烈磨损，主线程/UI 线程频繁发生严重卡顿与掉帧。
* **机理分析**：
  在工业软件中，每秒可能产生数百条日志。然而在此处的设计中，每一次调用 `NextLogSequenceId()` 时，**都会同步阻塞地调用 `SaveLocked()` 重写整个 settings JSON 配置文件，并发生 `File.WriteAllText` 和 `File.Copy` 备份操作**。这导致非凡的磁盘 IO 瓶颈，不仅大大削减了工控机固态硬盘（SSD）的物理使用寿命，还会因为主线程被同步 IO 挂起而造成界面经常性的假死。
* **修复建议**：
  日志和健康序号是典型的内存临时高频状态，根本不需要每次自增都执行刷盘。应当只在内存中自增，并仅在应用正常关闭时刷盘，或者在后台以低频定时器（例如 30 秒一次）进行异步批量刷盘。

### 风险点 10：SpoolBytes 属性频繁同步文件系统递归枚举引起巨大 IO 瓶颈
* **所处文件**：[StationSpoolStore.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Station/Sync/StationSpoolStore.cs#L95-L106)
* **代码片段**：
  ```csharp
  public long SpoolBytes
  {
      get
      {
          lock (_syncRoot)
          {
              return Directory.Exists(_directoryPath)
                  ? Directory.EnumerateFiles(_directoryPath, "*", SearchOption.AllDirectories).Sum(path => new FileInfo(path).Length)
                  : 0;
          }
      }
  }
  ```
* **潜在危害**：健康检查循环高频触发时，由于同步大目录枚举，磁盘 IO 瞬间瘫痪，拖慢检测主流程。
* **机理分析**：
  `SpoolBytes` 属性每次被读取（如在健康监测 DTO 中）时，都会在锁内对 `_directoryPath` 整个目录进行递归检索，并对里面堆积的所有文件调用 `FileInfo.Length` 获取大小求和。当本地 spool 目录中积累了上万条数据记录时，这会变成一个极其昂贵的文件系统扫描操作。在锁的保护下，会卡死所有其他调用 `Enqueue` 写入数据的引擎线程，直接引起极大的数据处理延迟。
* **修复建议**：
  在内存中维护一个增量的 `_currentSpoolBytes` 变量。只在系统初始化 Load 时扫描一次，此后在 `Enqueue` 添加数据和 `Acknowledge` 删除数据时直接从内存中做加减计算，避免高频物理扫描文件系统。

### 风险点 11：写入 JSON 文件缺乏物理强刷落盘（Flush to Disk）导致断电配置损坏
* **所处文件**：[StationSpoolStore.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Station/Sync/StationSpoolStore.cs#L303-L309)
* **代码片段**：
  ```csharp
  private void SaveStateLocked()
  {
      var tempPath = _stateFilePath + ".tmp";
      var json = JsonSerializer.Serialize(_state, _jsonOptions);
      File.WriteAllText(tempPath, json, new UTF8Encoding(false));
      File.Move(tempPath, _stateFilePath, overwrite: true);
  }
  ```
* **潜在危害**：车间突然断电后，系统配置文件、序列状态文件发生 0x00 空白损坏，导致下次启动时直接崩溃闪退。
* **机理分析**：
  虽然使用了 `.tmp` 加 `File.Move` 的方式来保障元数据级别的覆盖原子性。然而，`File.WriteAllText` 只是将数据写入了操作系统的内核页缓存（Page Cache），并未保证物理落盘。如果发生车间断电或蓝屏系统崩溃，内存数据未落盘，导致下次开机时 `station-sync-state.json` 变成一堆空字节（Null-Byte）。Json 序列化就会彻底损坏崩溃。
* **修复建议**：
  在写入流时，显式调用 `Flush(true)` 或 `FileStream.Flush(flushToDisk: true)`，强迫操作系统将数据从内核缓存真正刷新写入到 SSD 物理介质中后，再执行 Move 重命名操作：
  ```csharp
  using (var fs = new FileStream(tempPath, FileMode.Create, FileAccess.Write, FileShare.None))
  {
      JsonSerializer.Serialize(fs, _state, _jsonOptions);
      fs.Flush(flushToDisk: true); // 强刷物理磁盘
  }
  File.Move(tempPath, _stateFilePath, overwrite: true);
  ```

### 风险点 13：部署时拷贝 DLL 文件引发文件锁定，破坏性 RollBack 导致系统瘫痪
* **所处文件**：[StationPackageDeploymentService.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.Product.Station/Sync/StationPackageDeploymentService.cs#L78-L110)
* **代码片段**：
  ```csharp

  {
      ResetDirectory(lastKnownGoodRoot);
      CopyDirectory(activeRoot, lastKnownGoodRoot);
  }
  ...
  if (Directory.Exists(activeRoot))
  {
      Directory.Move(activeRoot, archiveTarget);
  }
  Directory.Move(runtimeRoot, activeRoot);
  ```
* **潜在危害**：在算法运行包部署过程中，由于正在加载的 DLL 或模型文件正被引擎独占锁定，拷贝或移动操作抛出 `IOException` 失败，随后触发的 `RollBack` (L298) 无法恢复，导致核心运行目录直接被删空瘫痪。
* **机理分析**：
  系统在部署新算法包时，直接在运行期间对 `activeRoot` 进行 `Move` 文件夹操作。在 Windows 环境下，任何正被 `RuntimeHost` 使用的活动文件（如算法库 DLL、AI 算子模型文件）都无法被重命名或移动。这会导致 `Directory.Move` 抛出 `IOException` 失败。此时系统进入 catch 并触发 `RollBack`。然而，`RollBack` 内部首先执行了具有毁灭性的 `Directory.Delete(activeRoot, recursive: true)`！由于文件锁定，这一步极易再次失败或仅删除了部分文件，最终使 `activeRoot` 处于**半残缺受损状态（Corrupted State）**，回滚完全失效，系统彻底罢工，无法自愈。
* **修复建议**：
  1. 部署前必须先通知 `RuntimeHost` 完全停止引擎运行，并释放所有对 `active` 目录的文件流、句柄以及 DLL 卸载（如使用 AssemblyLoadContext 隔离加载）。
  2. 回滚或部署应采用**两阶段原子提交（Two-Phase Atomic Commit）**机制，决不能先删除、后拷贝。应当先将新版本命名为 `active.next`，成功后进行瞬间的原子文件夹重命名切换。

### 风险点 15：PLC 长连接误判逻辑导致频繁断开重连及端口耗尽
* **所处文件**：[PlcBaseClient.cs](file:///c:/Users/A/Desktop/ClearVision/Acme.Product/src/Acme.PlcComm/Core/PlcBaseClient.cs#L41-L54)
* **代码片段**：
  ```csharp

  {
      get
      {
          if (_disposed) return false;
          if (_tcpClient?.Connected != true) return false;
          // 检查最后通信时间，超过60秒认为可能断开
          if (DateTime.Now - _lastCommunicationTime > TimeSpan.FromSeconds(60))
              return false;
          return true;
      }
  }
  ```
* **潜在危害**：在产线平稳无高频数据读写时，PLC 通信链接被频繁无故断开并重连，引发 ephemeral port 套接字耗尽并导致设备离线。
* **机理分析**：
  `IsConnected` 属性在判断连接时，增加了一个极其严苛且不合理的规则：如果距离最后通信时间超过了 60 秒，就直接返回 `false`。

* **修复建议**：
  不能单凭最后通信时间就直接把 `IsConnected` 判死。应使用 `_tcpClient.Client.Poll(0, SelectMode.SelectRead)` 配合可读性来检查网络套接字物理真实连接情况；或者在 60 秒内无通信时，通过定时器发送轻量心跳（Ping），而不是在有业务请求时强行断开重连。

## 总结与改善建议

ClearVision 项目整体架构具备了良好的工业设计基础（如使用了 SemaphoreSlim 互斥、缓存 Spool 设计等），但在一些“高级异步特征细节”、“文件占用边界处理”以及“本地 IO 原子性安全”上依然存有隐患。

> [!TIP]
> **黄金三条改建议**：
> 1. **全链路淘汰同步阻塞**：严禁在 `Dispose` 或是 `Validate` 中使用 `.GetAwaiter().GetResult()`，全面拥抱 `IAsyncDisposable` 异步释放。
> 2. **异步回调边界捕获**：在 `async void` 事件、`BeginInvoke` 和 `WebView2` 跨进程回调中，建立 100% 的最外层 try-catch 与 IsDisposed 保护，确保崩溃不向上传播。
> 3. **IO 与网络长连接解耦**：采用内存增量或后台低频定时器来执行 Settings/Spool 大小的文件落盘，彻底解决高频写磁盘带来的工控机 IO 假死与 SSD 寿命磨损。
