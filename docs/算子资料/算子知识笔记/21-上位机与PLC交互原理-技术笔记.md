# 上位机与 PLC 交互原理技术笔记

> 这篇笔记的目标不是把你训练成电气工程师，而是让你在视觉软件岗位面试里，把 `上位机 - PLC - 相机 - IO - 执行机构 - HMI` 这条链讲顺，并且能回扣到 ClearVision。

---

## 1. 一句话先理解这个专题

上位机和 PLC 的交互，本质上是在做三件事：

1. **控制命令下发**
2. **设备状态同步**
3. **检测结果回写**

PLC 负责稳定、确定、毫秒级的现场控制；上位机负责复杂计算、视觉算法、界面交互、历史记录和配方管理。工业视觉通常就站在两者之间。

---

## 2. 先把角色分工讲清楚

### 2.1 工业现场里常见的几个角色

| 角色 | 最擅长的事 | 不擅长的事 | 面试里怎么讲 |
|------|------------|------------|--------------|
| **PLC** | IO 控制、节拍控制、状态机、联锁、安全逻辑 | 复杂图像算法、复杂 UI、长链路数据分析 | "PLC 更像现场控制中枢" |
| **上位机** | 视觉算法、AI、配方管理、界面、日志、报表、历史追溯 | 替代 PLC 做实时硬件联锁 | "上位机更像大脑和操作台" |
| **HMI/工位屏** | 简单按钮、状态显示、参数输入 | 大规模数据处理、复杂建模 | "HMI 更偏现场操作界面" |
| **相机** | 采集图像 | 做复杂业务判断 | "相机是感知入口，不是决策中心" |
| **传感器 / IO 模块** | 检测到位、光电、限位、急停等 | 复杂业务逻辑 | "负责原始现场信号" |
| **执行机构** | 气缸、机械手、分拣器、报警灯等动作执行 | 自己判断业务逻辑 | "只负责执行，不负责思考" |

### 2.2 一个更容易记忆的比喻

- **PLC** 像一个非常稳定的现场班组长，擅长按固定节拍管动作、管安全、管联锁。
- **上位机** 像一个能看图、会分析、会记账、还能让人操作的工程站。
- **相机** 像眼睛。
- **执行机构** 像手。

所以工业视觉系统不是"谁替代谁"，而是：

> `PLC 负责稳，上位机负责聪明，视觉负责看懂。`

## 3. 一个典型的现场链路长什么样

```text
         [HMI / 工位屏]
                |
                v
[上位机 / 视觉软件] <------> [PLC] <------> [IO / 执行机构]
        |                       |
        v                       v
      [相机]                 [传感器]
```

更具体一点：

```text
工件到位
   |
   v
PLC 收到到位信号
   |
   +--> 触发相机 / 允许拍照
   |
   v
上位机拿到图像并做视觉检测
   |
   v
上位机把 OK / NG / 测量值 回写给 PLC
   |
   v
PLC 决定 放行 / 剔除 / 报警 / 停机
```

这就是面试里最常见的"视觉系统怎么和现场设备协同"的最小闭环。

## 4. PLC 为什么重要，但又不直接替代视觉

### 4.1 PLC 的强项

- 输入输出稳定
- 扫描周期固定
- 梯形图 / 状态机适合做联锁
- 和现场电气设备集成成熟
- 对"动作一定要发生"和"动作绝不能乱发生"更有保障

### 4.2 PLC 的弱项

- 不适合跑复杂图像处理
- 不适合管理大量图像和历史结果
- 不适合做复杂的 UI 交互
- 不适合承担 LLM、模板管理、场景规则和资源配置

### 4.3 面试里最稳的表达

> PLC 不是拿来替代视觉算法的，它更像一个稳定的现场控制器。上位机负责看图、算结果、做人机交互，PLC 负责把这些结果变成可靠的现场动作。

## 5. 位、字、寄存器这些概念到底是什么

### 5.1 为什么一定要懂这几个词

因为上位机和 PLC 交互时，最终经常不是在传"对象"或"接口"，而是在读写：

- 一个触发位
- 一个完成位
- 一个报警位
- 一个寄存器里的数值
- 一段配方参数区

### 5.2 最小概念表

| 概念 | 可以怎么理解 | 常见用途 |
|------|--------------|----------|
| **Bit / 位** | 只有 0 或 1 | 触发、完成、报警、允许 |
| **Word / 字** | 一般是 16 位 | 数值、状态码、计数 |
| **DWord / 双字** | 一般是 32 位 | 更大的整数、时间戳、组合值 |
| **寄存器** | PLC 里存数据的地址单元 | 读写状态、参数、结果 |
| **地址** | 具体去哪里读写 | 比如 `D100`、`M0`、`DB10.DBW2` |

### 5.3 一个直觉化例子

```text
D100 = 触发命令
D101 = 检测结果
D102 = 缺陷数量
D200~D210 = 配方参数区
```

上位机如果读到 `D100 = 1`，就知道 PLC 在发起本次检测。

上位机如果把 `D101 = 1` 写回去，PLC 可能解释为 OK；写 `0` 可能解释为 NG。
这个编码规则不是协议天然规定的，而是双方约定的"现场语义"。

### 5.4 地址体系深挖：不同 PLC 厂商的地址模型

不同厂商对"寄存器"的组织方式差异很大，这不是语法差异，而是**内存模型差异**：

| 厂商 | 地址示例 | 地址模型 | 特点 |
|------|----------|----------|------|
| **三菱 MC** | `D100`、`M200`、`X10`、`Y17` | 按软元件类型分区 | D=数据寄存器，M=内部继电器，X=输入，Y=输出，每种类型独立编址 |
| **西门子 S7** | `DB1.DBW100`、`M100`、`I0.0`、`Q0.0` | 数据块 + 区域寻址 | DB 是核心数据容器，M=标志位，I=输入，Q=输出；支持位级寻址 `DB1.DBX10.3` |
| **欧姆龙 FINS** | `D100`、`CIO0`、`W0`、`H0`、`A0` | 区域码 + 偏移 | DM=数据存储，CIO=I/O，WR=工作区，HR=保持区，AR=辅助区；每种区域有独立的功能码 |
| **Modbus** | `40001`、`00001` | 功能码隐含区域 | 1x=线圈(bool)，3x=输入寄存器，4x=保持寄存器；地址从 0 开始但业界常从 1 标号 |

**面试关键点：** 地址不只是"一个数字"，它包含了**区域类型**（决定数据保持性、断电行为）、**数据宽度**（位/字/双字）、**访问权限**（只读/读写）。ClearVision 中每种协议都有独立的地址解析器（`McAddressParser`、`S7AddressParser`、`FinsAddressParser`），就是因为这个差异。

### 5.5 位寻址的隐含陷阱

位操作看起来简单，但不同协议的位偏移范围不同：

- **西门子 S7**：一个字节内位偏移 0~7（`DB1.DBX10.3` = DB1 的第 10 字节的第 3 位）
- **欧姆龙 FINS**：一个字内位偏移 0~15（`D100.05` = DM 区第 100 字的第 5 位）
- **三菱 MC**：位元件（M、X、Y）本身就是位地址，字元件（D）按字访问

这意味着同一个"读第 5 位"的操作，在不同 PLC 上需要完全不同的地址表达和字节偏移计算。ClearVision 的 `FinsAddressParser` 中对位偏移做了范围校验（0~15），而 `S7AddressParser` 中位偏移范围是 0~7，就是这个原因。

## 6. PLC 扫描周期为什么会影响视觉触发

### 6.1 PLC 的基本工作方式

PLC 不是像 Web 服务那样"请求来了再处理一次"，它更像一个不停循环的控制器：

```text
读取输入（采样阶段）
  ->
执行逻辑（程序执行阶段）
  ->
刷新输出（输出刷新阶段）
  ->
再次读取输入
  ->
再次执行逻辑
```

这整个循环就叫一个**扫描周期**。

### 6.2 扫描周期的三个阶段详解

**阶段 1：输入采样**
PLC 把所有物理输入端子的状态一次性锁存到输入映像寄存器。在本次扫描周期内，程序看到的输入状态是"快照"，不会因为现场信号的短暂抖动而变化。

**阶段 2：程序执行**
PLC 从第一条指令开始，按顺序执行用户程序（梯形图 / 指令表 / 结构化文本）。这个阶段的时间取决于程序复杂度——简单逻辑可能 1ms，复杂程序可能 50ms 甚至更长。

**阶段 3：输出刷新**
程序执行完毕后，PLC 把输出映像寄存器的状态一次性写到物理输出端子。这意味着输出的变化只在扫描周期的末尾发生。

### 6.3 扫描周期对视觉触发的三个影响

**影响 1：信号可见性窗口**
假设 PLC 扫描周期是 10ms。如果一个传感器信号只持续 2ms（比如快速通过的工件），它可能在某个扫描周期的"程序执行阶段"出现，然后在下一个"输入采样"之前消失。这种情况下，PLC 可能根本看不到这个信号。解决方法是用 PLC 的**中断捕获**或**脉冲展宽**功能。

**影响 2：触发时刻的不确定性**
PLC 在扫描周期末尾才刷新输出。如果上位机在扫描周期的中间时刻读取 PLC 状态，它读到的是"上一次输入采样 + 当前程序执行到一半"的状态，不一定是最新状态。这就是为什么工业通信要考虑**读取时刻与 PLC 扫描周期的对齐**。

**影响 3：响应延迟的叠加**
假设 PLC 扫描周期 10ms，上位机轮询间隔 50ms。最坏情况下：
- 工件到位信号在 PLC 扫描周期的第 1ms 出现
- PLC 在第 10ms 才刷新输出（触发位 = 1）
- 上位机在第 50ms 才轮询到这个变化
- 上位机处理 + 相机拍照 + 算法执行可能再花 100~500ms
- 结果回写给 PLC 后，PLC 又要等下一个扫描周期才执行分拣

整个链路的延迟 = PLC 扫描周期 + 轮询间隔 + 处理时间 + PLC 响应周期。在高速产线上（节拍 < 1s），这个延迟叠加可能成为瓶颈。

### 6.4 一个典型误区

很多人会把"PLC 发了触发"理解成"上位机一定立刻准确收到并正确消费"。
实际上中间还隔着：

- 通信延迟（网络往返 + 协议开销）
- 轮询间隔（ClearVision 默认 50ms）
- 软件线程调度（操作系统的线程切换）
- 相机曝光时间（通常 1~10ms）
- 本次检测是否还没处理完（上一拍还在跑）

所以面试里要知道：

> 视觉触发不是一个单点动作，而是一段时序。

## 7. 上位机通常怎么和 PLC 交互

### 7.1 最常见的是轮询 + 请求响应

工业现场里，上位机经常会做这种事：

1. 周期性读 PLC 某个地址
2. 看值有没有变化
3. 满足条件就开始拍照 / 检测 / 回写

这就是**轮询**。

而大多数工业协议本质上是：

> 上位机发请求，PLC 回响应。

它不像 Web 前端那样天然强调事件推送，也不像消息队列那样默认有复杂订阅模型。

### 7.2 为什么工业现场很爱轮询

- 逻辑简单
- 设备兼容性高
- 地址化读写容易标准化
- 对 PLC 和上位机都容易落地
- 在很多老设备上，轮询本来就是最现实的方式

### 7.3 轮询的代价

- 太慢会增加响应延迟
- 太快会增加网络和 PLC 压力
- 如果没有"沿触发 / 完成位 / 清零位"，容易重复消费同一信号

### 7.4 ClearVision 中的两种轮询模型

ClearVision 针对不同场景实现了两种轮询策略：

**模型 A：按需轮询等待（WaitForValue）**
用于 MC、S7 协议。当算子参数设置 `PollingMode=WaitForValue` 时，算子进入一个 `while(true)` 循环，每次读取后用 `Task.Delay(intervalMs)` 等待，直到条件满足或超时。这不是后台定时器，而是**一次算子执行 = 一次完整的等待过程**。

```text
算子执行开始
  |
  +--> while(true)
  |      |
  |      +--> 读取 PLC 地址
  |      +--> 检查条件（Equal / NotEqual / GreaterThan ...）
  |      +--> 条件满足？--> 返回结果，算子结束
  |      +--> 超时？--> 返回失败，算子结束
  |      +--> Task.Delay(50ms)
  |      +--> 继续循环
  |
  v
算子执行结束
```

默认参数：轮询间隔 50ms，超时 30000ms（30 秒），可配置范围 10~5000ms 间隔、最大 300000ms（5 分钟）超时。

**模型 B：单次请求-响应**
用于 Modbus、TCP 协议。每次算子执行只做一次读或写，不做内置轮询。如果上层需要轮询，由流程编排层在外层实现循环。

**为什么有两种模型？** 因为不同场景对"等待"的需求不同：
- 视觉检测链路中，"等到 PLC 触发信号"是常见需求，用模型 A 封装在算子内部更简洁
- 配方参数读写、状态查询等场景，单次读写就够了，用模型 B 更直接

### 7.5 轮询条件的语义

ClearVision 的 `EvaluatePollingCondition` 支持 6 种比较条件：

| 条件 | 含义 | 典型用途 |
|------|------|----------|
| `Equal` | 值等于目标 | 等待触发位 = 1 |
| `NotEqual` | 值不等于目标 | 等待状态码 ≠ 0（有新结果） |
| `GreaterThan` | 值大于目标 | 等待计数器超过阈值 |
| `LessThan` | 值小于目标 | 等待温度降到阈值以下 |
| `GreaterOrEqual` | 值大于等于目标 | 等待完成标志 ≥ 1 |
| `LessOrEqual` | 值小于等于目标 | 等待压力降到安全值 |

数值比较时使用浮点容差 `Math.Abs(current - target) < 0.0001`，避免浮点精度问题导致条件永远不满足。

## 8. 软件触发、硬件触发、PLC 触发到底是什么关系

### 8.1 软件触发

上位机主动让相机拍一张。

适合：

- 调试
- 离线演示
- 节拍要求不高
- 上位机主导流程

### 8.2 硬件触发

相机通过外部电信号触发拍照，常见触发源就是 PLC、光电传感器、编码器等。

适合：

- 节拍要求高
- 到位就拍
- 对时序稳定性要求高

### 8.3 PLC 触发

"PLC 触发"不是一个和前两者平行的新类别，而是要再问一句：

> PLC 触发的到底是谁？

它有两种常见落法：

1. **PLC 直接给相机外部触发信号**
   这在本质上属于**硬件触发**——PLC 的输出端子直接接到相机的触发输入线，通过高低电平控制拍照时刻。这种方式时序最精确，延迟最低（微秒级），但需要硬件接线。

2. **PLC 通过通信告诉上位机"现在该检测了"**
   这在本质上是**PLC 发状态，上位机再软件触发**——PLC 写一个触发位到寄存器，上位机通过轮询读到这个位，再调用相机 SDK 的软件触发接口。这种方式灵活但延迟更高（毫秒到十毫秒级）。

### 8.4 ClearVision 中的触发实现

ClearVision 的 `TriggerModuleOperator` 实现了三种触发模式，对应不同的使用场景：

| 模式 | 实现方式 | 适用场景 |
|------|----------|----------|
| `Software` | 每次执行都直接触发（`triggered = true`） | 调试、演示、上位机主导的流程 |
| `Timer` | 基于 `DateTime.UtcNow` 的时间间隔判断，首次必触发 | 周期性采图、视频流场景 |
| `ExternalSignal` | 从上游算子的 `Signal` 端口读取 bool 值 | **PLC 触发的典型落法**：PLC 写触发位 → MC/S7 算子轮询读取 → 输出 bool → TriggerModule 的 ExternalSignal 端口接收 |

ExternalSignal 模式下，信号类型转换支持 bool / int（非零为 true）/ long / double（大于 epsilon）/ string（`bool.TryParse`），这是因为 PLC 写过来的"1"可能以不同数据类型到达。

### 8.5 面试里怎么说最稳

> 软件触发和硬件触发描述的是"相机怎么被拍"；PLC 触发描述的是"谁在发起这次节拍"。PLC 既可以通过 IO 直接硬触发相机，也可以通过通信让上位机去执行软件触发。在 ClearVision 里，PLC 通信触发的典型链路是：PLC 写触发位到寄存器 → MC/S7 算子轮询读取 → TriggerModule 的 ExternalSignal 模式接收信号 → 触发相机采集。

## 9. 一个最经典的交互时序

### 9.1 PLC 触发拍照 -> 上位机检测 -> 回写 OK/NG

```text
PLC: 工件到位
  |
  +--> 置 Trigger=1
  |
  v
上位机: 读到 Trigger=1
  |
  +--> 采图
  +--> 视觉检测
  +--> 得到 OK / NG
  |
  v
上位机: 回写 ResultCode / Done
  |
  v
PLC: 读取结果并执行分拣 / 放行 / 报警
```

### 9.2 如果没有"完成握手"会怎样

常见问题包括：

- PLC 还没来得及读结果，上位机已经把值覆盖了
- 上位机连续两次读到同一个 Trigger，重复检测
- PLC 没清 Trigger，上位机不断重复消费同一拍

所以现场系统很少只靠一个"触发位"，而是常见这几类信号组合：

- Trigger
- Busy
- Done
- Ack
- ResultCode

### 9.3 完整的四步握手协议详解

工业现场最可靠的交互模式是**四步握手**（也叫"触发-确认"协议）：

```text
步骤 1: PLC → 上位机
  PLC 置 Trigger=1（触发请求）
  上位机轮询读到 Trigger=1

步骤 2: 上位机 → PLC
  上位机置 Busy=1（正在处理）
  上位机将 Trigger 清零（防止重复消费）
  PLC 读到 Busy=1，知道上位机已收到触发

步骤 3: 上位机 → PLC
  上位机完成检测
  上位机写入 ResultCode（OK=1 / NG=2 / ErrorCode=3...）
  上位机置 Done=1（结果就绪）
  上位机清零 Busy=0

步骤 4: PLC → 上位机
  PLC 读到 Done=1，读取 ResultCode
  PLC 执行相应动作（分拣/放行/报警）
  PLC 置 Ack=1（确认已消费结果）
  上位机读到 Ack=1，清零 Done 和 ResultCode
  PLC 清零 Ack=0，回到待机状态
```

**为什么需要四步而不是两步？**

| 简化方案 | 会出现的问题 |
|----------|-------------|
| 只用 Trigger + Result | PLC 可能还没读到 Result，上位机就被下一个 Trigger 覆盖了 |
| 只用 Trigger + Done + Result | 上位机可能连续两次读到 Trigger=1（PLC 还没来得及清零），重复检测 |
| 没有 Ack | 上位机不知道 PLC 已经消费了结果，可能提前清零导致 PLC 读到空值 |
| 没有 Busy | PLC 不知道上位机正在处理，可能在等待期间重复发送 Trigger |

### 9.4 ClearVision 中的握手实践

在 ClearVision 中，这个握手逻辑是通过**流程编排 + 多个算子组合**实现的，而不是在一个算子内部硬编码四步握手。典型编排：

```text
[MitsubishiMcCommunication]  -- 轮询等待 Trigger=1（WaitForValue 模式）
        |
        v
[MitsubishiMcCommunication]  -- 写 Busy=1，清 Trigger=0
        |
        v
[ImageAcquisition]           -- 采图
        |
        v
[视觉检测算子链]              -- 算法处理
        |
        v
[ResultJudgment]             -- 判定 OK/NG
        |
        v
[MitsubishiMcCommunication]  -- 写 ResultCode + Done=1，清 Busy=0
        |
        v
[MitsubishiMcCommunication]  -- 轮询等待 Ack=1（确认 PLC 已消费）
        |
        v
[MitsubishiMcCommunication]  -- 清 Done=0，清 ResultCode
```

这种编排方式的好处是每个算子职责单一、可复用，缺点是流程编排层需要承担握手逻辑的正确性。

## 10. 工业协议的底层通信机制

### 10.1 协议分层：不只是"发个请求"

工业协议不是简单的"发字符串等回复"，它们有严格的帧结构。以 MC 协议（三菱）为例，一个读取请求帧的结构：

```text
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│ 副头部    │ 网络号   │ PLC号    │ IO编号   │ 模站号   │ 请求长度  │
│ (2字节)  │ (1字节)  │ (1字节)  │ (2字节)  │ (1字节)  │ (2字节)  │
│ 固定5000 │ 00=本地  │ FF=站号  │ 03FF     │ 00       │ 计算得出  │
├──────────┼──────────┼──────────┼──────────┼──────────┼──────────┤
│ 监视定时器│ 命令     │ 子命令   │ 起始地址 │ 软元件   │ 读取点数  │
│ (2字节)  │ (2字节)  │ (2字节)  │ (3字节)  │ (1字节)  │ (2字节)  │
│ 000A=10s │ 0401=读  │ 0000=字  │ 低位在前 │ D=4400   │ 实际值   │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

**关键细节：**
- 地址编码是 3 字节，低位在前（小端序），需要把十进制地址转换为 3 字节小端表示
- 软元件代码是 ASCII 编码（`D` = `0x44`，但 MC 协议中 `D` 的代码是 `0x4400` 的大端表示 → 实际发送 `0044`）
- 监视定时器控制 PLC 等待响应的时间，单位 250ms，设为 `0x000A` = 10 × 250ms = 2.5 秒

ClearVision 中的 `McFrameBuilder` 负责构建这些二进制帧，`McAddressParser` 负责把用户输入的 `D100` 解析为 `{软元件代码=0x4400, 地址=100, 长度=1}` 这样的结构。

### 10.2 字节序：最容易被忽略的坑

不同协议使用不同的字节序，这是跨厂商通信最常见的 Bug 来源：

| 协议 | 字节序 | 例子：值 0x1234 的存储 |
|------|--------|------------------------|
| **三菱 MC** | 小端序 (Little Endian) | `34 12`（低字节在前） |
| **西门子 S7** | 大端序 (Big Endian) | `12 34`（高字节在前） |
| **欧姆龙 FINS** | 大端序 (Big Endian) | `12 34`（高字节在前） |
| **Modbus** | 大端序 (Big Endian) | `12 34`（高字节在前） |

**为什么这很重要？** 假设 PLC 里存了一个 16 位整数值 `256`（十六进制 `0x0100`）：
- 用小端序读：收到字节 `00 01`，正确解析为 256
- 用大端序读：收到字节 `00 01`，错误解析为 1（把 `00` 当高位）

ClearVision 通过 `IByteTransform` 接口统一处理这个差异：
- `LittleEndianTransform`：用于 MC 协议
- `BigEndianTransform`：用于 S7、FINS、Modbus 协议

底层使用 `System.Buffers.Binary.BinaryPrimitives` 实现，支持 Int16/UInt16/Int32/UInt32/Int64/UInt64/Float/Double/Bool/String 的互转。

**32 位浮点数的字节序陷阱更隐蔽：** 一个 `float` 值 `3.14` 在内存中是 4 字节 `0x4048F5C3`。如果字节序搞反，读出来的可能是一个完全不同的浮点数（如 `3.90625E-36`），程序不会报错，但值是错的。这种 Bug 在调试时非常难发现。

### 10.3 协议连接的建立：握手方式对比

不同协议建立连接的方式差异很大：

| 协议 | 连接建立方式 | 握手复杂度 |
|------|-------------|-----------|
| **三菱 MC** | TCP 三次握手即就绪，无应用层握手 | 最简单 |
| **西门子 S7** | TCP 连接后需要 COTP 连接请求 + S7 协商（PDU 大小等） | 中等 |
| **欧姆龙 FINS** | TCP 连接后需要发送节点地址请求帧，解析 24 字节握手响应获取 client/server node | 中等 |
| **Modbus TCP** | TCP 连接即就绪，无应用层握手（但需要 slaveId） | 简单 |

**FINS 握手的具体过程：**

```text
上位机 → PLC: 发送节点地址请求帧（固定 20 字节）
  - 副头部: 00000000
  - 命令码: 00000000（节点地址请求）
  - 客户端 MAC 地址（或自定义值）

PLC → 上位机: 返回 24 字节响应
  - 副头部: 00000000
  - 错误码: 00000000（成功）
  - 客户端节点: 实际分配的节点号
  - 服务器节点: PLC 自身的节点号

后续所有通信帧中必须携带这两个节点号，否则 PLC 会拒绝请求。
```

ClearVision 中 `OmronFinsClient` 的 `ConnectAsync` 方法实现了这个握手流程，将获取的 `_clientNode` 和 `_serverNode` 保存在实例变量中，后续所有读写帧都使用这些值。

### 10.4 请求-响应的串行化：半双工约束

工业协议绝大多数是**半双工**的——同一时刻只能有一个请求在等待响应。如果同时发送两个请求，PLC 的响应会混在一起，导致解析错误。

ClearVision 通过 `_communicationLock`（SemaphoreSlim）保证串行：

```text
算子A: 请求1 → Lock → 发送 → 等待响应 → 收到响应 → Unlock
算子B: 请求2 → 等待 Lock → Lock → 发送 → 等待响应 → 收到响应 → Unlock
```

这个锁是协议客户端级别的，不是全局的——同一个 PLC 连接上的所有算子共享同一个锁。这意味着：
- 同一个 PLC 上的多个读写操作会排队等待
- 不同 PLC 的操作可以并行
- 轮询等待（WaitForValue）会长时间占用锁，阻塞同一 PLC 上的其他操作

**面试关键点：** 如果产线上有多个视觉工位共用一台 PLC，需要考虑轮询操作是否会阻塞关键的写操作。ClearVision 的设计中，每个协议客户端实例对应一个 TCP 连接，通过连接池管理多个 PLC 的连接。

## 11. 连接管理与健壮性

### 11.1 连接池：为什么不每次读写都新建连接

每次读写都新建 TCP 连接的问题：
- TCP 三次握手耗时 1~3ms（本地网络）
- S7/FINS 的应用层握手再加 1~5ms
- 频繁建连会导致端口耗尽（TIME_WAIT 状态）
- PLC 侧的连接资源有限（通常最多 8~32 个并发连接）

ClearVision 的连接池设计：

```text
连接池: Dictionary<string, IPlcClient>
  key = "{协议}:{IP}:{端口}" （S7 还包含 cpuType:rack:slot）
  value = 已建立连接的客户端实例

流程:
  1. 算子需要读写 PLC
  2. 查找连接池中是否有活跃连接
  3. 有 → 复用（检查 IsConnected 状态）
  4. 没有 → 创建新连接并放入池中
```

连接状态判断不只看 `TcpClient.Connected`（这可能滞后），还检查**最后通信时间是否超过 60 秒**。超过 60 秒没有通信的连接被视为"可能已死"，下次使用时会先尝试重连。

### 11.2 心跳机制：主动探测连接存活

ClearVision 在首次创建算子时自动启动后台心跳线程：

```text
心跳线程:
  while (算子存活)
    每 1000ms（可配置）:
      尝试 Ping PLC（超时 2000ms）
      成功 → 设备在线
      失败 → 设备离线，主动断开连接
           → 下次算子执行时自动重连
```

心跳读取的地址因协议而异：
- **S7**：读取 `MW0`（标志字）
- **FINS**：读取 `DM0`（数据存储区第 0 字）
- **MC**：使用 MC 协议的批量读取测试

心跳的作用不只是检测断线，还有：
- 保持 NAT/防火墙的连接映射不过期
- 及时发现网络闪断，避免算子执行时才发现连接已死
- 提供设备在线/离线状态给上层 UI 显示

### 11.3 自动重连与指数退避

当连接断开时，ClearVision 的 `ExecuteWithReconnectAsync` 模板自动处理重连：

```text
尝试执行操作
  |
  +--> 成功 → 返回结果
  |
  +--> 连接异常（SocketException / IOException）
        |
        +--> 断开当前连接
        +--> 重试次数 < 3？
              |
              +--> 是: 等待 2^retry 秒（2s → 4s → 8s，最大 30s）
              |         重新连接
              |         再次尝试操作
              |
              +--> 否: 返回失败
```

**为什么用指数退避？** 如果 PLC 侧断电重启，立即重试会持续失败。指数退避给了 PLC 启动时间，同时避免重试风暴。但最大间隔限制在 30 秒，不会无限等待。

**IOException 的特殊处理：** 检测到 `IOException` 时直接断开连接并返回失败，不做重试。因为 `IOException` 通常意味着数据流已经损坏，重试没有意义，必须重新建立连接。

### 11.4 Modbus 的分层锁机制

Modbus 算子的锁比其他协议更复杂，因为它有两层：

```text
连接级锁 (ConnectionLocks): 保护连接的创建和销毁
  |
  +--> 操作级锁 (OperationLocks): 保护单次读写操作

流程:
  1. 获取连接级锁 → 确保连接存在且活跃
  2. 释放连接级锁（让其他操作可以检查连接）
  3. 获取操作级锁 → 执行读写
  4. 释放操作级锁
```

使用 `RefCountedSemaphore`（引用计数信号量）防止锁泄漏——即使操作异常退出，锁也能被正确释放。

操作前还会检查连接存活性：`Socket.Poll` + `Available`。如果连接已死，直接 `PurgeConnection` 清理，下次执行时自动重建。

## 12. 数据类型的深层问题

### 12.1 从原始字节到业务值的转换链

PLC 通信的原始数据都是**字节数组**。从"读到 4 个字节"到"这是一个 Float 值 3.14"，中间经过的转换链：

```text
TCP Socket 收到响应帧
  |
  +--> 协议层解析：去掉帧头、帧尾、状态码，提取数据区字节
  |
  +--> 字节序转换：根据协议选择 BigEndian / LittleEndian
  |
  +--> 类型转换：根据用户指定的数据类型解释字节
        - Bit(Bool): 读取字节的某个位
        - Word(UInt16): 2 字节 → ushort
        - Int16: 2 字节 → short（有符号）
        - DWord(UInt32): 4 字节 → uint
        - Int32: 4 字节 → int（有符号）
        - Float: 4 字节 → float（IEEE 754）
        - Double: 8 字节 → double
        - String: N 字节 → string（按编码解码）
```

### 12.2 有符号与无符号的陷阱

PLC 中很多寄存器是 16 位无符号的（0~65535），但上位机可能需要处理有符号值（-32768~32767）。

例如 PLC 中存储了值 `65535`（0xFFFF），如果上位机按 `UInt16` 读取，得到 `65535`；按 `Int16` 读取，得到 `-1`。这两种解释都是"正确的"，取决于业务约定。

ClearVision 通过参数让用户选择数据类型，而不是自动推断，避免歧义。

### 12.3 浮点数的精度问题

PLC 中的浮点数通常遵循 IEEE 754 标准，但需要注意：
- 不是所有 PLC 都支持浮点运算——老型号可能只有整数运算
- 整数除法和浮点除法的结果不同：`1 / 3` 整数结果是 `0`，浮点结果是 `0.333...`
- 浮点数的精度有限：`0.1 + 0.2` 在 float 中不等于 `0.3`，而是 `0.30000001192092896`

ClearVision 的轮询条件判断中使用了浮点容差 `Math.Abs(current - target) < 0.0001`，就是为了解决这个问题。

### 12.4 Modbus 的类型限制

Modbus 算子的原始数据是 `ushort` 数组，输出为逗号分隔字符串。这意味着：
- 不支持直接读取浮点数（需要上位机把两个 ushort 拼接后按 IEEE 754 解释）
- 不支持直接读取 32 位整数（需要把两个 ushort 拼接）
- 写入时也需要用户提供 ushort 值

如果需要在 Modbus 中传输浮点数，通常的做法是：
1. PLC 侧把浮点数拆成两个 16 位寄存器
2. 上位机读取两个寄存器的 ushort 值
3. 上位机把两个 ushort 拼回 4 字节，按 IEEE 754 解释为 float

ClearVision 当前不内置这个拼接逻辑，需要在流程编排层自行处理。

## 14. 面试高频追问怎么接

### 14.1 "上位机和 PLC 的交互本质是什么？"

稳定答法：

> 本质上是控制命令、状态同步和结果回写。PLC 擅长现场控制，上位机擅长视觉算法和人机交互，工业视觉系统通常需要两者协同，而不是让谁替代谁。

### 14.2 "为什么 PLC 不直接做视觉？"

稳定答法：

> 因为 PLC 更适合确定性的 IO 和状态机控制，不适合承担复杂图像处理、模型推理、界面展示和历史记录。视觉一般由上位机完成，PLC 接收结果后决定现场动作。

### 14.3 "PLC 为什么常用轮询和寄存器？"

稳定答法：

> 因为工业现场首先看重简单、兼容、稳定。轮询和寄存器读写实现成本低、厂商支持广、调试方式成熟，所以在很多现场仍然是主流方案。

### 14.4 "你们怎么处理通信异常？"

> ClearVision 有多层防护：第一层是心跳巡检（每秒一次），主动发现设备离线；第二层是操作级异常捕获，通信失败时自动清理连接；第三层是自动重连，指数退避策略（2s → 4s → 8s，最大 30s，最多重试 3 次）；第四层是连接池状态检查，操作前验证连接存活性。整个设计目标是：网络闪断自动恢复，设备重启后自动重连，单次失败不影响后续操作。

### 14.5 "字节序问题你怎么处理的？"

> 不同协议的字节序不同——三菱 MC 用小端序，西门子 S7、欧姆龙 FINS、Modbus 用大端序。ClearVision 通过 `IByteTransform` 接口统一抽象，MC 用 `LittleEndianTransform`，其他用 `BigEndianTransform`，底层基于 `System.Buffers.Binary.BinaryPrimitives` 实现。算子层完全不感知字节序差异，只关心"我要读一个 Float"这样的业务语义。

### 14.6 "多个算子同时读写同一个 PLC 会冲突吗？"

> 会，但有保护。工业协议大多数是半双工的，同一时刻只能有一个请求在等待响应。ClearVision 在协议客户端层面用 `SemaphoreSlim` 做串行化，保证同一连接上的请求排队执行。不同 PLC 的连接是独立的，可以并行。需要注意的是，如果一个算子在做轮询等待（WaitForValue），它会长时间占用连接，阻塞同一 PLC 上的其他读写。设计流程时需要考虑这个约束。

## 15. 常见误区

### 误区 1：把 PLC 触发理解成一个单一概念

实际上要分清：

- PLC 触发相机
- PLC 触发上位机
- PLC 只负责给"允许检测"状态

### 误区 2：把"读到了值"当成"时序可靠"

现场要看的是完整闭环，不是某一次读写成功。

### 误区 3：把上位机当 PLC 用

上位机可以协调流程，但不该承担本来属于 PLC 的强实时联锁职责。

### 误区 4：只谈协议，不谈业务语义

协议只负责把值传过去；`1` 代表 OK 还是 NG、何时清零、谁先确认，这些是现场约定。

### 误区 5：忽略字节序和数据类型

同一个 `0x0100`，按小端序读是 256，按大端序读是 1。同一个 `0xFFFF`，按 UInt16 读是 65535，按 Int16 读是 -1。这些不是 Bug，是"解释方式不同"，但选错了解释方式就会出问题。

### 误区 6：认为通信成功等于业务成功

TCP 连接建立了不代表 PLC 程序在运行；读到了寄存器值不代表这个值是"新的"；写入成功不代表 PLC 已经执行了对应的逻辑。通信层只保证"字节传过去了"，业务层需要通过握手协议（Trigger / Busy / Done / Ack）确认"事情做完了"。

---

## 16. 一句话总结

> 上位机和 PLC 的交互，不是"谁更强谁替代谁"，而是把 `稳定控制` 和 `复杂计算` 各自放在最合适的位置，再通过触发、状态、结果回写把整条工业视觉链闭起来。通信层本身也有完整的工程设计——连接池、心跳、自动重连、字节序适配、半双工串行化——这些是工业软件区别于普通桌面软件的核心差异。
