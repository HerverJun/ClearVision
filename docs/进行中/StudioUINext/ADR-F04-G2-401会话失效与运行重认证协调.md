# ADR F04-G2：401 会话失效与 Formal Run 重认证协调

## 状态

```text
STATUS=ACCEPTED
DECISION_OWNER=PRODUCT_OWNER
IMPLEMENTATION_OWNER=authLifecycleRoot
AUTHORITY_INPUT=F04_PROMPT_3_OF_4
ACCEPTED_AT=2026-07-18
```

## 问题

共享 HTTP transport 可能在 Workspace Save、Preview、Formal Run 或只读查询期间收到权威 401。前端不能通过 EventBus 广播后各自清理，也不能把运行中或 unknown-outcome 的 Formal Run 猜测为停止。直接销毁 Workspace 又会丢失 F03 已冻结的 Project、snapshot、revision 与 hash reconcile 身份。

## 决策

1. `ApiTransport` 只保留一个直接 `onUnauthorized(context)` callback，context 带 method、path、URL 与发起请求时的 session generation。
2. `authLifecycleOwner` 按 generation 去重；旧 generation 的 401 不得影响新 session。Auth 自身请求使用 `suppressUnauthorizedHandler`，由 owner 在当前 operation/generation 内直接解释，避免 `401 → auth/me → 401` 递归。
3. 首个有效 401 固定执行：

   ```text
   freeze new mutations
   → phase=expired
   → removeToken
   → ProductRuntime 从 DOM 卸载
   → Workspace/Run owner 隔离或无状态时释放
   → route login
   ```

4. 有活动 Workspace owner 时保留隔离 Runtime；Workspace 进入 readonly，保存与运行新写入被冻结。保存 unknown-outcome 继续保留 `ProjectId`、submitted revision 与 GET reconcile 输入。
5. Formal Run 保留以下当前权威身份：

   ```text
   projectId
   operationId = clientSnapshotId
   runId = 已有正式结果 id，否则 null
   executionSnapshotId = result.executionSnapshotId 或 clientSnapshotId
   expectedPersistenceRevision
   expectedCanonicalFlowHash
   expectedDecisionConfigurationHash
   ```

   当前 F03 后端合同没有独立的 admission OperationId 字段；不得伪造第二身份，因此 G2 将 `clientSnapshotId` 作为现有 operation/snapshot identity。
6. 重新认证必须先通过 `/api/auth/me`，再对隔离 owner 执行保存/运行 reconcile。只有 reconcile 得到 `cancelled`、`succeeded` 或 `failed` 等权威终态，才恢复受保护 Runtime；仍为 running、identity mismatch 或请求未知时保持 `protected-transition`，用户只能重试会话恢复。
7. 无活动 Workspace owner 的 Runtime 立即 dispose；重新登录后创建全新 Runtime。存在受保护 draft/run 的 Runtime 在 reconcile 后以 readonly 方式恢复，离开该 Workspace 后再由常规 composition 创建新的可编辑 owner。

## 主动 logout 与修改密码

- 两者在发 HTTP 命令前调用相同的 ProductRuntime/Workspace `prepareForProtectedTransition`。
- dirty、saving、conflict、admitting、executing、cancel-requested、save/run unknown-outcome 未能权威 settle 时返回 `LOGOUT_BLOCKED` 或 `CHANGE_PASSWORD_BLOCKED`。
- 进入 `/change-password` 本身也由全局 Auth guard 先执行保护；不得先走允许 force-confirm 的普通 Workspace route leave。
- change-password 成功后服务端会撤销该用户 session；前端随后 remove token、dispose Runtime 并进入 login。
- logout 只有收到服务端成功响应才清本地 token。网络/响应未知时保留本地 session projection并报告结果未知，不伪装成服务端已注销。

## 放弃的方案

- EventBus 广播 401：会产生多个失效 owner、重复 dispose 与 generation 竞态。
- 401 后立即无条件销毁所有 Workspace：会丢失 unknown-outcome reconcile identity。
- 401 后继续挂载 ProductRuntime：允许新 mutation 在失效 token 下继续发起。
- 通过结果名称、Project 名称或异常文本猜测运行结果：不是权威 reconcile。

## 验证要求

- 401 burst 只触发一次 expire/dispose；
- 旧 generation 401 不注销新 session；
- Auth endpoint 401 不递归；
- ProductRuntime mount/unmount ledger；
- unknown run identity 保留并在 reauth 后先 reconcile；
- dirty/saving/executing/unknown-outcome 阻止 logout/change-password；
- browser back 不恢复 protected DOM。
