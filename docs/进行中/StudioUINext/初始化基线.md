## 当前真实技术栈

- 根 `global.json` 请求 .NET SDK `9.0.300`，并设置 `rollForward: latestFeature`；本机实际选择 SDK `9.0.304`。
- 主产品项目目标为 .NET 8 / C# 12。Desktop 与 Station 为 `net8.0-windows` WinForms；Runtime 和领域/应用层为 `net8.0` 类库。
- Desktop 依赖 WebView2，并在进程内启动 ASP.NET Core minimal APIs、SSE/SignalR 相关入口和静态文件服务。
- 数据与持久化包括 EF Core/SQLite、项目 Flow JSON、Project save transaction journal、AgentRun JSONL、Inspection result repository/spool 和 Station 本地状态。
- 当前正式前端是原生 ES modules + HTML/CSS/Canvas；UI 自动化使用 Node.js + Playwright Chromium。
- 历史 `FrontendV2` 是 Vue 3 + TypeScript + Vite + Pinia 项目，仍参与 Desktop build/publish，但不是默认正式入口。

主解决方案当前包含 `ClearVision.Product.Desktop`、`Core`、`Application`、`Infrastructure`、`Contracts`、`Runtime.Abstractions`、`Runtime`、`Station`、`Station.Simulator`、`ClearVision.PlcComm`、`ClearVision.Product.Tests` 和 `ClearVision.Product.Desktop.Tests`。Node UI tests 不在 `.sln`；`Desktop.Package` 与 `Benchmarks` 项目文件存在但不是主解决方案成员。

## 构建、测试与发布事实

- Product tests 为 `net8.0` xUnit 项目；Desktop tests 为 `net8.0-windows` xUnit/TestHost 项目；UI tests 由独立 Node package 驱动。
- `scripts/run-dotnet-test-serial.ps1` 以项目路径 mutex 保证同一 `.csproj` 单进程，并把多个 `FullyQualifiedName` 合并到一次 `dotnet test`。现有 services、phase42、PLC 和 Desktop endpoints preset 都复用该入口。
- UI Playwright 配置用 Node `http-server` 在 `127.0.0.1:5000` 服务静态 `wwwroot`，运行 Desktop Chrome；它不启动 WinForms Desktop host。
- Desktop publish 配置为 `win-x64`、self-contained、single-file、ReadyToRun、untrimmed。正式 `wwwroot` 作为外部静态资产复制；普通 build/publish 还会运行 Node 构建 `FrontendV2` 并复制到 `wwwroot/v2`。
- GitHub `release-build` 只在 main 或 `v*` tag push 后运行；普通 `studio-ui-next` push 不触发当前四个 workflow。完整 CI 必须以真实 workflow/PR checks 为证据。
- 仓库已有 Studio/Station packaging 脚本以 `.tmp/publish-check/` 为 staging；临时验证必须继续使用该目录或仓库外路径。
- “发布包静态扫描未包含 Node/source/dev artifacts”与“无 Node 目标机能够启动”是不同证据；后者当前没有现成通过证据。

## 正式前端入口与宿主

- WinForms 入口为 `ClearVision.Product.Desktop.Program`，先启动本地 ASP.NET Core 服务，再运行 `MainForm`。
- `MainForm` 创建一个 WebView2 控件和一个 `WebView2Host`。默认用户数据目录位于本机 LocalAppData 下的共享 ClearVision 路径。
- 正式静态入口为 `wwwroot/index.html`。composition root 的副作用分布在 `index.html` 提前启动的 bridge/core/feature modules 与后续 `wwwroot/src/app.js`，新入口迁移必须同时审计两处，而不能只替换 `app.js`。
- `index.html` 暴露 Project、Flow、Inspection、Results、Stations、AI 和 Settings 视图，并加载现有 FlowCanvas、ImageCanvas、HTTP、state 和 feature 模块。
- `app.js` 复用单例 `core/app/eventBus.js`、`core/app/serviceRegistry.js`、`core/messaging/httpClient.js` 与 `core/messaging/webMessageBridge.js`，并创建/注册 Canvas、页面和 capability owners。
- 现有代码包含 Property、Preview、GlobalVariables、Settings、Project、Inspection、Results/Review 和 AI capability owners。默认路径中 Property、Preview、GlobalVariables、Project、Results 使用 capability owner；Inspection、Settings、AI 的替换路径还受 `app.js` 内 experimental global gate 约束，不能只看 `appsettings.json` 推断实际 owner。
- `appsettings.json` 当前 `Studio:WorkspaceV2Enabled=false`，因此默认启动 `/index.html`。Desktop 仍会把 `FrontendV2` 构建到输出/发布目录的 `wwwroot/v2/`。
- 正式执行已收敛到 authenticated HTTP/SSE；后端会拒绝旧 WebMessage 执行消息。WebMessage bridge 仍用于文件选择、宿主消息和受控会话能力。

### 当前设计方向

正式 `wwwroot` 使用集中式 `variables.css` 设计 tokens，包含浅色/深色表面、状态色、Canvas tokens 和克制的红色强调；现有 UI 测试还包含 Quiet Precision 静态证据。旧 `FrontendV2` 自带另一套绿色 Workspace 样式，不能视为当前正式 Design System，也不应被新分支复制。

## 当前后端、运行时和现场权威

### Project、Flow、GlobalVariables

- Desktop `/api/projects/*` endpoint 调用 `ProjectService`；Flow 和 GlobalVariables 的正式更新最终进入 `ProjectSaveCoordinator`。
- `ProjectSaveCoordinator` 使用 `PersistenceRevision`、项目级 gate、prepared/commit-intended/completed journal 和 startup recovery，协调 Project、Flow、变量状态及正式 Project assets。
- Inspection 运行期间，`IInspectionRuntimeCoordinator` 的 mutation lease 会阻止冲突的 Project、Flow、Variables 和 runtime-package 变更。
- 前端 `flowRevision`、selection revision 或 Pinia state 不能替代后端 `PersistenceRevision`。
- Flow 不能被简化为一个前端对象：Project DTO authoring 读取可由文件 Flow 覆盖 DB 投影；显式 draft 执行可使用 UI 提交的 Flow；未显式传 Flow 的正式持久化执行则读取 DB `Project.Flow`，不隐式回退文件 Flow。新前端必须保留这些不同语义。

### AgentRun

- `AgentRunEventStore` 以受脱敏保护的 JSONL 保存 event/summary；`AgentRunEventStreamService` 负责 append、replay、terminal reservation 和 terminal intent。
- AgentRun endpoint、reconciliation hosted services 和 Workspace Snapshot 维护终态与恢复语义。新 UI 只能消费这些权威，不重建第二事件日志、状态机或终态判断。

### Inspection 与 Results

- `InspectionService`、`InspectionWorker` 和单例 `InspectionRuntimeCoordinator` 管理执行会话。
- 正式结果使用 `InspectionOutcome` 的 Execution/Decision 双语义，并持久化为 `InspectionResult`；后台 channel、repository、spool/dead-letter 和 evidence service 负责落盘与恢复。
- Preview/Observation/Scene/浏览器缓存只是投影；不能充当正式 Inspection history 或结果库。
- Inspection SSE 使用的 `IEventStore` 是有界内存 replay，不是持久结果库；不要与持久化 JSONL 的 AgentRun EventStore 混为一谈。

### Runtime Package 与 Station

- `RuntimePackageExporter` 从 Project 的 canonical DTO、Flow hash、`PersistenceRevision` 和正式 assets 生成运行包并校验 revision 一致性。
- `RuntimeHost` 加载运行包的 execution snapshot、执行流程、持久化现场变量状态和结果记录。
- Station 是独立 WinForms 进程，注册 `RuntimeHost`、package deployment、本地 settings/site profile、spool/journal 和 SignalR 同步服务。Station 不依赖 Studio 前端实现。
- Studio inspection history 与 Station result summary 是不同权威域；Station 上报的是受限、带 ACK/spool 语义的 runtime summary，不是完整 `InspectionResult`。
- Desktop Station ingress 与 StationSync 当前默认关闭；代码具备链路不等于现场连接已启用或已验收。

## 旧 `FrontendV2` 的真实定位

代码事实：

- `FrontendV2/package.json` 仍标记早期 `studio2-frontend-v2` 版本；源码内部 build info 停留在 `G04B`。
- 它通过动态 import 直接复用 legacy `httpClient`、`webMessageBridge`、`eventBus`、`serviceRegistry` 和 `flowCanvasAdapter`。
- 它实现了一个早期 Workspace Shell、FlowEditor port 和 Project persistence port，但默认未作为正式入口。
- Desktop `.csproj` 和主 CI 仍安装、构建并复制其资产到 `/v2`，属于当前仓库的历史集成事实。

本分支决策：

- `FrontendV2` 已废弃，仅作历史取证材料；不以其代码、路由、目录、组件、store、port、HostBridge 或样式为新地基。
- 旧 Studio2 的架构原则可重新验证后继承；旧 Goal 顺序、完成报告、实现代码和过去 PASS 不能直接继承。

## 可以继承的原则

- capability 单一 mounted owner、单一订阅集合、单一写入口。
- EventBus、ServiceRegistry、HTTP、HostBridge、Canvas 和保存链避免重复建设。
- 前端状态只作投影/草稿，后端 revision 与业务服务保持权威。
- FlowCanvas/ImageCanvas 通过 adapter 托管，生命周期资源统一 dispose。
- Feature Flag 切换必须真正停止未选中的 owner，不能只做 CSS 隐藏。
- build/publish 静态资产审计、no-Node 运行、真实 WebView2、DPI、生命周期和回滚必须作为独立验收类别。

## 明确不继承的实现

- `FrontendV2` 的 Vue 组件、Workspace Shell、Pinia store、typed ports、`hostBridge.ts`、legacy dynamic imports 和 `/v2` 路由。
- 旧 Studio2 的 G00—G16 执行卡、阶段状态机和逐 Goal 流水账维护方式。
- 旧原型的绿色视觉语言、局部 CSS 和占位页面。
- 过去 build/test/publish 的结论、测试数量、截图或 SHA；需要时必须在当前分支重新运行并记录真实结果。

## 已确认代码与配置风险

1. 当前正式前端的 composition 副作用分布在 `index.html` 与大型 `app.js`。命令式 Canvas、capability owner、订阅、timer、SSE 和请求生命周期集中；未发现应用级统一 teardown，多个资源虽暴露 dispose，但 bootstrap 未集中调用，构成双挂载和资源残留风险。
2. `ServiceRegistry.register()` 会覆盖同 key 服务且不会自动 dispose 被替换对象；唯一性必须由 composition root、调用方和架构守卫保证。
3. `FrontendV2` 仍参与 Desktop build/publish 且动态依赖 legacy `/src` 模块；复用它会继续绑定旧迁移路径。
4. Desktop 默认端口、数据库和 WebView2 user-data 具有共享默认值；多 worktree 并发运行存在端口、数据库、用户数据和进程互斥冲突风险，必须显式隔离。
5. DPI 配置不一致：Desktop `.csproj` 声明 `PerMonitorV2`，`Program.Main` 又显式调用 `HighDpiMode.SystemAware`，且 manifest 未声明 DPI。真实行为不能仅凭任一配置推断。
6. Playwright 只服务静态 `wwwroot` 并运行 Chromium；它不能证明 WinForms/WebView2 bridge、真实宿主启动、真实 DPI 或本地 API 全链路。
7. 当前四个 workflow 都不监听 `studio-ui-next` push；首次 push 不会形成 CI 证据。
8. Feature flags 在 bootstrap 时一次性读取，当前代码没有安全的应用级热切换/unmount 协议；运行时改 flag 不能视为可靠 cutover。
