# 知识库初始化统一基准方案

> 状态：`active` ｜ 文档类型：`plan` ｜ 创建：`2026-07-22` ｜ 目标：作为后续接入任何知识库平台的统一初始化基准
> 关联事实源：`docs/参考资料/规范/文档治理标准.md`、`docs/ai/operator-knowledge/operator_knowledge_schema.json`、`models/model_catalog.json`、`quality/evals/reports/operator_quality_matrix.md`

---

## 0. 背景与现状摘要（只读调研结论）

本方案在**不改动任何现有文件**的前提下，对 ClearVision 现有知识组织做了只读盘点。结论是：底层基础已经很强，缺的是"跨域、跨平台"的同一套初始化口径。

### 0.1 已存在的六块基础（直接复用，不重造）

| 基础 | 事实源 | 可复用的约定 |
|---|---|---|
| 文档治理标准 | `docs/参考资料/规范/文档治理标准.md` | 单一事实源、文档状态 6 态、文档类型 11 类、生命周期、命名与 front matter |
| 文档治理台账 / 审计 / 健康检查 | `docs/文档治理台账-2026-05-31.md`、`docs/文档审计报告-2026-05-31.md`、`docs/文档健康检查报告-2026-05-16.md` | 治理节奏、断链/编码/TODO 占位自动检查口径 |
| 算子名片 | `docs/算子资料/算子名片/_TEMPLATE.md` | 原子知识单元的章节模板（基本信息/算法/参数/端口/性能/场景/限制/变更） |
| 算子知识图谱 Schema v2 | `docs/ai/operator-knowledge/operator_knowledge_schema.json` | 结构化字段 + `IntentTags`/`ScenarioTags` + 8 类关系边（`PRODUCES`/`CONSUMES`/`USED_IN_TEMPLATE`/`HAS_EVIDENCE` 等） |
| 模型目录 | `models/model_catalog.json` | 模型 `id`/`type`/发布门禁字段（`modelSha256`/`license`/`labelsContract`/`reportId`…） |
| 算子质量矩阵 | `quality/evals/reports/operator_quality_matrix.md` | 四轴质量态（Execution / AlgorithmQuality / ProductionReadiness / FieldValidation）+ 成熟度 + 优先级 |

### 0.2 当前缺口（本方案要补的）

1. **碎片化**：`docs/` 下除原治理标准覆盖的 9 个区外，还生长出 `ai/`、`engineering/`、`frontend/`、`runtime/`、`operator-library/`、`operator-quality/`、`validation/`、`quiet-precision/`、`试验细则/`、`面试/` 等新区，彼此没有统一分类契约。
2. **定义域窄**：知识图谱与质量矩阵目前只覆盖"算子"域，计划/审计/指南/模型/试验细则等没有被同一套 schema 描述。
3. **标签是隐式的**：现有"分类"靠目录层级 + front matter 表达，没有显式、跨平台可检索的标签词汇表；`IntentTags`/`ScenarioTags` 只在算子卡里出现。
4. **平台绑定**：整套知识活在文件系统里，没有"导入任意平台（Notion / Confluence / 腾讯乐享 iWiki / 向量库）"的映射契约。

> 本方案的核心主张：**把算子知识卡 schema 泛化为"知识单元"schema，把 6 块基础收敛为一套分类 + 命名 + 标签 + 维护基线，使任何平台都能无损接入。**

## 1. 设计目标与原则

| 原则 | 说明 |
|---|---|
| 平台无关 | 只用"分类 / 命名 / 标签 / 元数据"四件事描述知识，不依赖任何平台的特有能力。 |
| 单一事实源 | 每条知识有且仅有一个正式存放点，镜像/导出是派生产物，禁止手改镜像当事实源。 |
| 受控词汇 | 分类、状态、类型、质量轴、标签全部走"受控词表"，不允许自由拼写。 |
| 机器可读 | 元数据用结构化 front matter / JSON Schema，人和平台都能消费。 |
| 最小侵入 | 复用现有目录与命名，不强制搬迁存量；新内容按基线落地即可。 |
| 证据边界 | 文档措辞不能替代现场/产线签收；质量与成熟度必须有可追溯证据路径。 |

## 2. 分类结构（统一分类树）

分类是知识的第一层坐标。**域（domain）= 顶层坐标；其余为交叉维度（状态/类型/质量轴/成熟度），用标签表达，不建额外目录树。**

### 2.1 知识域（受控词表 `domain`）

| `domain` | 中文 | 正式入口（现状） | 备注 |
|---|---|---|---|
| `operator` | 算子 | `docs/算子资料/`、`docs/ai/operator-knowledge/` | 已有 schema v2，本方案的直接蓝本 |
| `plan` | 计划 | `docs/进行中/当前计划/` | 含提升 TODO、Studio2 等 |
| `audit` | 审计 | `docs/审计资料/` | 算子/算法/系统/外部审计 |
| `reference` | 参考资料 | `docs/参考资料/` | 规范/指南/手册/PR 门禁 |
| `template` | 模板 | `docs/模板/` | 计划/任务/闭环/验收模板 |
| `model` | 模型 | `models/` | 目录 + 发布门禁 |
| `quality` | 质量证据 | `quality/evals/reports/`、`docs/operator-quality/` | 质量矩阵、证据清单、回归报告 |
| `guide` | 指南教程 | `docs/参考资料/指南/`、`docs/试验细则/` | 含试验细则、检测教程 |
| `runtime` | 运行时 | `docs/runtime/`、`docs/engineering/`、`docs/frontend/` | 同步 SOP、契约、前端通信 |
| `scenario` | 业务场景 | `线序检测/`、`docs/面试/` | 终端线序、黄金场景包等 |
| `archive` | 归档 | `docs/归档/` | 已关闭/历史/过期 |
| `temp` | 临时 | `docs/临时/` | 过程草稿，定期清理或转正 |

> 设计要点：**目录层级只表达 `domain` + `status` 两个维度**（沿用现状的 `进行中/归档/临时` 分区），其余维度（类型、质量轴、场景、受众）一律用标签，避免目录爆炸。

### 2.2 交叉维度（受控词表，作为标签）

| 维度 | 词表 | 来源 |
|---|---|---|
| `status`（生命周期状态） | `active` / `needs-review` / `closed` / `archived` / `deprecated` / `snapshot` | 复用文档治理标准 |
| `doc_type`（文档类型） | `index` / `plan` / `task-list` / `audit` / `report` / `standard` / `guide` / `manual` / `template` / `record` / `snapshot` | 复用文档治理标准 |
| `category`（算子分类） | `Acquisition` / `ImagePreprocessing` / `SegmentationAndRegion` / `FeatureExtraction` / `MatchingAndLocalization` / `DefectDetection` / `Measurement` / `CalibrationAndCoordinates` / `AiInference` / `PointCloud3D` / `DataProcessing` / `FlowControl` / `Communication` / `OutputAndAuxiliary` | 复用 CATALOG 14 类 |
| `maturity`（成熟度） | `stable` / `experimental` / `reference` / `compatibility-only` / `deprecated` | 复用名片 + 质量矩阵 |
| `quality_axis`（质量轴） | `Execution` / `AlgorithmQuality` / `ProductionReadiness` / `FieldValidation` | 复用四轴质量态 |
| `evidence_level`（证据等级） | `none` / `contract` / `golden` / `dataset` / `field-replay` | 由质量矩阵映射 |
| `audience`（受众） | `engineer` / `tester` / `auditor` / `pm` / `ai-agent` / `external` | 新增 |
| `scenario`（场景标签） | `wire-sequence` / `screw-inspection` / `defect` / `calibration` / `measurement` … | 新增，源自 `ScenarioTags` |
| `intent`（意图标签） | 取自算子 `IntentTags`（如 `locate` / `measure` / `classify`） | 复用算子卡 |

## 3. 命名规范

### 3.1 文件名

| 类别 | 规则 | 示例 |
|---|---|---|
| 长期稳定入口 | `README.md` / `导航.md` / `索引.md` / `CATALOG.md` | `docs/算子资料/README.md` |
| 主题文档 | `主题-YYYY-MM-DD.md`（主题用中文或 PascalCase，禁止空格） | `知识库初始化统一基准方案-2026-07-22.md` |
| 周期/审计文件 | 稳定前缀 + 序号 | `Week5-审计台账.md` |
| 结构化数据 | `xxx_catalog.json` / `xxx_matrix.md` / `xxx_schema.json` | `model_catalog.json` |
| 资产/图片 | `主题-描述.扩展名`，放 `docs/图片/` 或 `图片/` | `线序检测-端子特写.jpg` |

### 3.2 标题与 H1

- 每个知识文件 H1 与文件名主题一致；结构化单元（如算子卡）H1 为"中文名 / English Name"。
- 禁止在标题里写状态时态（如"最新""最终"），状态用 `status` 标签表达。

### 3.3 全局唯一 ID（跨平台锚点）

每条知识单元必须有一个稳定 `id`，用于平台导入后去重与互链：

- 算子：`OperatorType.<Enum>`（如 `OperatorType.CaliperTool`）
- 模型：`model:<id>`（如 `model:coco_yolo_external_onnx`）
- 文档/计划：`kb:<domain>/<slug>`（如 `kb:plan/kb-init-baseline`）
- 质量报告：`qr:<operator>:<dataset>:<variant>`（如 `qr:CaliperTool:golden:baseline`）

> `id` 一旦分配不可变更；重命名/迁移只改展示名，不改 `id`。这是跨平台同步的"主键"。

## 4. 标签规范（显式、受控、跨平台可检索）

### 4.1 标签与目录的关系

- **目录 = `domain` + `status` 的物理落点**（沿用现状分区，最小改动）。
- **标签 = 其余所有维度的逻辑坐标**，写在元数据里，平台侧建立索引即可跨域检索。
- 同一份知识可被多标签命中（如一张"测量类算子精度验收报告"同时带 `doc_type=report`、`category=Measurement`、`evidence_level=field-replay`、`audience=tester`）。

### 4.2 受控标签词汇表（唯一真值，禁止自由扩展）

见第 2.2 节的维度词表。新增标签必须走"提案 → 治理台账记录 → 写入词表"流程，不允许在单篇文档里私自发明。

### 4.3 知识单元元数据 Schema（跨平台契约）

本方案把算子知识卡 `operator_knowledge_schema.json` **泛化为通用「知识单元」Schema**。所有域的知识都套同一套 front matter，平台导入零改造。

归一化 front matter（YAML，所有文件通用）：

```yaml
---
id: "kb:plan/kb-init-baseline"          # 全局唯一主键（§3.3）
title: "知识库初始化统一基准方案"
domain: "plan"                          # §2.1 受控词表
doc_type: "plan"                        # §2.2 受控词表
status: "active"                        # §2.2 受控词表
category: ""                            # 算子域填 14 类之一，其余留空
maturity: ""                            # stable/experimental/...
evidence_level: "none"                  # none/contract/golden/dataset/field-replay
audience: ["engineer", "ai-agent"]      # §2.2 受控词表
scenario: []                            # 场景标签
intent: []                              # 意图标签（算子域）
tags: []                                # 自由但建议受控的补充说明
created: "2026-07-22"
updated: "2026-07-22"
owner: "知识治理负责人"                  # 责任人，禁止空缺
source_of_truth: true                   # 是否为正式事实源（镜像填 false）
aliases: []                             # 历史别名/旧显示名，仅用于检索兼容
---
```

> 完整机器可读 Schema（JSON Schema draft 2020-12，泛化自 `operator_knowledge_schema.json`）见同目录配套文件 `知识库初始化统一基准-知识单元Schema.json`，可直接作为平台导入的字段契约。

## 5. 维护规则

### 5.1 单一事实源与镜像

- 每条知识有且仅一个 `source_of_truth: true` 落点（见 §2.1 正式入口列）。
- 导出/镜像（如 `docs/operators/`、`算子资料/` 根镜像、平台副本）`source_of_truth: false`，由生成器同步，**禁止手改镜像当事实源**。
- 算子类：继续走 `scripts/OperatorDocGenerator`；知识图谱类：继续走 `quality/tools/OperatorKnowledgeGraphRunner`；本方案新增的跨域索引由统一生成器产出。

### 5.2 生成物同步

- 任何 `source_of_truth` 变更后，必须重跑对应生成器，使 `CATALOG.md` / `OPERATOR_CATALOG.md` / 知识图谱 / 质量矩阵 / 跨域索引保持一致。
- 不手动复制第二份索引；确需镜像时在变更记录/治理台账中说明。

### 5.3 生命周期流转

严格沿用文档治理标准的五步生命周期，并补充状态机：

```
创建(active) → 待复核(needs-review) → 转正(active) | 关闭(closed,写闭环说明后入 archive/已关闭事项)
                                   ↘ 归档(archived) / 弃用(deprecated) / 快照(snapshot)
```

- 关闭计划：先写闭环说明（完成项/验证方式/遗留边界/后续入口），再迁入 `docs/归档/已关闭事项/`。
- 重新启用历史资料：新建 `active` 文档并引用旧文，不改写旧快照。

### 5.4 健康检查与审计节奏

复用既有健康检查口径，扩展为"知识库级"巡检：

| 检查项 | 频率 | 口径 |
|---|---|---|
| 断链检查 | 每次提交 / 周 | 活跃文档本地相对链接断链 = 0 |
| 编码与占位 | 每次提交 | 无 `U+FFFD`、无私有 citation 标记、名片 TODO 占位仅留模板 |
| 元数据完整性 | 每次提交 | 必填 `id`/`title`/`domain`/`doc_type`/`status`/`owner` 齐全 |
| 标签合法性 | 周 | 所有标签命中 §2.2 受控词表，无私自发明 |
| 事实源一致性 | 月 | 各 `CATALOG`/矩阵/图谱口径与正式入口一致 |
| 证据边界 | 月 | 无 `field-replay=No` 被写成"产线签收完成"的越界措辞 |

### 5.5 质量门禁与证据边界

- 模型/AI 算子发布门禁字段（`modelSha256`/`license`/`labelsContract`/`reportId`…）沿用 `models/model_catalog.json` 的 `releaseGate`。
- 质量结论必须引用质量矩阵或专项证据报告，**不得只引名片里的质量分**。
- 公开数据集/冒烟证据**不得**表述为产线签收，除非有 `field-replay` 证据（沿用既有 claim boundary）。

### 5.6 所有权与准入

- 每份 `source_of_truth` 知识必须填 `owner`（人或 Agent），空缺不予合入。
- 新增文档必须能从主入口或分区 README 追溯；新增计划前先查是否已有同主题 `active` 入口。
- 外部审计建议须先转写为内部计划/审计/修复清单再执行。

### 5.7 平台接入同步规则

- 平台只是"视图"，不是事实源；平台内副本 `source_of_truth: false`。
- 同步方向：文件系统（事实源）→ 平台，单向；平台侧的评论/批注通过回写或定期人工归集回事实源。
- 跨平台去重键 = `id`（§3.3）；平台内禁止用标题去重。

## 6. 平台接入映射（"任何平台"通用契约）

同一套分类 + 命名 + 标签 + 元数据，映射到不同平台时只换"容器"，不换"语义"：

| 本方案概念 | 文件系统 | Notion | Confluence | 腾讯乐享/iWiki | 向量库(RAG) |
|---|---|---|---|---|---|
| `domain` | 顶层目录 | 顶层 Database/Workspace | Space | 知识库/分类 | namespace / metadata 字段 |
| `doc_type`/`status` | 分区目录 + front matter | Select 属性 | Page Properties | 属性/标签 | metadata 字段 |
| `category`/`maturity`/`evidence_level`/`audience`/`scenario`/`intent` | front matter | Multi-select 属性 | Labels | 标签 | metadata 字段（参与检索过滤） |
| `id` | 文件名 + front matter | Page ID 映射表 | Page ID | 文档 ID | chunk 的 `doc_id` |
| 正文 + 章节 | Markdown 文件 | Page 内容 | Page 内容 | 文档正文 | 切片文本 + metadata |
| 关系边（算子图谱） | `operator_knowledge_graph.json` | Relation 属性 | References | 双向链接 | 图边 / 关系表 |

> 接入新平台只需：(1) 把 front matter 映射为平台属性；(2) 用 `id` 建去重键；(3) 把 §2.2 词表配置为平台下拉/标签受控项。无需改动知识本体。

## 7. 初始化清单（Bootstrap Checklist）

新建或接入一个平台时，按顺序执行：

- [ ] 1. 确认事实源落点：为每个 `domain` 指定唯一 `source_of_truth` 目录（见 §2.1）。
- [ ] 2. 配置受控词表：把 §2.2 的词表录入平台的下拉/标签受控项，关闭自由输入。
- [ ] 3. 补齐元数据：存量重要文档补 front matter（至少 `id`/`title`/`domain`/`doc_type`/`status`/`owner`）。
- [ ] 4. 建立 `id` 映射表：文件系统 `id` ↔ 平台内部 ID 的对照（避免重复导入）。
- [ ] 5. 部署生成器：算子（`OperatorDocGenerator`）、知识图谱（`OperatorKnowledgeGraphRunner`）、跨域索引（新增）接入 CI。
- [ ] 6. 接入健康检查：把 §5.4 的检查项挂到提交门禁与周巡检。
- [ ] 7. 配置关系导入：算子图谱 8 类边映射到平台关系能力（或无则存为结构化字段）。
- [ ] 8. 试运行 + 审计：跑一轮健康检查与文档审计，把缺口登记到治理台账。
- [ ] 9. 写闭环说明：初始化完成，记录口径版本与后续维护责任人。

## 8. 与现有体系的衔接

- 本方案**不替代** `文档治理标准.md`，而是它的"跨域 + 跨平台扩展版"：把原本只覆盖 `docs/` 的规则，上探到全仓库知识（含 `quality/`、`models/`、算子知识图谱），并补上"标签词汇表"和"平台映射"两块原本缺失的拼图。
- 算子域完全沿用 `operator_knowledge_schema.json` 与质量矩阵，本方案仅将其元数据字段**提升为全库通用 front matter**。
- 建议本方案评审通过后，迁入 `docs/参考资料/规范/`，并在 `文档治理标准.md` 中增加"跨平台知识单元"一节作为引用；在 `文档治理台账` 登记本次基线版本 `kb-baseline/2026-07-22`。
