# 现场无光电/PLC触发 —— 端子线序检测改造评估报告

> 基于 ClearVision 当前代码架构（Commit 基准：2026-05-07）

---

## 一、当前架构现状（代码层面已确认）

### 1. 相机连接与触发支持

底层相机抽象已经完整支持三种触发模式：

| 模式 | 枚举值 | 现状 |
|------|--------|------|
| **Software（软触发）** | `CameraTriggerMode.Software = 0` | ✅ 已启用，默认模式 |
| **External（外部触发）** | `CameraTriggerMode.External = 1` | ✅ 已启用，支持 PLC/IO 硬触发 |
| **Continuous（连续采集/FreeRun）** | `CameraTriggerMode.Continuous = 2` | ⚠️ **底层已支持，但 UI/算子参数未暴露** |

关键实现：
- `CameraFrameStreamCoordinator.cs`（帧流协调器）已经实现了 `Continuous` 模式的生产者-消费者架构，支持按 `TargetFrameRateFps` 限流、多消费者共享同一相机流、空闲 5 秒自动停止。
- `InspectionWorker.cs` 的 `IsFrameDrivenExecution()` 已经把 `External` 和 `Continuous` 识别为帧驱动模式，会进入**来帧即检**的循环（成功后不 delay，立即等待下一帧）。

### 2. 图像采集算子

`ImageAcquisitionOperator.cs` 当前暴露的参数：
```csharp
[OperatorParam("TriggerMode", "触发模式", "enum", DefaultValue = "Software", 
    Options = new[] { "Software|软件触发", "External|外部触发" })]  // ← 注意：没有 Continuous
```

- 算子内部代码逻辑实际上已经能处理 `Continuous`（通过 `bindingConfig.TriggerMode.IsFrameDriven()` 分支走 `_streamCoordinator.AcquireFrameAsync`），但前端/模板参数只给了 Software 和 External 两个选项。

### 3. 端子线序检测流程

当前模板（`terminal-wire-sequence.flow.template.json` v1.4.0）：

```
ImageAcquisition → DeepLearning(YOLO, 640×640) → BoxFilter → BoxNms → DetectionSequenceJudge → ResultOutput
```

- **深度学习算子** `DeepLearningOperator` 每次执行都会加载/使用 ONNX 模型做一次完整推理，模型输入 640×640。
- **流程执行** `FlowExecutionService.ExecuteFlowAsync` 每轮检测会串行（或并行）执行所有算子。
- 这意味着：**每一张送入流程的图，都会触发一次 YOLO 推理**。

## 二、如果直接改成"视频流检测"会暴露的问题

你提到的"连续视频检测"在技术上**底层已经能跑通**，但如果直接把相机设成 `Continuous` 并让 `InspectionWorker` 每帧全检，会撞上三个大问题：

### 问题 1：算力爆炸（最关键）

假设皮带线速度一般，你设 10fps 连续采集：
- 每秒 10 帧，每帧跑一次 640×640 的 YOLO 推理。
- 端子可能 5~10 秒才来一个，**90% 以上的帧都是在空跑**（皮带空转、无料状态）。
- 即使 GPU 能撑住，风扇狂转、整机发热、功耗都是问题，笔记本/工控机现场很可能扛不住。

### 问题 2：重复检测

一个端子从进入视野到离开视野，会停留 N 帧（取决于视野宽度和皮带速度）。
- 没有"来料隔离"逻辑的话，**同一个端子会被判定多次**，结果输出会刷屏。
- 如果第一次 NG、第二次 OK、第三次 NG，统计和产线动作都会乱。

### 问题 3：结果输出没有防抖/消抖

当前 `InspectionWorker` 每轮成功后立即发 `InspectionResultEvent`，前端/IO 动作（如打标、剔料）没有与"物料到位"对齐，而是与"帧到达"对齐。

## 三、可选方案对比

| 方案 | 改动量 | 算力消耗 | 漏检风险 | 重复检测 | 对现有架构影响 | 推荐度 |
|------|--------|----------|----------|----------|----------------|--------|
| **A. 直接 Continuous + 每帧全检** | 极小 | **极高** | 低 | **高** | 几乎不改 | ⭐ |
| **B. Timer 软触发** | 极小 | 中 | 中 | 中 | 几乎不改 | ⭐⭐ |
| **C. Continuous + 帧变化检测（软件触发）** | 中等 | **低** | 低 | **低** | 需新增算子/Worker 逻辑 | ⭐⭐⭐⭐⭐ |
| **D. 加装光电传感器（硬件方案）** | 小（硬件） | 低 | 极低 | 无 | 无需改软件 | ⭐⭐⭐⭐⭐ |
| **E. 编码器触发（如有编码器）** | 中（硬件+软件） | 低 | 低 | 无 | 需新增编码器算子 | ⭐⭐⭐⭐ |

### 方案说明

**A. 直接 Continuous + 每帧全检**
- 把 `ImageAcquisitionOperator` 的 `TriggerMode` 参数里加上 `Continuous`，相机绑定配置设成 `Continuous`，`InspectionWorker` 就会进入帧驱动循环。
- **不建议**：空跑严重、重复判定、结果刷屏。

**B. Timer 软触发**
- 用现有 `TriggerModuleOperator` 的 `Timer` 模式，每隔固定时间（比如 500ms~1s）触发一次 `ImageAcquisitionOperator`。
- **能用但不理想**：间隔设短了浪费算力，设长了容易漏检；端子到达时间是随机的，定时触发命中率不高。

**C. Continuous + 帧变化检测（软件方案，推荐）**
- 相机以 `Continuous` 模式自由运行（比如 5~10fps），但**不是每帧都进检测流程**。
- 在图像进入 `DeepLearning` 之前，先做一次**轻量级的帧间变化检测**（帧差、背景减除、ROI 灰度变化等）。
- 只有当变化量超过阈值（= 有新物体进入视野）时，才将该帧送入完整检测流程。
- 同时加一个**检测冷却期**（比如 1~2 秒），防止同一端子停留期间被重复判定。
- **这是软件层面最平衡的方案**。

**D. 加装光电传感器（硬件方案，最推荐）**
- 在皮带线入口或检测工位前装一个对射式/漫反射式光电开关（几十到一百多块钱）。
- 光电信号接入 USB IO 模块或直接接入 PLC（如果有的话），再映射为 `External` 触发。
- 这是工业现场最可靠、最省心的做法，**软件几乎不用改**。

**E. 编码器触发**
- 如果皮带线电机有编码器输出，可以按固定脉冲数触发采图。
- 需要新增编码器采集算子或接口，改动量较大。

## 四、推荐方案与实施规划

### 短期建议（首选）：加装光电传感器

如果现场允许动硬件，**这是性价比最高、最可靠的方案**。
- 买一个 24V 对射式光电开关（如欧姆龙 E3F 系列），装在端子进入相机视野前的位置。
- 如果工控机有 IO 卡/USB IO 模块，把光电信号接入后，在 ClearVision 里把相机绑定配置设为 `External`，即可实现"来料即检"。
- 不需要改任何代码。

### 如果现场不能加装硬件：软件方案「Continuous + 帧变化检测」

如果现场确实不能动硬件（客户不允许、空间不够、工期太紧），按下面两阶段实施：

---

#### 阶段 1：最小改动快速可用（预计 1~2 天）

目标：让现有架构支持 `Continuous` 模式，并在 `InspectionWorker` 层加上简单的变化过滤和冷却期。

**改动点 1：暴露 Continuous 选项**
```csharp
// ImageAcquisitionOperator.cs
[OperatorParam("TriggerMode", "触发模式", "enum", DefaultValue = "Software", 
    Options = new[] { "Software|软件触发", "External|外部触发", "Continuous|连续采集" })]
```
> 实际上算子内部代码已经兼容，只需要改这一行让前端能选。

**改动点 2：相机绑定配置界面允许设置 Continuous**
- `CameraBindingConfig` 已经有 `TriggerMode` 和 `TargetFrameRateFps` 字段。
- 在 Desktop 设置端点或配置文件中，把对应相机设成 `"triggerMode": "Continuous"`，`"targetFrameRateFps": 5`（根据皮带速度调整，5fps 通常够用）。

**改动点 3：在 `InspectionWorker` 检测循环中加入变化检测 + 冷却期**

在 `RunRealtimeLoopAsync` 的 `ExecuteCycleAsync` 调用前后，加入以下逻辑：

```csharp
// 伪代码，示意
private Mat? _lastFrame;
private DateTime _lastDetectionTime = DateTime.MinValue;
private readonly TimeSpan _detectionCooldown = TimeSpan.FromSeconds(1.5);

// 在 ExecuteCycleAsync 获取到 frame 后
if (!IsSignificantChange(currentFrame, _lastFrame) || 
    (DateTime.UtcNow - _lastDetectionTime) < _detectionCooldown)
{
    // 变化不够大 或 还在冷却期 → 跳过本轮深度学习，直接 continue
    cycleSucceeded = true; // 避免触发退避
    continue;
}

_lastFrame = currentFrame.Clone();
_lastDetectionTime = DateTime.UtcNow;
// 继续执行完整流程...
```

`IsSignificantChange` 可以用最简单的帧差法：
1. 将当前帧和上一帧转灰度；
2. 做绝对差分 `Cv2.AbsDiff`；
3. 对差分图二值化（阈值比如 30）；
4. 统计非零像素数或计算均值；
5. 如果超过阈值，认为有新物体进入。

> 端子线序检测场景背景相对固定（皮带/工装板），帧差法在这种场景下效果很好。

**阶段 1 产出**：
- 端子到达时，帧间变化触发检测；
- 同一端子停留期间，冷却期阻止重复判定；
- 皮带空转时，变化量小，直接跳过，**YOLO 不会被调用**。

---

#### 阶段 2：算子化/产品化（预计 3~5 天）

目标：把变化检测和冷却逻辑从 `InspectionWorker` 下沉为独立算子，让流程更灵活、可配置。

**新增算子：`FrameChangeTriggerOperator`**

```csharp
[OperatorMeta(DisplayName = "帧变化触发", Category = "逻辑工具")]
[InputPort("Image", "图像", PortDataType.Image, IsRequired = true)]
[OutputPort("Triggered", "是否触发", PortDataType.Boolean)]
[OutputPort("ChangeMask", "变化掩码", PortDataType.Image)]
[OperatorParam("Threshold", "变化阈值", "double", DefaultValue = 0.05, Min = 0.0, Max = 1.0)]
[OperatorParam("RoiX", "ROI X", "int", DefaultValue = 0)]
[OperatorParam("RoiY", "ROI Y", "int", DefaultValue = 0)]
[OperatorParam("RoiW", "ROI 宽", "int", DefaultValue = 0)]  // 0=全图
[OperatorParam("RoiH", "ROI 高", "int", DefaultValue = 0)]
[OperatorParam("CooldownMs", "冷却时间(ms)", "int", DefaultValue = 1000, Min = 0, Max = 10000)]
[OperatorParam("MinChangeArea", "最小变化面积", "int", DefaultValue = 500, Min = 0)]
public class FrameChangeTriggerOperator : OperatorBase { ... }
```

流程模板改为：
```
ImageAcquisition(Continuous) 
    → FrameChangeTrigger        // 有变化且过冷却期 → Triggered=true
    → (条件分支或门控) 
    → DeepLearning
    → BoxFilter
    → BoxNms
    → DetectionSequenceJudge
    → ResultOutput
```

或者更简单地，让 `FrameChangeTriggerOperator` 在 `Triggered=false` 时直接中断/跳过下游执行。

**阶段 2 优势**：
- 参数化：用户可自己调阈值、ROI、冷却时间；
- 可视化：可输出 `ChangeMask` 图，方便现场调参时看变化区域；
- 通用性：不只线序检测，其他无触发场景也能复用。

## 六、总结

1. **你担心"对视频流检测支持不够"，实际上底层（`CameraFrameStreamCoordinator` + `Continuous` 模式）已经支持了**，缺的只是算子参数没暴露 + 检测循环没有"变化过滤"机制。

2. **比"视频检测"更好的方法有两个优先级**：
   - **第一优先（推荐）**：现场加装一个光电传感器，走 `External` 触发。这是最工业、最稳定、最省算力的做法。
   - **第二优先（纯软件）**：启用 `Continuous` 模式 + 帧间变化检测 + 冷却期防抖。改动量中等，能在不碰硬件的情况下解决无触发问题。

3. **不建议直接 Continuous 每帧全检**，算力浪费和重复判定会让你现场很难受。
