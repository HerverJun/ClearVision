# ClearVision 产品审计报告（2026-05-16）

## 1. 审计结论

ClearVision 当前已经不是单点 OpenCV demo，而是一套面向工业视觉检测的本地化平台型产品：它把 Windows Studio、WebView2 前端、本地 ASP.NET Core API、流程编排、156 个视觉/测量/通信/AI 算子、运行包导出、Station 现场同步、PLC/相机接入、质量矩阵与 OperatorLibrary NuGet 打包放在同一条产品链路中。

从产品状态看，项目已经具备“可演示、可持续迭代、可工程化验证”的基础，但距离“可稳定对外承诺工业闭环交付”还有几类缺口：真实产线签核证据不足，部分功能仍处于占位/内部能力状态，前端和 AI 编排热点文件偏大，算子质量等级与证据等级容易被误读，SDK/文档口径仍有少量不一致。

建议把下一阶段目标从“继续堆功能”收敛为“现场可信交付”：围绕真实场景包、运行包、Station 健康诊断、AI/模型 gate、性能证据和文档口径做收口。产品叙事应强调“工业视觉平台骨架 + 可证据化治理体系”，避免把 public dataset、semi-synthetic、field-substitute replay 或 smoke 结果包装成真实产线签收。

## 3. 产品定位

### 3.1 一句话定位

ClearVision 是一个面向工业视觉检测项目的本地化 Studio + Runtime + Station 平台，用流程编排和算子库把图像采集、预处理、检测、测量、标定、AI 推理、PLC 通信、结果持久化和现场同步串成可交付链路。

### 3.2 目标用户

| 用户 | 主要诉求 | ClearVision 当前支撑 |
|---|---|---|
| 视觉工程师 | 快速搭建检测流程，调参，验证效果 | Studio、流程画布、算子库、节点预览、模板与 Demo 工程 |
| 现场操作员 | 执行检测、看结果、少误操作 | 检测面板、结果看板、Station Monitor、健康状态 |
| 工艺/质量工程师 | 查看 OK/NG、缺陷趋势、追溯证据 | 检测历史、统计接口、结果面板、质量报告 |
| 集成工程师 | 接相机、PLC、MES/HTTP、运行包 | 相机设置、PLC profiles、通信算子、Runtime Package |
| 平台维护者 | 控版本、控质量、控发布边界 | CI gate、质量矩阵、OperatorLibrary、模型 manifest |

### 3.3 当前最强卖点

- 覆盖面宽：156 个正式算子，横跨预处理、定位、测量、标定、3D、AI、通信和流程控制。
- 架构不是玩具：WinForms + WebView2 + 本地 API + Runtime + Station 的端到端结构已经成型。
- 工程治理意识强：串行测试脚本、CI 最低测试数、密钥扫描、编码扫描、质量矩阵、性能 budget、field replay 口径都已存在。
- 现场链路初步闭环：运行包导出、Station 同步、健康、结果摘要、命令、部署包和审计记录已经进入代码和测试。
- AI 流程生成不只是 prompt：仓库中有 prompt composer、response parser、validator、自动修复、manual retry、模型配置与测试覆盖。

### 3.4 当前最需要克制的宣传点

- 不宜宣称“已完成真实工业产线签核闭环”。质量文档已经明确区分功能存在、public dataset、field-substitute replay 和真实产线签收。
- 不宜把 152 个 A 级算子理解为 152 个都具备同等现场证据。质量矩阵中 contract、golden、dataset、field replay 的覆盖差异很大。
- 不宜把 MQTT、部分高级分析、目录选择器、即时清理等能力包装成已可用生产功能。它们当前仍是占位、内部能力或未开放入口。

## 4. 产品能力地图

### 4.1 Studio 主工作台

当前 Studio 是产品的主入口，负责项目管理、流程编辑、算子配置、图像预览、检测运行、结果查看、设置、用户管理和 Station 监控。前端位于 `ClearVision.Product/src/ClearVision.Product.Desktop/wwwroot/src/`，以原生 JS 模块拆分，功能模块已经覆盖：

- `features/project/`：工程创建、打开、导入导出、Demo 工程。
- `core/canvas/` 与 `features/flow-editor/`：流程画布、属性面板、节点预览、ROI 编辑。
- `features/inspection/`：单次/连续检测、SSE 实时结果、检测状态。
- `features/results/`：结果面板、统计、趋势、缺陷分布、报告占位。
- `features/settings/`：系统设置、PLC、相机、AI 模型、用户管理。
- `features/stations/`：Station 监控、命令、部署和健康。
- `features/ai/` 与 `features/ai-generation/`：AI 流程生成与辅助配置。

产品评价：功能入口完整，但前端仍有明显“巨型模块 + legacy window 全局桥接 + console 调试输出”特征。短期可用，长期维护会越来越吃力。

### 4.2 本地 API 层

Desktop 内嵌 ASP.NET Core minimal APIs，覆盖：

- 工程 CRUD 与流程保存：`/api/projects`
- Runtime package 导出：`/api/projects/{id}/runtime-package/export`
- 检测执行与历史：`/api/inspection/*`
- 实时事件：`/api/inspection/realtime/{projectId}/events`
- 算子库与算子预览：`/api/operators/*`
- 模板：`/api/templates`
- AI 模型管理：`/api/ai/models`
- 设置、相机、PLC、触发输入：`/api/settings`、`/api/cameras/*`、`/api/plc/*`
- Station：`/api/stations/*`、`/api/station-packages/*`

产品评价：API 面已经覆盖 MVP 到现场联调的主要路径。近期值得继续做的是 API contract 文档与错误语义统一，避免前端和外部集成方靠读代码理解。

### 4.3 流程与算子体系

算子目录当前总数为 156，质量矩阵显示：

| 指标 | 当前值 |
|---|---:|
| 正式算子总数 | 156 |
| A 级 | 152 |
| B 级 | 4 |
| 有任意证据信号 | 155 |
| Contract evidence | 116 |
| Golden test | 46 + 1 partial |
| Dataset evidence | 16 + 6 partial |
| Field replay | 21 |
| 无证据信号 | 1 |

产品评价：算子广度是优势，证据密度是短板。A/B 级更像“功能成熟度”，不应直接等同“现场验证成熟度”。

重点风险：

- `FrameChangeTrigger` 已进入 156 正式目录；2026-05-20 已补齐 contract、dataset 与 field-substitute replay 证据，质量矩阵不再存在 `Any evidence signal = No` 算子。
- `MqttPublish` 在目录中显示为 A 级和 Stable，但源码明确是 `placeholder-disabled`，执行时返回 failure；这会造成“目录说可用，运行时不可用”的产品预期偏差。
- OperatorLibrary 包目录显式排除了 `FrameChangeTrigger`，但根算子目录已经把它纳入正式 156 口径。需要把“主产品正式算子”和“NuGet 包公开算子”两个边界讲清楚。

### 4.4 AI 流程生成与模型管理

AI 相关能力已经比较完整：

- 多模型配置、API key 不回显、连接测试。
- Prompt builder / composer / response parser / validator。
- 自动修复解析失败、manual retry、澄清上下文。
- 模型目录与 release gate 字段，包括 `modelSha256`、license、labels contract、provider fallback、dataset version、hardware profile、report ID。

产品评价：这是一个有潜力的差异化模块。问题不在“有没有 AI”，而在“AI 生成能否变成可审计、可复现、可现场交付的流程资产”。当前方向正确，但需要把 AI 生成结果的可解释性、模板约束、算子参数来源、风险提示和回退路径产品化。

### 4.5 Runtime Package 与 Station

运行包导出已具备较强工程边界：

- 导出前检查密钥类字段并阻止打包。
- 检查参数合法性、缺失文件或目录。
- 导出目录由 `RuntimePathGuard.ResolveControlledExportRoot` 限制在默认 Studio export root、`.tmp/publish-check`、系统 temp 或显式配置白名单。
- 测试已覆盖拒绝非受控目录、允许 `.tmp/publish-check`。

Station 同步链路也明显增强：

- Station sync 是 opt-in，需要 StudioHubUrl 和 SharedToken。
- 出站结果摘要队列为 bounded channel。
- 结果摘要先写本地 spool，再由同步任务推送。
- 队列满时记录 backpressure/dropped 计数，并暴露到 health snapshot。
- Station 命令、身份更新、部署包、测试包接口已有 Admin 校验。

产品评价：Station 已从“概念功能”向“现场可靠性功能”移动。下一步应把现场 SOP、故障诊断、断网恢复和证据包导出打磨成用户能看懂的产品流程。

### 4.6 结果看板与分析

结果看板已接入现有统计、缺陷分布、趋势和 inspection SSE/history 语义。高级分析仍未完全产品化：

- CPK、MTBF、缺陷聚类目前显示“暂无数据 / 未接入”，不再硬展示固定假数据。
- PDF 深度报告与图片打包仍是未接入占位。
- 吞吐面积图在趋势数据不足时仍“保持默认 Mock 路径”，文案和默认图形需要避免误导。

产品评价：结果看板可用于演示与基础追溯，但还不能承载严肃质量分析承诺。应优先做“真实数据可解释”，而不是扩展更多花哨指标。

## 8. 机会点与产品路线

### 8.1 最推荐的产品切入点

建议把 ClearVision 对外叙事聚焦在“可配置工业视觉工作站 + 证据化算子平台”，以端子线序检测作为主样板场景。

原因：

- 线序检测场景包已经有模板、规则、版本、样例与落地文档。
- `FrameChangeTrigger`、`DetectionSequenceJudge`、DeepLearning、NMS、Station sync 都能串进这个故事。
- 该场景能展示从工程配置、到运行、到现场结果、到质量证据的完整产品链路。

### 8.2 三个可打包版本

| 版本 | 目标 | 必备能力 | 不应承诺 |
|---|---|---|---|
| Demo / 面试演示版 | 展示平台完整性 | Studio、流程、156 算子目录、Demo 工程、基础检测报告 | 真实产线签核 |
| 内部试点版 | 小范围现场联调 | 运行包、Station、PLC 虚拟联调、spool/replay、日志和健康 | 长周期无人值守 |
| 生产候选版 | 可控产线 PoC | 真实样本、硬件 profile、模型 hash、现场签核、故障演练、SOP | 泛行业全自动适配 |

### 8.3 30 天优先路线

1. 统一产品口径：修正 SDK rollForward 文档/代码不一致，拆分“功能成熟度”和“证据成熟度”。
2. 修补算子目录风险：`FrameChangeTrigger` 补证据，`MqttPublish` 降级或显式禁用。
3. 做一份真实场景证据包：以线序检测为主，包含样本、模板、规则、运行包、Station 日志、结果、性能和签核记录。
4. 收敛结果看板：高级分析未接入就彻底禁用；已接入指标必须来自后端真实数据。
5. 清理前端调试噪声：优先 `settingsView.js`、`operatorLibrary.js`、`flowCanvas.js`、`httpClient.js`。

### 8.4 60-90 天路线

1. Runtime/Station：做断网、重启、队列满、spool 满、部署失败、包回滚的现场演练报告。
2. AI 生成：引入模板约束评分、参数来源标记、生成后 dry-run、用户确认清单。
3. OperatorLibrary：建立包级 public catalog、placeholder 排除策略、NuGet smoke/acceptance 分层。
4. 质量 gate：把 quick PR gate、nightly industrial gate、release gate 分层接到 CI。
5. 前端架构：从大文件拆出状态机和纯函数，保证每个关键用户路径有单测或 Playwright smoke。

### 9.1 演示版指标

- 新建 Demo 工程成功率：100%

- 演示环境无密钥泄漏、无乱码、无断链核心文档

### 9.2 试点版指标

- Station 断网后结果摘要不丢失：spool 可回放
- Station backpressure 可观测：dropped/backpressure/spool 指标出现在 health
- 核心算子 p95 在预算内：按场景分辨率承诺
- 每个试点场景至少有 20 个现场 OK/NG 样本和签核记录
- 运行包可复现：包 hash、flow hash、模型 hash、配置版本可追溯

### 9.3 生产候选指标

- 现场连续运行 8-24 小时无阻塞
- 断电/重启/Studio 离线/Station 离线有演练记录
- 结果持久化失败可恢复，dead letter 有告警和处理 SOP
- 模型 release gate 字段全量补齐
- 所有对外声明指标都有报告 ID 和数据集/硬件版本

## 10. 结论与下一步

ClearVision 的核心优势在于平台完整性和工程治理意识：它已经把工业视觉项目里最难散落的几件事放到同一个系统里了，包括算子、流程、运行包、现场同步、质量矩阵和 CI gate。这是一个很好的产品底子。

下一步最关键的不是继续扩大功能面，而是把“能跑”变成“能被证明可靠地跑”。建议先围绕线序检测做一条真实闭环样板，把算子证据、模型证据、运行包、Station、结果追溯、性能和现场签核串起来。等这条样板站稳，再扩展到其他检测场景，产品可信度会比单纯增加算子数量提升得更快。
